# 首版产品形态对比

日期：2026-09-09

状态：历史评估。用户已明确选择 **Electron 桌面应用**，见 [正式决策](../.ai/decisions/0003-electron-desktop.md)。下文保留初轮对比及当时建议，旧建议不再作为当前实施方向。

关联：[Spec 001](../specs/spec-001-product-and-technical-foundation/spec.md)。本文只比较使用形态，不代替后续完整产品定义和技术选型。

## 共同前提

- 产品运行在用户自己的电脑上，目标平台包括 macOS 和 Windows。
- UI 负责操作和展示，音频采集、ASR 和会议状态由本地应用核心管理。
- LLM 是否调用外部服务需单独确定，界面形态本身不决定数据是否外发。
- 当前优先验证 Meeting Agent MVP，再逐步加入周报和长期 Memory。

本次比较的“本地网页”指浏览器访问本机服务，由本地 Python 进程负责后续录音和模型调用。它仍需启动本地程序；不能仅打开一个静态网页就自动获得这些能力。

## 官方资料核对

Python 可以承担本地录音：sounddevice 官方文档说明其提供 PortAudio 绑定与音频录制功能，并列出 macOS 和 Windows 支持。该资料支持把采集放在本地 Python 层的候选方向，尚不能证明本项目在特定设备上的可靠性。[sounddevice 文档](https://python-sounddevice.readthedocs.io/en/latest/)

桌面窗口也可以使用 Web UI：pywebview 官方资料描述了独立窗口中的 Web 内容以及 Windows、macOS 支持；其架构文档允许窗口连接本地服务或采用 JavaScript / Python 桥接。因此桌面应用不必等同于为两个平台分别重写全部界面。[pywebview 简介](https://pywebview.flowrl.com/guide/)、[应用架构](https://pywebview.flowrl.com/guide/architecture.html)

本地网页需要运行服务进程：FastAPI 文档说明应用由 Uvicorn 等 ASGI 服务运行，并涉及进程运行与生命周期管理。本文将其列为实现这种形态的候选例子，没有选定 FastAPI 或相应版本。[FastAPI 运行说明](https://fastapi.tiangolo.com/deployment/manually/)

以上来源查阅于 2026-09-09。下述成本、优先级和复用判断是基于项目现状的工程判断，不是官方性能结论；本轮未安装这些依赖或执行录音验证。

## 两种方案

| 比较项 | 桌面应用 | 本地网页 + 本地 Python 服务 |
| --- | --- | --- |
| 用户入口 | 打开应用窗口；适合后续做成日常桌面工具 | 启动本地程序，再打开浏览器；可以后续封装自动打开页面 |
| 界面组织 | 可以采用原生组件，也可以用桌面容器承载 Web UI | 浏览器承载 UI，与本地服务通信 |
| 持续录音 | 由本地应用核心管理；窗口关闭时的继续 / 停止行为需设计 | 由独立于页面的本地服务管理；页面断开后的录音状态与重连需设计 |
| 本地 ASR 与存储 | 在本机运行与保存 | 同样可在本机运行与保存，不要求云服务 |
| 初期工程工作 | 除核心功能外，需要处理窗口生命周期、容器集成及选定的分发方式 | 可以先用开发启动入口验证核心功能；需要处理服务启停、端口和页面连接状态 |
| macOS / Windows 适配 | 验证录音与模型之外，还要验证选定的窗口后端和打包环境 | 验证录音与模型之外，还要验证浏览器交互及本地服务启动方式 |
| 系统级体验 | 有利于后续组织托盘、通知、快捷键等能力，实际能力取决于框架 | 这些能力通常仍需本地组件支持；当前 MVP 尚无此要求 |
| 后续演进 | 适合持续完善应用体验 | 若保持 Web UI 与核心边界清晰，可评估复用 UI 并添加桌面容器；仍需处理生命周期和分发差异 |

关闭窗口或页面并不自动确定录音是否停止。两种方案都需要独立设计录音生命周期、显式结束操作、可见状态和异常收尾；本文不预先承诺后台持续录音行为。

## 初轮建议（已被用户决策取代）

初轮曾建议首版优先评估“本地网页 + 独立的本地 Python 服务”。用户随后选择 Electron 桌面应用，后续设计按已确认的桌面方向推进。

理由是当前首先需要验证录音、转写、会后总结的核心链路，而产品尚未要求托盘、快捷键、商店分发或安装包。这个方向允许在既有 Python 方向上先建立应用核心与 UI 的边界，将桌面容器和分发工作留到体验需求明确时处理。

代价是启动本地服务的使用步骤，以及页面连接状态、端口和服务退出的设计工作。它不意味着免安装，也不意味着没有平台差异。

如果首版必须提供双击图标进入、统一窗口体验，或近期就要交给不使用开发工具的同事，应提高桌面应用方案的优先级，并将分发与安装要求纳入工程范围。当前尚未确认这些要求。

## 对后续架构的影响

两种方案都建议保持以下边界，具体接口和框架仍待选型：

```text
浏览器 UI 或桌面 UI
        ↓
本地应用核心
        ↓
录音 / ASR / Transcript / LLM / 存储
```

如果选择本地网页，后续设计需明确：

- 服务默认仅供本机访问，针对 UI 请求定义必要的访问边界。
- 录音任务归本地应用核心管理，不依附某次页面请求。
- 刷新、关闭或重开页面时，如何呈现和恢复真实会议状态。
- 用户如何显式结束会议、退出服务，异常退出如何保留已获得的数据。

这些是待设计要求，不是当前已实现能力。

## 当前结论

首版产品形态与桌面框架已确定为 Electron 桌面应用。具体界面框架、Electron 与 Python 的通信方式以及分发方案仍待细化；`constitution/tech-stack.md` 已区分已确认和待定内容。
