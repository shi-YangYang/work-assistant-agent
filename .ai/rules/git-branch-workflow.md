# Git 分支工作规则

更新日期：2026-09-11。

来源：用户最新要求固定维护 `dev` 开发分支，验证通过后通过 PR 合并到 `main`，随后将 `main` 合并回 `dev`。本规则替代此前默认直接在 `main` 开发的约定。

## 持续约定

- `dev` 和 `main` 长期保留；默认在 `dev` 开发、提交和推送，不为每个任务另建临时分支，也不直接在 `main` 开发业务改动。
- 开发与验收仍遵循 Spec 流程和 S0～S3 验证规则。本地按改动范围执行相关检查，推送 `dev` 后核对该提交的必需 CI；失败先在 `dev` 修复，不将未通过的改动合入 `main`。
- 开发验收与 `dev` 的必需检查通过后，创建 `dev → main` PR；如果已有相同方向的开放 PR，更新已有 PR，不重复创建。合并前确认最新 PR 提交的必需检查通过，不能引用旧 SHA 的结果。
- 合并前读取远端最新状态。如果 `main` 已有新改动，先同步到 `dev`，解决冲突并完成相应验证，再合并 PR。PR 优先使用普通 merge commit，保留长期分支的共同历史。
- PR 合并后，将最新 `main` 合并回 `dev`，可 fast-forward 时优先使用，推送 `dev` 并将工作区留在 `dev`。正常 PR 合并和回同步已有持续授权，无需重复确认；仅推送 `dev` 或创建 PR 不算完整交付。
- 不删除长期 `dev`。如另行创建临时分支，只有本任务创建、已完成合并且内容已安全推送的分支才可清理；不删除用户或其他任务的分支。
- 保留用户修改和他人提交，不使用强制推送、reset 或丢弃内容解决分歧。无法安全合并或推送时保留现场并说明具体原因。
- 复用与最终代码对应的验证证据，不因不改变内容的同步重复本地业务测试；远端触发的检查仍按实际 SHA 核对。分支流程不能代替修复不稳定测试，也不能将尚未运行的检查视为通过。
- 本规则持续适用，除非用户明确改变要求。
