# Spec 工作规则

更新日期：2026-09-11。

来源：用户最新明确区分决策与实施：Spec 决策由主 Agent 完成并轻量自查，用户后续审查；开 Spec 的业务实施走多 Agent，不开 Spec 则主 Agent 自行完成。

## 适用范围

本规则适用于本项目当前及后续 Spec 的需求讨论、草案起草、产品与技术选型决策、决策留痕和相关文档同步。它是项目持久规则，任务切换或上下文恢复后仍应遵守。

## 工作方式

- Spec 的需求讨论、调研、技术选型、决策和文档起草由协调 Agent 直接完成，不创建子 Agent 或安排独立验收；完成后按 S0 轻量检查 diff、需求一致性和引用，再交用户审查。
- 开 Spec 的业务实施阶段由实施 Agent 开发，再交新的独立 Agent 验收；不让子 Agent 替用户作产品决策。
- 用户要求不开 Spec／直接修改时，由协调 Agent 自行完成分析、实施和验证，不创建子 Agent。该明确选择优先于通用多 Agent 分工。
- 关键决策未确认时不提前实施；由协调 Agent 推进不依赖答案的调研与文档工作。
- 用户已明确的决定直接记录并采用。提问遵循 [集中提出问题约定](../../AGENTS.md#项目补充约定集中提出问题)：只用普通文本，每轮集中多个问题，一个 Spec 可有多轮，不使用问题卡。
- 决策记录到 `.ai/decisions/`，同步当前 Spec、Plan 和适用的 `constitution/` 文档。

## 与工程实施的关系

开 Spec 的实施与验收 Agent 必须独立；不开 Spec 时由协调 Agent 自查并如实报告验证结果，不伪造独立验收。两种模式均遵循 S0～S3 验证与停止规则。

## 文档精简

用户于 2026-09-10 明确要求：不仅整理现有文档，还要持续避免再次产生冗余。本约定适用于后续所有任务及上下文恢复，除非用户改变要求；无需再次提醒或确认。

- **写之前先找归属**：按 [Spec 文档分工](../../specs/README.md) 更新已有文件。只有独立职责确实需要时才新增 Markdown，不因一次尝试、一次 CI 失败或换一个 Agent 就新增永久报告。
- **一处详述，其他引用**：背景、技术栈、决策依据、参数和实测数据各有归属；Spec 不复述决策全文，Plan 不重抄需求，实施与验收不复制整套测试日志。更新只写本次变化。
- **报告保留增量**：同一 Spec 的实施与返工归入实施摘要；独立验收者维护验收结论，用简短历史记录保留 FAIL、修复依据和最终 PASS。详细原文须有可追溯的 Git 记录，不能为精简抹掉失败或未验证项。
- **原始材料与结论分开**：大段日志、截图和原始输出放对应 artifacts，正文只保留判断所需摘要和证据位置；实测较多时才使用 verification.md。
- **主动收尾**：交付前检查本次涉及文档的重复段落、过期状态和引用。删除不影响需求、约束、取舍、结论或证据追溯的文字；不为填满模板扩写，也不顺手扩大为全仓整理。

文档自查按 S0 处理，不触发业务测试重跑；是否采用多 Agent 按上述用户指令确定。
