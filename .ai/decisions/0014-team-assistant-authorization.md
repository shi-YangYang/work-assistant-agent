# 团队助手的授权与业务来源

管理员团队查询限定为已确认业务及关联材料，未关联原始上报不独立检索；本人督办须确认，权限由服务端执行。

## 背景

当前员工工具按本人取数，管理员通过团队页面另有人工查看权限。仅给模型增加团队工具或在前端隐藏入口，无法保证直接调用、来源链接及历史上下文保持相同边界。业务跟进还需要把引用落实到正式对象，不能只保存一段模型回答。

## 决策

- 沿用现有角色与公司／owner 数据隔离，不引入自定义权限平台。身份来自登录会话及当前数据库成员；团队工具、页面接口和对象投影共用业务服务授权，发布状态及来源关系属于权限条件。
- 模型工具按角色提供，执行仍复核；读取和写入分别授权。新增团队问答可读范围以 Spec 为准，不因管理员能看某页面就自动将所有私人上下文送入模型。
- 现有 harness 负责工具调用、预算和持久恢复。补充服务端生成的读取凭据、来源依赖及当前权限检查；模型只引用确实读到的资料，不能通过 ID／URL 自行授予访问权。
- 权限约束覆盖派生回答、摘要、缓存、建议与 checkpoint，依赖沿后续上下文传播。当前权限或来源删除使旧内容不再可用；普通修订保留有版本的历史，不冒充最新事实。
- 督办复用管理员本人工作与人工确认，关联员工只是业务来源。保留原有删除语义，不把同意督办解释为派单、通知员工或代其更改状态。

## 取舍与影响

复用 SQL 业务记录、已有报告与文件提取结果即可支持首版问题，不为此增加向量库、通用 SQL 工具或更换 runtime。代价是必须补上跨员工来源依赖和历史失效处理；不能只靠提示词约束权限。具体范围、数据迁移与检查分别由 Spec／Plan 维护，不在本文件复制。
