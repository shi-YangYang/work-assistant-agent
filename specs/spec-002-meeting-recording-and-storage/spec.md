# Spec 002 — 会议录音与本地保存

## 状态

`DONE` — 默认麦克风录音、保存、历史与回放已完成，新的独立工程验收 [PASS](acceptance.md)。首轮恢复重试缺陷已闭环；Windows 实机与首次 macOS 授权弹窗仍明确未实测。

Spec 决策由协调 Agent 直接处理，不创建子 Agent 验证。后续工程实施与独立验收遵循 AGENTS.md，并按改动风险控制验证范围。

## 背景

[Spec 001](../spec-001-product-and-technical-foundation/spec.md) 已交付 Electron 桌面骨架和 Python 控制核心。本阶段开始实现 [路线图](../../constitution/roadmap.md) 中 Meeting Agent MVP 的原始信息采集部分，为后续转写和纪要提供真实会议数据。

用户已明确正式应用应自带运行环境；本 Spec 沿用开发启动方式，安装包与内置运行时仍由后续分发 Spec 交付，不能将环境配置要求转嫁给正式用户。见 [决策 0005](../../.ai/decisions/0005-self-contained-desktop-distribution.md)。

## 目标

1. 点击开始会议后，持续录制系统默认麦克风的声音，展示真实录音状态、时长和输入音量反馈。
2. 结束会议后保存可播放的音频及会议元信息。
3. 重启应用后能够找到会议并播放录音。
4. 权限、设备、写入或进程出现问题时，如实反馈，保留已经落盘的可恢复内容。

核心验收流程：**开始会议 → 录下一段真实讨论 → 结束会议 → 重启应用 → 找到记录并播放。**

## 非目标

- ASR、Transcript、LLM 纪要、模型下载与模型设置。
- 系统音频或屏幕采集、混音、说话人识别；本次仅采集麦克风。
- 同时录制多场会议、暂停后续录、录音中切换设备、后台托盘常驻。
- 会议删除、导出、音频编辑、复杂检索、标签、账号与云同步。
- 周报、Memory、Agent 编排，以及大量尚未使用的 Provider 空实现。
- 签名安装包、内置 Python、自动更新和正式双平台分发。

## 实施前行为

- 中文会议工作区与设置可用；“开始会议”禁用，会议列表始终为空。
- Electron 主进程管理 Python，通过带请求 ID 的 JSON Lines / stdio 通信。
- 只有健康、空会议列表和退出请求；没有音频依赖、业务数据库或播放入口。
- 窗口关闭会直接退出并清理 Python；当前拒绝设备权限请求。

## 目标行为

用户打开应用可查看历史会议。没有正在录制的会议时，“开始会议”在核心及存储基础可用后可点击；尚未取得麦克风授权不应让按钮永久禁用，点击后才进入授权与设备检查。

成功打开输入设备后，界面才显示“录音中”。用户可以最小化窗口或切换到设置，录音持续；系统休眠、设备失效和应用异常退出不能伪装成连续有效录音。

点击结束后先显示“正在保存”，待录音停止、数据写入和元信息保存完成，再进入会议详情。重启后从真实存储加载记录，可播放已保存内容。

## 功能需求

### R1 — 开始会议与权限

- 首版使用开始时的系统默认输入设备，显示实际设备名称；无可用设备时明确提示。录音中系统默认设备发生改变时，不自动切换到其他来源。
- 本次不在应用启动时自动采集声音。用户点击开始会议后才请求必要的麦克风权限并打开输入流。
- 默认标题为本地时间生成的“会议 YYYY-MM-DD HH:mm”；内部记录唯一 ID 和带时区时间。标题编辑留待后续。
- 一次只允许一场活动会议；启动中、录音中及收尾中均不能再创建另一场。桌面多实例不得绕过此限制。
- 权限拒绝、设备无法打开或存储准备失败，不得显示已经录音或保存成功；如果已有中间记录，应明确失败状态。
- 开始前停止已有音频回放，录音期间不提供历史录音播放，避免将回放声音再次录入。

### R2 — 持续录音与状态

- 使用真实麦克风输入持续写入本地文件，不将整场音频保存在内存中等待结束。
- 界面显示录音标识、时长、输入音量和结束按钮。静音时音量可以为零，不能通过随机动画伪造输入。
- 时长来自单调时钟或采样进度，最终保存时长以有效音频帧数为准；用户修改系统时间不能产生负时长。
- 采集回调、磁盘写入和界面更新分离，使用有界缓冲。队列或驱动报告音频丢失时显式标记中断，不能静默丢块后宣称录音完整。
- 控制消息仍使用 stdio，音频二进制不通过 JSON 或 IPC 高频转发。
- 采集块包含顺序与样本偏移，块大小可配置；驱动回调块与未来 ASR 业务分块保持可区分，不在录音路径上执行推理。
- 状态查询保持有界，不因频繁轮询积累并发请求；页面切换不会中止录音。

### R3 — 结束与保存

- 结束顺序为停止采集 → 排空已接受的音频缓冲 → 关闭音频文件 → 提交最终元信息。
- 重复点击结束或重试已完成的结束请求，不得生成多份会议或重复结束错误。
- 请求超时表示结果尚不确定，客户端应查询权威状态恢复；不得以超时为依据重新启动录音或直接宣告成功。
- 收尾期间显示明确状态。磁盘空间不足、目录不可写、文件关闭失败或数据库写入失败时，不显示“已保存完整录音”。
- 保留已经写入的文件与失败原因，不通过删除原始文件来清除错误；支持查看可恢复的部分录音，明确标记录制中断。

### R4 — 会议记录与回放

- SQLite 保存元信息，WAV 文件保存音频，均放在应用用户数据目录。不能把生产会议数据写进仓库、临时构建目录或模型目录。
- 历史列表按开始或创建时间倒序，展示标题、时间、实际时长及状态；空列表只用于真实无记录的情况。
- 点击记录进入详情，展示已保存信息，并提供播放、暂停和进度定位。
- 播放入口只接受合法会议 ID，由可信边界解析对应音频；不向界面开放任意本地文件读取能力。
- 文件缺失、无法读取或损坏时显示错误，不能将会议误呈现为没有录音内容的成功记录。
- 在同一用户数据目录重新启动应用后，历史记录和音频关联仍存在。应用版本或工作目录变化不应改变数据根目录。

### R5 — 关闭与异常中断

- 最小化不停止录音。录音中关闭窗口或退出时，提供“继续录音”和“停止并保存后退出”；取消退出保持原会话。
- 选择保存退出后完成 R3 的收尾，再退出主进程和 Python。保存失败时保持界面可见并显示原因，不能静默关闭。
- 强制结束进程或系统关闭可能绕过确认，应用下次启动将遗留活动记录标为中断，并检查已落盘内容；不能继续显示“录音中”。
- 核心异常退出、设备失效、系统休眠造成的采集中断应反映为中断状态，不能自动创建新录音或掩盖缺失时段。
- 核心重连不得直接终止活动录音。正在录制时的恢复操作应遵循相同的停止与保存边界。
- 异常恢复保留可恢复的完整音频帧；不承诺强制关机时尚在内存或系统缓存中的数据零丢失。

## 数据与状态约定

| 对象 | 本次最小字段 |
| --- | --- |
| Meeting | id、title、createdAt、startedAt、endedAt、status、durationMs、可空 errorCode |
| Audio | meetingId、相对存储路径、format、sampleRate、channels、sampleWidth、有效帧数 / 字节数 |
| RecordingStatus | 当前 meetingId、state、elapsedMs、实际 deviceName、归一化 inputLevel、可空错误 |

持久状态：starting、recording、stopping、completed、interrupted、failed。正常收尾且文件与元信息一致才是 completed；保留部分音频但未完整结束为 interrupted；没有可用音频的启动或保存失败为 failed。播放可用性由文件实际情况决定，不只由状态名称决定。

界面文案使用“正在准备”“录音中”“正在保存”“已完成”“录制中断”“录制失败”。核心 ready 表示内部进程可达，recording.available 表示录音功能已经接入且基础依赖可用，两者均不保证本次设备打开一定成功。

## 边界条件

- 无麦克风、权限拒绝、默认设备不可用、设备断开、静音输入。
- 快速重复操作、请求已执行但回复丢失、结束与窗口关闭同时发生。
- 中文或含空格的数据路径、数据库锁冲突、磁盘不足及文件缺失。
- 音频写入与数据库提交不是同一个事务，需通过中间状态和启动恢复保持可解释的一致性。
- 达到缓冲或文件格式容量限制时，应安全停止并说明原因，不承诺无限录音时长。
- 系统休眠与强制退出后不能声称没有音频缺口。

## 技术约束

- 沿用 Electron / React / TypeScript、Python 3.12、stdio 及既有 src/、tests/、docs/ 结构。
- 采用 sounddevice 的原始输入流、Python wave 与 sqlite3，见 [决策 0006](../../.ai/decisions/0006-recording-and-storage-baseline.md)。锁定依赖及 macOS 实录结果已记录，Windows 设备兼容性尚未验证。
- 保持 renderer 沙箱、上下文隔离、严格 IPC 来源和参数校验；只增加录音所需的权限与本地媒体访问边界，摄像头等无关权限继续拒绝。
- 不引入外部业务 HTTP 服务、付费 API、ASR 或 LLM 依赖。
- 不将真实音频、数据库和用户信息提交 Git；自动化测试使用隔离临时目录与明确的测试音频。

## 兼容性要求

macOS 与 Windows 均为目标平台，默认设备、录音权限、应用退出和数据路径的差异应在适配层处理。两平台的真实设备录音结果分别记录，不能用 CI 的合成音频测试替代麦克风实测。

本轮可先在当前 macOS 实机验收核心录音闭环。若 Windows 没有可用实机，保持未实测状态，不阻塞本阶段开发交付，也不能宣称已完成 Windows 录音验收。正式分发仍受决策 0005 约束。

## 待确认问题

当前没有阻塞这份范围的产品问题。默认输入来源为系统默认麦克风，一次一场会议，不做暂停续录或设备切换；这些默认行为已在本文明确。

实施阶段已确认锁定音频依赖的安装及当前 macOS Electron → Python 原生输入流实录路径，没有改变录音归属或引入额外系统驱动。首次系统授权弹窗与 Windows 实录仍明确标为未实测。

模型、系统音频、正式安装包、最低系统版本和 Windows 实机安排不在本次默认实现中提前承诺。
