# Spec 066：通知页面与公告管理

## 状态

已完成。主体功能已独立验收；列表标记已读和删除操作另做定向回归。独立“通知”页面使用顶部“提醒／公告”Tab，管理员另有“公告管理”入口。公告面向本公司全部用户；首期采用标题和 Markdown 正文，不含图片／附件。

## 背景

管理员需要在 Noria 内自主发布公告，让用户能够看到通知并回查。现有“汇报通知”依赖个人日报／周报待办。提醒与公告统一在“通知”页面分类阅读；管理员通过独立“公告管理”页面维护公告，给长文阅读和编辑提供完整的页面空间。

## 目标

- 管理员可自行撰写、预览、发布、修改及删除公告，无审批流程。
- 用户通过同一个“通知”入口查看系统提醒和管理员公告，能回查历史公告；管理员另有职责清晰的“公告管理”入口。
- 复用现有页面布局、Markdown 编辑器和身份体系，不增加 Agent 的提示词或处理步骤。

## 非目标

- 首期不做定时发布、审批、评论、点赞、置顶、强制确认或阅读统计报表。
- 不做钉钉、邮件、短信或系统推送，不将公告自动插入聊天消息。
- 不提供 Agent 发布工具，不将公告自动注入模型上下文。
- 不改变现有汇报提醒的产生条件、内容、跳转及已读规则；只整合展示入口，不新增消息队列、实时推送服务或第三方编辑器。

## 当前行为

- 左侧主菜单和系统设置是两套导航，页面入口由 `navigation-items.ts` 统一定义。
- 员工侧栏底部有“汇报通知”，使用 `/notifications` 和个人待办记录；管理员不显示该通知入口。
- 已有 Markdown 编辑／预览、分页、身份与请求入口，可供公告功能复用。
- 尚无公告存储、发布接口、公告列表和个人阅读记录。

## 目标行为

通知页负责个人阅读，公告管理页负责公司公告维护。

| 使用者与入口 | 页面内容 | 可执行操作 |
| --- | --- | --- |
| 普通用户及管理员：通知 | 顶部“提醒／公告”Tab，下方显示对应列表或内容 | 提醒沿用现有业务操作；查看已发布公告及详情 |
| 管理员：公告管理 | 管理列表、发布入口、详情及编辑 | 预览、发布、编辑、删除本公司公告 |

“提醒”表示系统自动产生的业务提醒，首期承接现有汇报通知；“公告”表示管理员手动发布的内容。统一入口和未读总数，数据及业务规则仍按类别维护。管理员当前没有个人汇报提醒，因此“提醒”展示空状态，不把员工提醒提升为管理员可读。

公告面向本公司全部用户，包括管理员；新成员可阅读仍在发布中的历史公告。不同公司之间完全隔离。

## 功能需求

### 1. 内容与发布

- 首期采用标题和 Markdown 正文，支持段落、标题、列表、强调和链接；暂不提供图片、文件上传或嵌入图片。
- 发布前可预览。标题和正文不能为空，前后端统一限制长度：标题 100 字符、正文 20,000 字符。
- 点击“发布”成功后立即出现在公司公告列表；失败保留输入，明确提示可重试，不能先显示发布成功。
- 防止连续点击和网络重试产生重复公告；同一次发布重试沿用同一个幂等键。
- 编辑区沿用会话内草稿机制；离开未提交表单时避免静默丢失输入。首期不新增服务端草稿箱或跨设备草稿同步。

### 2. 通知页面与分类

- 原侧栏底部“汇报通知”替换为“通知”，普通用户和管理员均可访问；主菜单和设置菜单共用此入口，不额外增加公告阅读菜单。
- 点击进入独立“通知”页面。电脑和手机均使用“通知标题 → 提醒／公告 Tab → 内容”的布局，沿用问题反馈页的分段 Tab 样式。
- 通知页只负责个人阅读、标记已读及业务跳转；管理员在此也不出现发布、编辑或删除操作，维护统一在“公告管理”进行。
- 入口显示两类未读数之和，两个 Tab 分别显示自己的未读数量；超过 99 显示 `99+`，没有未读时隐藏。进入页面或切换分类不会批量标记已读。
- Tab 和分页写入 URL，刷新、深链接及浏览器前进／后退可以恢复；同一身份本次会话内再次进入保留上次 Tab。没有指定 Tab 且无历史选择时，优先有未读提醒的“提醒”，其次有未读公告的“公告”；均无未读时员工默认“提醒”、管理员默认“公告”。
- 公告列表打开独立详情，提供“返回通知”，返回时恢复公告 Tab、页码及列表位置；直接进入详情时返回通知的公告 Tab。
- 提醒沿用现有查看报告、准备草稿和标记已读的行为；进入通知页及点击提醒目标均遵守现有录音离页拦截。
- 通知由用户主动进入，不自动弹窗或跳转，不打断当前工作。

### 3. 公告阅读与未读

- 列表显示标题、正文摘要、发布时间和未读标识；最新发布在前，默认每页 20 条，沿用现有分页样式。
- 详情显示完整标题、正文、发布人、发布时间；修改后增加“已更新”的时间信息。
- 详情成功呈现后自动标记该版本已读；通知列表中的未读公告也提供“标为已读”按钮，无需打开详情。服务端确认后更新列表及未读数量，失败时保留未读状态。加载列表、预取详情不标已读。已读记录按用户存储，刷新和换设备保持一致。
- 已发布公告修改后作为新版本重新提醒；读旧版本不能误标新版本已读。没有实质内容变化的保存不重复提醒。
- 公告未读数只统计当前可见的已发布公告；删除后从该分类和通知总未读数中移除，不影响提醒计数。

### 4. 管理员维护

- 管理员主菜单增加“公告管理”，位于“成员管理”之后、“云搭子”之前；普通用户不显示该入口。管理员仍保留个人“通知”入口。
- 公告管理页顶部显示标题和“发布公告”，下方为管理列表及分页；只显示可用公告，不提供已撤回／已删除筛选或回收站。
- 新建、详情及编辑使用页面内的独立路由，不将长表单放入模态框。提供明确的“返回公告管理”，返回保留页码及列表位置。
- 管理员可管理本公司公告，不受“只能编辑自己发布的记录”限制；普通用户没有发布或维护入口。
- 编辑成功后更新原公告，不生成重复列表记录；保留首次发布时间、最新修改时间、当前版本及操作者信息。
- 管理列表每条公告直接展示“删除”按钮，详情保留同一操作。使用公共 React 确认弹窗显示公告标题及不可恢复提示，不调用浏览器原生 confirm；提交中防止重复操作，失败保留弹窗和错误供重试。成功后列表原位更新，详情则返回管理列表；通知与管理列表均移除该公告，清理其个人已读记录并刷新未读数。旧详情再次读取时提示“公告已删除或不可用”。
- 删除在服务端校验公司、管理员身份与预期版本；相同幂等键重试返回同一结果。版本冲突或删除失败不隐藏公告。
- 管理预览及编辑读取不会自动标记个人通知已读；个人已读只在通知阅读流程中更新。
- 多管理员同时修改时检测版本冲突，提示重新读取，不能静默覆盖他人内容。

### 5. 布局与状态

- 两个页面均复用 `PageHeader`、现有列表、分页及编辑器，右侧内容区铺满；桌面横向留白 32px、手机 16px，不另套居中窄列或多层卡片。
- 通知页两个 Tab 沿用问题反馈页的分段控件样式；管理页操作与标题同行，窄屏自然换行。两页都避让顶部宠物，不额外增加空白顶栏。
- 整个右侧页面区域滚动，长正文及编辑内容可访问；详情／编辑返回入口就近放置，不依赖模态框关闭按钮。
- 手机沿用相同页面结构，适配安全区、软键盘及至少 44px 的触控目标。
- 切换 Tab 保留已有列表和各自页码；管理页草稿在本次身份会话内离页后可恢复，账号切换时清空。
- 手机点击通知或公告管理后收起导航抽屉；键盘、浏览器返回和菜单高亮沿用现有路由规则。无权限用户直接输入管理地址也不能访问数据。
- 两类内容独立显示加载、空、失败和无权限状态；某类加载失败不妨碍另一类使用，不将错误伪装为“没有通知”。
- 刷新期间保留已有内容，避免闪烁和高度跳动；发布／编辑错误就近显示，保留输入。
- 适配浅／深色、桌面／手机、键盘和钉钉 WebView；不依赖仅悬浮可见的操作。

## 边界条件

- 公司范围及管理员身份由服务端从登录身份获取，不能信任客户端提供的公司或作者 ID。
- 他公司 ID、普通用户伪造管理请求、未登录请求都不能绕过权限；列表、详情、未读摘要、标记已读必须使用一致范围。
- Markdown 沿用安全渲染，禁止原始 HTML、脚本和危险链接；图片语法不能绕过首期不支持嵌入图片的约束。
- 读取详情与删除／更新并发时重新校验有效状态及版本；重复标记已读应幂等。
- 发布人账号删除后不删除公司公告，保留发布人显示名快照；删除读者账号时清理其个人阅读记录。
- 注销或切换账号后清除前一身份的公告缓存和未读数，迟到响应不能串到新账号。
- 后台标签页不轮询；回到前台重新同步。不在通知页时只请求轻量分类摘要，不反复拉取列表和正文，不延长登录会话。
- 删除无法抹除用户已经看到或自行复制的内容；页面在下次请求时以服务端状态为准。

## 技术约束

- 前端 `features/notifications/` 承载通知入口、个人阅读页及摘要订阅，`features/announcements/` 承载共享公告内容与管理员页面，汇报提醒保留在 `features/reports/`；后端公告在 `modules/announcements/` 内组织，HTTP 层仅聚合两类摘要。
- 公告和阅读状态使用 PostgreSQL 持久化，写入复用事务、版本校验、幂等及 CSRF 机制。
- 每条公告只存一份正文，阅读时才建立个人已读记录；不在发布时按全体成员复制公告或批量创建通知。
- 分类摘要在前台按现有提醒的 30 秒节奏刷新，进入通知页、窗口重新获得焦点及发布／已读／删除成功后主动刷新；每个身份只维护一份摘要订阅，侧栏与通知页共用，不能各自轮询。
- 不修改现有 Agent、worker、模型调用、任务预算和工具集；不为公告请求调用模型。

## 兼容性要求

- 现有汇报通知记录及 API 保持兼容，不迁移或重置员工已读状态；前端入口统一后，主／二级菜单切换、聊天草稿、录音离页拦截及宠物状态继续正常使用。
- 使用增量迁移新增表和索引，不修改既有业务数据；沿用现有迁移部署方式，不增加容器。
- 老版本应用可忽略新增表；不通过回滚删除已发布公告。

## 验收标准

- [x] 管理员可预览、发布、修改及删除，重复点击／网络重试不会重复发布。
- [x] 管理员和员工均可进入通知页面，电脑和手机均使用顶部提醒／公告 Tab；通知页不出现管理操作。
- [x] 管理员有独立“公告管理”入口及页面；普通用户看不到入口，也无法通过深链接或伪造请求访问管理能力。
- [x] 总未读与分类未读一致；进入通知页、切换分类及管理预览不误标已读，管理员不能读取员工个人提醒。
- [x] 员工及管理员看到正确的本公司公告，跨公司和普通用户越权操作均被拒绝。
- [x] 公告分页、详情、返回及空／加载／失败状态正确，手机操作可达。
- [x] 打开详情或主动点击“标为已读”后标记对应版本，刷新／换设备保持；修改后重新未读，旧版本读取不能覆盖新版本。
- [x] 删除后通知与管理列表均移除公告、未读数同步减少、旧详情不可用，已读记录级联清理；重复删除请求幂等。
- [x] 并发编辑不会覆盖，失败保留输入，账号切换不会显示前一用户缓存。
- [x] 恶意 Markdown、危险链接和超长内容得到正确处理。
- [x] 空库及已有数据的迁移通过，成员删除不会误删公司公告。
- [x] 汇报通知和现有导航回归通过；公告查询不调用模型、不续期会话、不新增任务处理步骤。
- [x] Tab／分页 URL、深链接、浏览器历史、两类详情返回、草稿恢复、手机抽屉收起及整页滚动正常，无重复摘要轮询。
