## 背景

Personal Agent Assistant 面向 macOS 和 Windows，长期连接会议、周报及历史工作信息，形成对人员、项目、任务、决策和风险的持续理解。近期首要产品目标是 Meeting Agent MVP。

仓库已完成目录和开发管理文档初始化。本 Spec 在既有结构上确立产品与工程基础，将后续功能开发所需的关键约束落实到文档和最小可运行工程。

## 目标

1. **产品确立**：明确目标用户、核心使用流程、首版产品形态、MVP 范围及后续扩展边界。
2. **技术选型**：比较可行方案及取舍，确定支撑首版的技术栈、模块职责、数据流和工程约定。
3. **初始骨架搭建**：在方案确认后，从现有目录骨架推进到可安装、可启动、可验证的最小工程，为后续 Meeting Agent 功能提供落点。

## 非目标

- 本 Spec 不交付完整的真实录音、音频队列、ASR 转写或 LLM 会议总结功能。
- 不实现周报处理、复杂 Memory、RAG、知识图谱、说话人识别、主动 Agent 或产品中的多 Agent 工作流。
- 不预设采用 LangGraph 或其他 Agent 编排框架。
- 工程工具按实施基线落地；ASR 模型与 LLM 服务商在后续真实功能接入前明确，本次不安装模型依赖。
- 本次交付开发启动及构建预览，不包括商店发布、签名安装包、自动升级、云部署或双平台同步发布。
- 不重新建立或迁移现有 Agent 目录及业务代码根目录。

## 当前行为（实施前基线）

- 已有 `AGENTS.md`、`constitution/`、`specs/`、`.ai/`、`docs/`、`src/`、`tests/`。
- `src/` 和 `tests/` 仅有占位文件；没有应用入口、依赖清单、测试或构建配置。
- 已明确 macOS 和 Windows 为目标平台；macOS 是当前开发环境。
- 首版采用 Electron 桌面应用，保留 Python 开发方向；具体版本、包管理器、界面框架、数据库、ASR 和 LLM 方案仍待明确。
- 目前没有可运行产品，也没有经过平台运行验证的能力。

## 目标行为

完成本 Spec 后，应具备：

1. 一份明确的首版产品定义，能说明谁使用、如何使用、首版包含什么以及暂不包含什么。
2. 一套有依据的技术方案和模块设计，能说明组件的职责、输入、输出、依赖及关键取舍。
3. 一个按文档可启动的最小 Electron 桌面应用入口，呈现产品名称、骨架状态和已确定的基本界面结构。
4. 明确的后续 Meeting Agent 接入位置，以及与真实能力一致的界面提示。
5. 依据实际工程配置可执行的验证命令和结果记录。

最小应用应能在未配置 LLM 密钥、未下载 ASR 模型、未授权麦克风时启动。若使用样例会议或转写内容，必须明确标注为演示数据；未实现的操作不能显示成功结果。

## 功能需求

### P1 — 产品定位与范围

- 沿用 Personal Agent 的长期目标及 Meeting Agent 的近期优先级。
- 以现有项目背景为基础整理用户场景与价值，不重复询问已经明确的信息。
- 明确当前 Spec、Meeting Agent MVP 与后续周报 / Memory 阶段的边界。
- 将结果记录在 `docs/product-definition.md`，长期稳定结论同步至 `constitution/mission.md` 和 `constitution/roadmap.md`。

### P2 — 产品形态与用户流程

- 采用用户已确定的 Electron 桌面形态，细化启动体验、窗口行为、持续录音状态展示及跨平台需求，不重复询问产品形态。
- 明确开始会议、查看转写、结束会议、等待处理、阅读纪要及查看历史记录的目标用户流程。
- 明确设置和异常状态的产品要求，包括设备或权限不可用、模型 / LLM 未配置、转写或总结失败时用户应看到的信息。
- 区分上述目标流程与本次工程骨架实际实现的界面和行为；不将完整流程图视为功能已实现。
- 以文字或简单流程图表达即可，本 Spec 不默认要求完整视觉设计稿。

### T1 — 技术评估与结论

至少评估以下事项，并区分本次必须落地的选择与后续功能接入时才需要落实的选择：

| 范围 | 需要明确的内容 |
| --- | --- |
| 运行环境与工程工具 | Electron 与 Python 的运行时版本、包管理器、依赖与锁文件方式、源码组织 |
| 产品入口 | Electron 已确定；继续明确界面框架、窗口与应用生命周期、是否需要本地服务及其职责 |
| 音频与并发 | 采集方式、录音与 ASR 的隔离边界、分块可配置方式、积压与收尾策略的设计方向 |
| 本地 ASR | 候选实现、模型与运行后端的评估方式、双平台及硬件约束 |
| LLM | Provider 边界、结构化输出方案、配置与外部调用边界 |
| 持久化 | MVP 存储方案、音频 / Transcript / 纪要保留原则、未来 Memory 的接入边界 |
| 质量与交付 | 测试、Lint、格式化、必要的类型检查、启动、构建与平台验证方式 |

选型说明应包含适用理由、重要替代方案、维护成本、平台限制和验证依据。尚未验证的性能及兼容性假设必须标明；不得仅凭候选库名称认定可用。

对有版本或平台时效性的技术结论，查阅官方文档并记录来源及查阅日期。必要的技术验证应限定目标与规模；大模型下载、付费服务接入或重大外部依赖先明确范围。

### T2 — 架构与模块边界

- 在 `docs/architecture.md` 中说明模块职责、输入、输出、依赖与核心数据流。
- 明确 Electron 与 Python 的职责边界、进程管理和通信方式；本次采用主进程管理 Python 子进程及 JSON Lines / stdio 控制协议。
- 设计保持录音、ASR、Transcript 管理及 LLM 分析解耦。
- 设计覆盖会议结束后停止采集、处理剩余音频、整理完整转写，再执行会后总结的顺序。
- ASR、LLM 和持久化 / Memory 接入采用明确边界；不为尚未实现的长期能力生成大量空类或空模块。
- 识别录音权限、设备选择、文件路径、模型后端及打包等平台差异的归属，不使核心业务依赖单一操作系统。
- 明确 Meeting、Transcript Segment、Summary 的最小数据契约设计，以及未来字段扩展方式；具体业务实现留待后续 Spec。

### T3 — 决策同步

- 已确认的重大产品及技术决策记录到 `.ai/decisions/`，说明理由、替代方案与影响。
- 已确认且实际落地的工程约定写入 `constitution/tech-stack.md`；评估中、已选定待落地、已落地的状态应清晰可区分。
- 在相关决策确认前，候选方案不得被文档或实施计划写成已选定技术栈。

### S1 — 最小可运行工程

- 沿用 `src/`、`tests/`、`docs/` 及固定 Agent 结构，根据已选技术方案补充内部组织和必要配置。
- 建立可复现的依赖安装方式、应用入口、配置示例和基础日志行为。
- 提供最小 Electron 桌面窗口与界面，清晰显示项目处于功能接入前的骨架阶段。
- 模型或服务凭证缺失不能导致整个应用入口无法启动；相关模块应显示未配置或未实现状态。
- 如选择本地服务，明确其生命周期与访问范围；不得把单机应用默认开放给局域网或公网。

### S2 — 真实能力与演示隔离

- 本次启动和验证不依赖真实会议录音、模型推理或外部 LLM 请求。
- 如使用替身 Provider 或样例数据，只用于必要的边界与启动验证，须能与未来真实实现清晰区分。
- 产品中未实现的开始录音、转写或总结操作应有明确状态，不制造成功记录。
- 不写入真实密钥或敏感会议内容，示例配置仅含占位信息。

### S3 — 可验证与可交接

- README 提供与实际配置一致的安装、启动和验证步骤。
- 建立与骨架范围相称的检查，验证入口启动、配置缺失时的预期行为及实际创建的关键模块边界。
- 根据最终技术栈决定测试、Lint、格式化、类型检查及构建命令，不提前假设命令可用。
- 实施报告与独立验收报告区分已执行、失败和未执行的平台检查，记录原因与剩余风险。

## 边界条件

- 仓库已有结构是后续扩展基础；占位文件可以在目录获得实际内容时移除，目录位置和职责保持不变。
- 硬件、系统版本和验证设备尚未确定，不能默认采用某个平台专属的加速能力。
- 音频积压、ASR 失败、会后总结失败及超长会议的处理原则应在设计中明确；本次不以真实业务运行验证这些流程。
- 界面展示演示数据或骨架状态时，不能让用户误以为正在采集麦克风或调用 LLM。
- 如产品形态、持久化方案或关键数据契约存在重大歧义，应先解决再实施相关模块。

## 技术约束

- 遵守根目录 `AGENTS.md` 及 `constitution/` 已确认约束。
- 当前为文档与目录基础上的增量建设，不重新初始化 Git 或覆盖已有文件。
- Electron 桌面框架已由用户确定；本次采用 React / TypeScript 界面与 Python 3.12 核心，工程工具链见实施基线。
- 避免业务代码绑定具体 ASR、LLM 或存储实现。
- 实时音频处理与 Agent 推理解耦，不强制引入 LangGraph。
- 骨架默认不依赖付费 API、已下载模型或已授予麦克风权限。

## 兼容性要求

- macOS 和 Windows 均为目标平台，核心方案需考虑两者。
- 本 Spec 在当前 macOS ARM64 实机验证，并检查 Windows CI 配置和路径逻辑；最低系统版本及其他硬件的支持范围在后续分发前确认。
- 未在 Windows 运行验证时，必须标为未验证，不能声称已经通过 Windows 验收。
- 保留现有开发管理结构、MIT 许可证和已确认的产品范围。
