## 已通过的修复

- **来源发现事实不再被裁剪抹除。** [`web.py`](../../apps/server/app/agent/tools/resources/web.py#L51) 在既有租约事务中合并本任务来源，不再按 JSONB 字典顺序保留最后 40 项。相同 company/member/job 锁仍串行保护并发写入；没有新增事务、表或模型步骤。旧来源记录兼容，已经被旧版本淘汰的数据不能凭空恢复。
- **来源等级与公开展示保持正确。** 搜索摘要最多 400 字符，仍为 `search_snippet`；成功正文读取升级为 `page_text` 并清除旧摘要，后续较低等级来源不能覆盖正文证据。未知地址的失败没有变成来源，真实来源读取失败也不再撤销已发现事实。公开来源卡继续只接收真实正文阅读回执，未暴露私有摘要或进度字段。
- **恢复回执稳定。** [`tool_progress/service.py`](../../apps/server/app/agent/runtime/tool_progress/service.py#L64) 将首次 `newEvidenceCount`、`progressNotice` 保存在原调用进度行，按固定键序重放；不重新计数、不重复累计停滞。旧调用没有派生字段时保留原回执，不用后续发现反推历史。
- **范围受控。** 研究规则与两项工具说明按去缩进源码文本统计 4,022 → 1,700 字符；实际 HTTP 工具描述还包含格式空白，不能把该数字当作完整模型输入长度。搜索服务仍为 Bing RSS，没有更改调度、预算、权限或访问安全约束，也没有额外核对模型。

来源账本不等于全量模型上下文：失败回执只带回相应 URL 的已有证据。其代价是在原 Job JSON 中保留更多有界来源并随原事务序列化；每次搜索最多 5 项，每次网页返回最多 8 个链接和 1 个正文，既有 64 次工具预算约束单次任务规模。不能声称这完全没有存储成本，但没有新增网络往返；图输入、配置或数据作用域改变时，原有初始化流程仍清除旧 `webSources`。

## 未达标项与结论边界

**来源足够后仍继续探索。** low 在最终两页齐备后又有 19 次模型请求、25 次搜索、14 次读取，继续等待约 140.66 秒；high 又有 14 次模型请求、19 次搜索、10 次读取，继续等待约 176.51 秒。原题只要求各一个链接，最终仍复述 HTTP 403、未读正文等用户未要求的过程说明。

low 总耗时减少 14.77 秒，但模型和工具调用数增加，累计模型请求时间下降约 30.05 秒、工具墙钟反而增加约 13.71 秒，不能据此声称流程效率提高。high 总耗时增加 8.11 秒，累计模型请求时间减少约 2.20 秒、工具墙钟增加约 10.48 秒，不能全部归因为模型思考变慢。普通问答 high 没加载研究策略或工具仍多约 3 秒，说明单次上游调用存在波动，但它不能替搜索中的额外工具调用作解释。

每版本每题只有一个首轮样本，先后运行而非随机交叉，无法量化提示词、采样与上游结果各自对耗时的因果贡献。`newEvidenceCount` 只是 URL／标题／摘要增量，无关结果首次出现也会计数；它不代表用户需要的证据已经充分。当前证据不支持继续增加提示词、硬性缩减工具额度或更换搜索服务来宣称问题已解决，也不支持将残留直接认定为纯模型问题。

两项确定性缺陷可关闭；搜索收尾选择与过程说明冗余仍须作为未解决问题保留。验收只新增本报告，没有修改业务代码、追加测试或模型调用、提交或推送。
