# Spec 008 — 员工工作助手与汇报看板

## 状态

ACCEPTANCE · 2026-09-12。业务实施与两轮定向返工已完成，独立工程验收 [PASS](acceptance.md)；真实模型／ASR、手机实机和生产部署仍按报告保留外部验证边界。用户已审查并认可技术方案与[页面交互原型](prototype.html)。首期 Web＋共享服务端、保留 Electron、采用业务 harness、沿用桌面设计原则；老板／管理员可查看原始上报，汇报安排由管理员设置，仅设两类角色。

沿用 Spec 编号与现有目录，目录后缀保留历史名称。方向和取舍见 [决策 0011](../../.ai/decisions/0011-company-agent-direction.md)，跨端设计依据见 [决策 0009](../../.ai/decisions/0009-interface-design-direction.md)，工程方案见 [Plan](plan.md)。

## 背景与当前行为

试点公司希望员工通过图片、文字、语音及零散消息汇报工作，由 Agent 整理进展，减少重复写日报／周报，并让老板及时了解情况。

本 Spec 实施前，产品为 Electron 本地会议助手，已有录音、转写、纪要、回放和资料管理，公司账号、共享业务服务、员工消息、汇报看板与业务 harness 由本 Spec 新增；不能用静态示例、现有桌面 IPC 或一次总结调用冒充。

## 目标与目标行为

员工发消息 → Agent 关联已有工作、整理进展 → 员工确认或纠正 → 形成日报／周报 → 老板查看并追溯已共享的工作依据。

- 员工能够在电脑和手机浏览器中完成同一流程。
- Agent 持续维护工作上下文，后续消息能更新同一事项；人工纠正不会被后来的模型结果覆盖。
- 以减少重复汇报、提高进展可读性和事实可追溯性衡量试点价值。

## 功能需求

### R1 — 公司、人员与可见范围

- 首版服务一个试点公司，仅设“老板／管理员”和“员工”两类角色，由管理员创建、停用账号，不设部门负责人或复杂组织层级。权限由服务端执行，页面隐藏不能替代鉴权。
- 员工维护自己的消息、工作记录和报告；老板／管理员可查看本公司员工已发送的工作消息、助手回复、图片、语音及转写，以及已确认进展和已提交报告。员工不能查看其他员工的记录。
- 团队看板及其统计仅包含员工角色，管理员不作为被汇报对象；管理员不能读取其他管理员的工作消息、附件、工作和报告。本人资料仍通过“我的”入口访问，成员管理中的账号维护与看板分开。此规则按用户 2026-09-12 体验反馈明确。
- 工作助手的发送入口清楚标明“发送后的工作消息及附件，老板／管理员可查看”，不能将其呈现为私人聊天。尚未发送的内容、独立编辑中的进展草稿与未提交报告仍仅本人可见；已发送消息中的 AI 建议标明待确认，不作为已确认进展统计。
- 消息、附件、来源跳转和 Agent 工具使用同一套可见规则。管理者的查看权限不包括代员工确认进展或提交报告，不扩展到用户现有 Electron 本地资料。
- 登录过期或账号停用后停止受保护访问，切换账号不显示上一账号的消息、附件或草稿。

### R2 — 工作助手与多种输入

- 员工默认进入“工作助手”，通过持续消息流提交文字、图片与短语音，查看处理状态、Agent 回复及待确认的进展。
- 图片可预览、移除后再发送；语音可录制、停止、试听、取消和发送。采集由用户主动触发；权限拒绝时保留文字输入入口。首期保证前台短语音采集，录制中离开需明确处理，不承诺浏览器锁屏持续录音。
- 上传前显示支持格式、大小和时长限制，服务端再次校验；本轮提案为单条最多 4 张图片或一段 3 分钟语音，可附文字，具体格式与限额见 Plan。图片必须进入具备图片理解能力的处理流程，不能只把文件名作为内容；语音先经外部 ASR 转为可核对的文字，再交给 Agent。
- 区分上传中、已发送、处理中和失败；以服务端保存成功作为“已发送”的依据。发送失败保留本次可重试内容，同一次发送重试不重复创建消息或进展。
- 转写或图片处理失败不丢弃已保存原始材料，员工可以修正文字或发起重试；离线时不显示已提交成功，不在恢复网络后偷偷发布报告。

### R3 — 业务 harness 与工作进展

- 消息保存后产生持久处理任务。Agent 根据当前员工身份，读取允许访问的历史消息、工作事项和确认记录，调用受控业务工具生成回复、澄清请求或进展草稿。
- 首版工具围绕查询本人工作、提出新增／更新进展、整理报告草稿展开；正式确认和发布使用明确的用户操作。模型不自行决定权限，也不能替其他员工确认责任或完成情况。
- 进展包含事项、完成内容／当前状态、问题或阻碍、下一步、更新时间与来源；无依据的负责人、期限和完成比例留空。归属不明时澄清；员工可选择已有事项或新建，不将相似文字直接认定为同一任务。
- 待确认进展支持编辑、确认、忽略；可一次处理本轮多个提取结果。确认后进入“我的工作”和授权范围内的看板，后续修正保留变更依据，不用模型输出覆盖已确认内容。
- 例如“初稿完成，等待报价”只能表示对应进展；后续“报价拿到了”可更新同一事项，不能直接将整个项目标记完成。
- 任务保存处理阶段和结果，重启后可恢复未完成任务，重试不重复应用业务变更；失败提供可理解的恢复入口。切页或关闭浏览器不取消服务端已经接收的处理任务。
- 员工输入、图片文字和模型返回都作为业务数据处理，不能扩大工具权限或绕过确认。限制单任务步骤、并发、超时和费用相关重试，不开放任意系统命令或无限工具循环。

### R4 — 日报与周报

- 日报默认按每天组织，周报按周组织。管理员在“汇报规则”中分别设置是否启用、日报适用日期／周报生成日、草稿生成时间、提交截止时间和公司时区；时区默认 Asia/Shanghai，具体几点不写死。
- 管理员完成时间配置并启用后，系统按规则自动准备草稿，也允许员工主动生成。草稿由员工审阅、修改后提交，生成完成不等于已发布；员工可查看适用于自己的规则，但不能修改公司的安排。
- 调整规则对后续调度生效，已存在的草稿和报告保留所属周期及输入快照，不自动回补历史生成任务。停用自动生成不删除既有内容，恢复时不重复生成同一周期报告。
- 从所选周期内的已确认工作记录整理完成事项、进行中工作、问题／阻碍和下一步，允许员工补充内容；显示周期、更新时间和可访问的来源。没有记录时显示真实空状态，不编造工作。
- 每位员工、报告类型与周期对应一个报告及修订记录，重复触发不重复发布；生成失败或晚到结果不覆盖人工编辑或上一份已提交版本。
- 提交前展示可见范围。提交后的更正形成新修订；老板能区分报告提交时间和工作记录更新时间，历史报告不被新进展悄悄重写。

### R5 — 老板看板

- 按员工、时间范围及有依据的状态查看已确认工作进展、阻碍和已提交报告；员工详情分为“工作进展”“原始上报”“报告”，可回看已发送消息、助手回复、图片、语音及转写。
- 显示最近更新时间、尚无上报及待补充信息。未上报不推断为未工作，不生成无依据的员工评分、效率排名或项目完成百分比。
- 看板支持手动刷新；建议可见页面在正常连接下于 30 秒内反映已确认更新，断线显示最后更新时间和重试入口，不能持续展示虚假的最新状态。
- 原始上报独立于已确认进展呈现，未经确认的信息不混入正式进展统计。来源链遵守 R1，老板／管理员可回到本公司原始上报核查，其他员工不能通过链接或 Agent 回复绕过权限；未提交报告草稿不出现在老板看板。

### R6 — 延续 Electron 的视觉与页面组织

继承 [Spec 006 的视觉与交互原则](../spec-006-interface-and-navigation/spec.md)，以现有 `src/renderer/styles.css`、导航及已修复的菜单行为作为实现参考；不复制桌面业务依赖。共同设计要求在决策 0009 维护，本节定义本轮 Web 验收行为。

- 中性灰阶、少量蓝色强调，统一背景、导航、内容面、弹层、正文、辅助信息、状态和焦点的语义色值。支持浅色、深色与跟随系统，默认跟随系统并记住选择。
- 正文与辅助信息层级清晰，辅助文字不小于 12 px；手机阅读和输入使用合适字号与触控区域。沿用普通文字 4.5:1、大字及必要控件状态 3:1 的对比度目标，状态不只靠颜色区分。
- 宽屏使用左侧导航、稳定页面标题与主要操作区；设置／账户位于侧栏下方。按任务拆页，折叠只收纳当前任务的高级内容，不将消息、报告、团队看板和设置堆进一个长页面。
- 员工入口为“工作助手”“我的工作”“我的报告”，日报／周报在报告页切换；老板／管理员额外拥有“团队看板”、员工详情与成员管理。设置按账户、外观及管理员可编辑的“汇报规则”拆分；员工在报告页可查看自己的汇报安排，不增加无功能占位页。
- 手机使用单列内容与可直接触达的导航，详情有清楚返回入口，账户／设置可从菜单进入。沿用配色、组件状态和术语，重新安排窄屏布局，不把桌面侧栏和双栏内容机械缩小。

### R7 — 连贯交互与浏览器适配

- 回复中的进展草稿可直接编辑、确认和查看来源；从报告／看板进入已授权的工作记录后，返回保留原筛选、滚动位置和阅读上下文。
- 导航与列表具有清楚的 hover、选中、键盘焦点和禁用反馈。“更多”使用稳定的独立操作区域，整行悬浮不让其变成抢眼主按钮；触屏和键盘操作不依赖鼠标悬浮才能发现入口。
- 菜单依附触发器，靠边时自动调整位置，长文字不被窄宽度截断。鼠标离开触发器与菜单整体区域后收起；菜单内有键盘焦点时保留，Esc、外部点击或切页关闭，焦点返回仍存在的触发器。
- 草稿在应用内切页时保留；刷新或离开前对尚未保存的内容明确提示。语音播放器按消息唯一实例化，离开页面不留下播放器、菜单或订阅，不能出现重复创建和残留浮层。
- 提供可点击的页面／操作查找入口，桌面浏览器支持 Cmd/Ctrl+K；只展示真实可用且获授权的页面和操作，不抢占文字输入及中文输入法组合输入。
- 浏览器刷新、前进、后退及授权页面直达可用；移动键盘弹出时输入框、发送操作和当前内容可达。建议覆盖 360 px 窄屏及现有桌面最小窗口的 900 × 640，长中文和混排内容无整页横向溢出。
- 状态反馈贴近操作；忙碌、空数据、离线及失败均有实际状态。界面使用业务语言，不出现 harness、worker、IPC 等实现解释或营销式大标题；必要的上传、可见范围和失败原因应清楚说明。
- 动效短且克制，尊重减少动态效果偏好。桌面与手机共用业务状态，权限和发布规则不因终端变化。

## 非目标

独立手机 App、Electron 接入共享业务或同步历史会议、本轮会议事项采纳与提醒、复杂组织层级、绩效画像、RAG／知识图谱、自动催办或代改日程、对接企业聊天平台，以及自托管 ASR／LLM。保留后续扩展边界，不提前增加空页面或复杂基础设施。

## 边界条件与兼容性

- 保留现有 Electron 启动、录音、模型、会议数据及服务配置；不自动上传本地资料或读取现有明文密钥。公司服务配置由部署方另行提供。
- 浏览器麦克风需要符合浏览器要求的安全访问环境；手机访问服务器不能照搬本机 localhost 的例外。选定 ASR 后按实际格式做适配，并说明取消、网络断开和不支持输入时的行为。
- 多端同时修改时校验版本，晚到保存不能静默覆盖更新；提交中的按钮防重复，服务端仍须保证幂等。
- 日期与报告周期使用公司时区；员工设备时区变化不改变已提交报告所属周期。停用账号不删除既有工作记录，查看权限按已确认规则执行。
- 故障与权限验证使用固定样本和测试账号；真实公司材料、API 密钥与既有会议不作为自动测试数据。

## 技术约束

共享业务由服务端 API 提供，Web 无需 Python、Node 或本地转写模型。本轮提案在同一仓库扩展 React Web、Python／FastAPI 服务和 PostgreSQL，入口独立，现有 Electron 保留；具体模块路径、依赖与命令见 Plan。图片输入需要实际能力适配，不能将当前文本纪要适配器视为已支持图片。

Harness 提案采用 Deep Agents／LangGraph 的上下文与恢复能力，只开放受控业务工具，按决策 0011 的官方依据配置。模型／ASR API 密钥保留在服务端，参考接入百炼图文模型与短语音 ASR；业务工具按请求身份鉴权。首期面向小服务器，采用有界后台任务，不增加复杂任务平台或重型默认 CI；具体接口、输入限制、超时、恢复和部署契约已写入 Plan，不能声称 2 核 2 GB 已验证可用。

## 验收标准

- [ ] 员工可在电脑和手机浏览器发送文字、图片、语音；原始内容、处理状态和失败恢复真实有效。
- [ ] 真实 Agent 流程能关联前后消息、提出进展、处理澄清并保存人工纠正；重启／重试不重复应用变更。
- [ ] 仅有老板／管理员和员工两类角色；管理员可查看本公司原始上报及附件，员工不能跨员工访问；未发送内容、独立编辑草稿和未提交报告遵守 R1，URL 与工具调用不能越权。
- [ ] 管理员可设置日报／周报的启停、日期、时间及公司时区，员工只能查看安排；调度遵循保存后的规则，变更不重复生成或改写历史周期。
- [ ] 日报／周报人工编辑、提交及修订可用；超时、重复触发、晚到结果不覆盖有效内容。
- [ ] 老板能按员工及周期查看已确认进展、原始上报和报告；待确认信息、数据更新及无上报状态符合 R5。
- [ ] 浅深主题、导航层级、菜单定位与宽度、hover／焦点、来源返回、草稿及唯一播放器符合 R6／R7。
- [ ] 目标窄屏与桌面尺寸、移动键盘、浏览器前进／后退／刷新和麦克风失败入口可用。
- [ ] Electron 原有能力与数据保持，云端调用和本地能力边界清楚；真实联调结果与固定样本自动验证分别记录。
