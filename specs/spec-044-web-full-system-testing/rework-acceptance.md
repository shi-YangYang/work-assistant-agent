## Issues

### S04：将清除取消状态错接为拒绝取消的必要条件

实际答复说，协程可以抑制异常，但“需配合 `uncancel()` 才谈得上‘撤销／拒绝’”。实际页文把 `uncancel()` 的要求限定于清除取消状态，不能据此断言不调用它就不能捕获异常并正常返回。

相关原文已在核对保留的 offset 39000 片段中，核对却返回 `issues=[]`。本地 Python 3.12.14 的只读语义探针也观察到：捕获取消异常后正常返回，不调用 `uncancel()`，仍可 `done=true`、`cancelled=false`、`cancelling=1`；这不是一次 Python 3.14 执行测试。完整证据：[source-fixed-S04-defect.json](../../artifacts/spec044/rework/reviewer/source-fixed-S04-defect.json)。

### F04：将吞掉异常误述为必然不能正常结束

实际第二轮答复说，捕获取消异常后“既不会进入已取消状态，也不会正常结束，而是继续 await 或继续运行下去”。协程之后可以正常 return，原文的 `might misbehave` 也不等于必然卡死。

本轮保留的 offset 5500／7000 有“可能异常”，33000 有“返回值也意味着 done”的定义；材料没有丢失，审核仍放行。第三轮在用户质疑后纠正，不能抵销第二轮错误。完整证据：[source-fixed-F04-defect.json](../../artifacts/spec044/rework/reviewer/source-fixed-F04-defect.json)。

两次冻结回放均使用同一组错误原答复、正确反例与实际页文。第一次两个坏样本正常结束但漏检；第二次两个坏样本均达到 4,000 输出上限并失败，不算识别成功。结果保留于 `rework/source-review-replay/` 和 `rework/source-contract-replay/`。因此不交付新增自动来源门禁，也不提高额度继续重跑碰运气。
