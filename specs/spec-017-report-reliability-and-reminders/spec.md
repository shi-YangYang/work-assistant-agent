# Spec 017 — 多人任务处理、报告可靠性与汇报提醒

状态：DONE · 2026-09-15。实施完成，独立验收 [PASS](acceptance.md)；验证范围见 [实施记录](implementation.md)。

## 目标与当前缺口

让多名员工同时使用工作助手、集中准备日报／周报时，任务可以有序处理，报告有明确结果，员工知道何时需要提交，管理员知道谁尚未提交。

本文“汇报”指管理员安排的日报／周报，由员工审阅或填写后正式提交；发送给工作助手的日常消息是整理报告的材料，不等于已提交报告。

实施前，`worker.main` 每次等待一个任务完成后才领取下一个；已有每人一个运行任务的数据库约束、租约与恢复机制。报告经过通用 Agent 工具循环，只有模型调用 `draft_report` 才能保存；普通文字回复不能形成报告。汇报规则已有生成时间与截止时间，但调度仅检查当天生成时间，没有汇报待办、提醒或停机跨日补齐机制。

沿用 [公司业务方向](../../.ai/decisions/0011-company-agent-direction.md)、[角色与报告管理](../spec-011-web-function-management/spec.md) 和 [任务反馈与用量](../spec-016-web-search-metrics-and-feedback/spec.md)。本次“多人任务”指多人后台请求处理，不新增多人共同编辑或任务指派。

## 范围与目标行为

### R1 — 有界并行与恢复

- 不同成员的任务允许并行，默认最多 3 个运行任务，部署配置可调整；同一成员仍逐个处理，避免会话、工作修订和报告相互覆盖。排队任务持久保存，按创建时间和 ID 领取最早可执行任务。
- 多人集中生成报告、某个模型响应慢或一个任务失败，不得阻止其他成员占用空闲处理名额；不无限创建后台协程或媒体转换进程。
- 多个领取者不得重复执行同一任务，已有公司／成员授权、来源权限、租约续期、配置快照、调用预算和用量记录继续生效；旧执行者不能覆盖新结果。
- 关闭或重启 worker 后，排队任务可继续处理。尚未开始外部请求的中断任务可恢复排队；已发出但结果不明的请求沿用人工确认重试，不静默重复调用模型。
- 前端延续已有排队、处理中和失败反馈，不显示猜测的剩余秒数或全公司队列内容。

### R2 — 报告生成由程序控制完成

- 定时生成、手动生成与重试共用一个受控报告流程：读取本期已确认的工作修订 → 调用报告用途模型 → 校验四个报告栏目 → 事务保存。模型负责整理内容，程序负责是否保存及是否成功，不再以模型主动调用保存工具为前提。
- 只使用本人员、本公司、本报告周期的有效已确认来源；来源 ID 由服务端绑定，模型不能选择员工、修改周期或提交报告。聊天工具不能绕过该入口直接生成已发布报告。
- 四个栏目保持“已完成、进行中、阻碍、下一步”。有效结果必须结构完整、内容有界且非全空；无效结构、截断、服务错误与超时须给出准确失败原因，保留原报告并允许重试，不把普通聊天答复标为报告成功。
- 无本期已确认工作时不调用模型，呈现“暂无已确认工作”，允许员工补充工作或手动填写报告；不编造完成事项。已启用汇报安排的周期仍需按 R3 提交。
- 同一周期始终对应同一份报告；重复点击、重试、调度重入不得重复创建或重复落库。结果已经保存时，任务恢复直接核对保存凭据完成，不再为了补一句模型答复重新调用。
- 员工在生成期间修改、提交报告时，生成结果只作为可选择采用的候选，保留其编辑与提交版本。删除报告、停用成员、角色／来源权限变化后，晚到结果不能使已失效资料重新出现。
- 继续由员工审阅后提交；管理员只能看到已提交正文，不能因新增待办查看员工私有草稿。不保证外部模型永不失败，也不自动重试结果未知的请求。

### R3 — 汇报待办与提交状态

- 员工在“我的报告”查看待提交汇报及截止时间；按日报／周报和状态筛选，点击进入对应周期报告，无报告时提供准备／填写入口。不额外新增一个通用任务管理模块。
- 待办来自管理员启用的汇报安排，不依赖模型成功生成：生成失败或无工作记录时仍可识别本期是否需要汇报。未到截止与已逾期按公司时区计算，排队／生成失败作为独立处理提示。
- **已确认**：无本期已确认工作记录时仍保留待办及提醒，员工可补充实际工作，或按实际情况手动填写“本期无新增进展”后提交。系统不自动代填、免交或视为完成；没有记录不能据此判断员工未工作。
- 提交成功即完成当期待办；已提交报告的新更正草稿不重新算漏交，逾期后提交保留实际提交时间。阅读或关闭提醒不等于完成汇报。
- 管理员在团队看板增加“汇报情况”入口，按周期查看应提交、已提交、未提交／逾期员工，并可筛选、分页和跳转已提交报告。分母来自该周期的汇报安排，不用消息发送人数代替；不新增绩效评价。
- 管理员本人不产生个人汇报待办。员工仅能访问本人待办；管理员仅能访问本公司员工的提交状态和已有授权内容。
- 删除报告后停止其周期提醒，不自动重建；成员停用或改为管理员后停止未完成提醒。保留不含正文的状态记录区分撤销与漏交，不将其算为当前待提交。
- 旧报告不倒推历史欠交；新成员从后续周期加入。已经产生的待办保存安排快照，规则修改不改写其截止时间，新规则用于后续周期；界面明确生效周期。未启用的日报／周报仍可手动生成，不强制产生待办。

### R4 — 站内提醒（渠道与节奏已确认）

- 员工在顶部通知入口看到提醒及未读数；点击定位对应汇报，支持已读。手机与电脑 Web 共用同一记录；沿用现有主题、紧凑布局与键盘操作，不添加常驻大段说明。
- 提醒时机：草稿首次就绪、截止前 30 分钟、逾期后一次。管理员可关闭提醒、调整提前分钟数；提交后停止后续催交，同一汇报的过期提醒合并为当前状态，不反复弹窗。
- 提醒只包含汇报类型、周期、截止时间和入口，不复制聊天、附件或草稿正文，不调用模型生成提醒。
- 未打开网页时记录仍保存在服务端，下次登录可见；本期不承诺关闭浏览器后的系统推送，不接短信、邮件、企业微信或钉钉。管理员先通过汇报情况查看，不自动逐人发送催办。
- 调度重复运行或重启不能产生重复待办／提醒。停机恢复时补齐启用后应有的待办并合并过期提醒；历史过期周期只补待办，不集中补发模型请求。补齐分批进行，不能拖住当前任务。

## 非目标与兼容

不涉及 Electron、移动 App、生产部署、服务器购买、任务指派、请假／节假日排班、老板个性化提醒、自动代提交、通用通知平台或新的消息队列服务。继续使用 PostgreSQL 和现有 harness 的授权、预算与恢复边界；本轮不更换模型供应商或依赖框架。

使用增量迁移，保留账号、模型配置、会话、报告及修订历史。部署并发数是运行上限，不构成几十人真实容量已通过的承诺；实际技术状态在实施完成后更新。

## 验收标准

- [x] 固定模型与同步屏障下，30 名成员集中入队可观察到多任务并行且不超过配置；同一成员不重叠，慢请求和失败不阻塞其他成员，重复领取不重复执行。
- [x] 请求中断、租约过期、旧执行者返回和关闭恢复可重现；已开始的未知请求不自动重发，用量记录与实际尝试一致。
- [x] 模型未调用保存工具但返回有效报告结构时可保存；无效输出、无来源、已保存后恢复、并发编辑／提交／删除均符合 R2。
- [x] 定时、手动和重试生成遵循相同保存规则；重复操作只产生一份周期报告和一份有效待办。
- [x] 提醒时机、已读、提交关闭、规则生效、停用／删除和跨日停机补齐可用固定时钟验证；无工作记录仍保留待办和提醒，手动填写并提交后完成，提醒无需调用模型。
- [x] 员工跨账号访问被拒绝，管理员不出现个人汇报任务，草稿正文不会通过待办、通知或团队统计泄露。
- [x] 电脑／手机 Web 的待办、通知和团队提交情况可操作，列表有界，导航返回保留筛选，错误反馈可恢复。
