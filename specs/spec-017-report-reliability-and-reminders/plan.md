## 实施顺序与边界

1. **任务调度**：在 `services/company/src/paa_server/worker.py` 将串行等待改为固定数量的处理槽位；`config.py` 增加有界并发配置，默认 3、允许 1～8。继续依赖 PostgreSQL 的成员运行唯一约束、短事务领取与租约；领取竞争属于可恢复情况，不令整个 worker 退出。每个任务独立上下文／会话，checkpoint 连接按槽位独立或使用有界连接池，不能共享可变请求状态。
2. **受控报告流程**：在服务端提取报告生成与候选保存模块，复用 `agent/harness.py` 的模型出站、授权、预算及 `usage.py` 的请求记录。一次显式生成尝试使用固定栏目输出契约；解析和校验在服务端完成，兼容现有 Chat Completions 配置，不强迫所有供应商支持某个私有结构化输出参数。无效结果返回失败，不追加隐式纠错调用。
3. **持久安排与提醒**：增量添加周期待办与通知记录，改造 `schedule_once` 为可分批补齐的调度；再接入提交、删除、成员启停与规则保存操作。无工作来源时跳过模型生成，但保留待办；手动填写后的提交沿用同一完成事务。
4. **Web 接入**：扩展 `packages/api-contracts`，在 `Records.tsx` 的报告页面和 `Settings.tsx` 的汇报规则／团队页面增加对应入口，顶部通知放在 `App.tsx` 的现有工具区。组件按职责拆分，沿用共享主题、弹层和响应式规则。

以上模块共享任务、报告和权限状态，实施时由一个实施 Agent 按顺序完成；再由新的独立 Agent 按验收标准复核，不并行改同一模块。

## 数据与事务契约

- **任务**：复用 Job，不引入第二套队列。空闲槽位才领取任务，排序为 `created_at, id`；报告和消息同样受每成员单任务约束，等待中的网络请求不占长事务。媒体转换另设低并发上限，避免仅提高网络并发就同时启动大量转换进程。
- **生命周期**：停止领取 → 有界等待在途处理 → 取消并收集剩余子任务／子进程 → 释放连接。正常退出和异常中断都沿用租约、请求已开始标记及 fence 恢复，不以重启为理由自动重发未知请求。
- **报告**：保存前复核 actor、来源有效性、报告是否删除、base revision 与 fence。内容／候选、服务端来源 ID、结果保存凭据和任务成功标记在一个事务内提交；模型不参与最终数据库提交。不覆盖编辑版本，已保存结果恢复不再请求模型。
- **历史任务兼容**：保留旧 `reportSaved` 凭据的识别；新流程带版本标识，部署时不把尚未结束的旧工具循环强行当作新调用。重试核对原输入／配置快照，显式采用新配置沿用已有尝试隔离。
- **待办**：唯一键为公司、员工、类型、周期；保存触发日期、周期边界、时区、生成／截止时刻和规则修订。提交状态与生成任务状态分离；已有提交与待办建立关联，重复提交不重复完成。规则从下一个对应周期生效，已产生实例保持快照。
- **通知**：按接收人、待办和提醒阶段去重；消息只保存必要定位信息。已读独立于业务完成；员工提交与待办完成、未触发催交的撤销同事务处理。读取和跳转均重新检查身份与当前权限。
- **补齐**：记录调度进度／规则生效范围，按批次处理未检查的周期，不只扫描当前日期。迁移从启用边界开始，不追溯旧欠交；过期周期不自动触发模型。多调度者以数据库唯一约束和锁保证幂等，单条失败不能回滚全公司已处理周期。
- **成员与删除**：待办适用对象为周期开始时有效员工，后加入成员从下一周期进入；停用／转管理员／报告删除撤销对应未完成事项和提醒。恢复账号不追补停用期间义务，历史已提交时间不改写。管理员查看汇总元数据不能复用会暴露私有草稿的 DTO。

## 接口与页面

在既有公司 API 下增加本人汇报待办、本人通知列表／未读数／标记已读、管理员汇报状态查询；列表采用有界分页、服务端过滤。汇报规则扩展提醒选项和生效周期，旧字段读写兼容。最终字段名以共享契约为准，不在文档重复维护完整类型。

待办入口可按类型和周期定位尚未生成的报告，准备报告沿用显式写操作及幂等键；GET 查询、打开通知和进入页面不自动调用模型。团队状态仅返回成员、周期、提交／逾期状态及授权报告入口。低频刷新与页面重新聚焦刷新即可，不新增长连接基础设施；失效会话清除当前通知状态。
