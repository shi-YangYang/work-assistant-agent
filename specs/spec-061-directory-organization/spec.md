# 项目目录归类与边界整理

## 状态

已完成目录整理与独立验收。本次迁移范围内无待返工项。验收时记录的两个既存日期假设失败，已按后续要求修复并定向复验通过；原验收结果保留，未重新运行全量。详见[最终验收](acceptance-final.md)。

## 背景

[此前的目录整理](../history-001-050.md)已建立应用、业务模块和组件分组，但后续功能继续增加，部分子目录又集中放入了不同职责的文件。需要沿用现有架构继续归类，并处理与路径绑定的测试、脚本和文档。

问题不在于一个目录同时存在 TSX 和 CSS：同一组件及其私有样式放在一起是合理的。需要解决的是不同功能堆在同一层，以及组件、Hook、辅助函数之间的归属不清。

## 目标

- 根据业务与功能职责找到文件，减少在大目录中依赖文件名前缀搜索。
- 整理 Web、公司后端及其测试中已经拥挤的目录；盘点桌面端、沙盒、共享包和脚本，保留已经清晰的结构。
- 同一组件的 TSX、私有 CSS 和专用展示逻辑保持就近；后端按现有子领域组织，不另建一套架构。
- 同步更新静态导入、动态导入、测试替身路径、脚本扫描和当前使用文档，保证正常功能与验证入口不受影响。
- 明确新增文件的归属规则，避免继续往通用目录堆文件。

## 非目标

- 不改变产品功能、页面排版、文案、交互、API、权限或数据结构。
- 不修改 Agent 提示词、工具说明、工具参数、调用顺序、模型参数、重试策略和任务预算；不增加模型核对或额外请求。
- 不借整理删除旧功能、兼容字段或历史测试，不修复无关问题，不以此宣称性能提升。
- 不新增框架、依赖、微服务、统一仓储层或代码生成器。
- 不改变 `apps/`、`packages/`、`tests/`、`scripts/` 的职责，不移动 Agent 治理目录；不整理用户数据、模型资源、历史附件或测试产物。
- 不为每个文件创建文件夹，不单独收集所有 CSS，也不制定“一个目录最多 N 个文件”的硬性门禁。

## 目标行为

用户仍使用相同页面、功能和启动方式。开发者寻找附件预览、思考强度、工作记录、工具注册等代码时，可以从职责明确的目录进入；增加相关功能优先放入已有分组。

测试仍由原来的命令发现并运行，目录变化不会少收集用例、漏跑验收或放松故障测试的环境保护。

## 功能需求

### 1. 统一归类原则

- 沿用 [Web 与服务端架构边界](../../docs/architecture.md)。Web 保留 `features/<业务>/{components,hooks,api,lib,utils}`，在拥挤层内按功能归组；不再新增平行的业务目录体系。
- 一个目录代表可以说清的业务能力或组件组合；先确认归属，再决定是否增加一层。已清晰的小目录不强行拆分。
- 私有 `*.module.css` 随所属组件迁移；跨组件共享样式继续放在现有 feature styles 或 `styles/patterns/`，不复制、不新增全局样式。
- 原文件名尽量保留，只在目标位置确有命名冲突时做必要调整。避免大量 `index.tsx`、通用 `helpers.py` 掩盖实际职责。
- Python 新包的 `__init__.py` 默认保持空，不建立汇总整个业务的大型导出入口；保留现有必要的领域注册入口。
- 不在旧位置留下仅转发新路径的空壳文件，也不复制出新旧两套实现。确实属于持久化类型身份或外部入口的文件原位保留。

### 2. Web 整理

- 聊天输入组件分为主体、附件、控制项；权限、上下文和思考强度控件采用同一归类方式。
- 会话选择和人设选择归组；消息转写及编辑归入 transcript 分组，已有 reply 分组保留。
- 聊天 Hook 按会话生命周期、消息输入、偏好设置、成果读取归组；不改变状态所有者或重复创建 Hook 实例。
- 公共 UI、模型服务、登录页、工作页等已按职责分组的区域保留；仅更新它们对被移动模块的引用。
- 保留当前懒加载、CSS 导入先后、滚动容器和路由边界。整理不能造成页面尺寸变化、样式覆盖变化或新增整页加载。

### 3. 服务端整理

- Agent 工具保留统一注册入口，工具实现按业务、资料、流程控制和沙盒能力归组。
- 上下文引用构建从上下文基础能力中归组；完成处理中的证据准备、可选核对、异常恢复各有明确位置。
- 工作模块保留 router、models、通用查询和保存规则；将草稿、记录命令和 Agent 适配归入相应子目录。
- 消息模块分出输入处理、来源引用；报告模块分出生成辅助逻辑，继续复用已有调度模块。
- 保留 `app.main:app`、`app.worker`、`app.cli`、`agent/harness.py`、公共任务上下文、租约、ORM 登记与数据库迁移位置。
- 只调整组织和必要的导入，不改变模型看到的工具集合、工具名称、参数 Schema、说明文本及注册顺序；可选核对不能因重新装配而进入默认路径。

### 4. 测试与工程引用

- 后端测试按 Agent、业务模块、模型服务、任务运行与集成等领域归组。跨领域端到端用例保留独立位置，不硬拆成多个重复用例。
- 把已被多个测试导入的工厂、受控模型、请求辅助函数等提取到测试专用支持模块；不复制函数，不让支持模块反向导入测试文件。
- 共享 fixture 留在共同父目录的 `conftest.py`，保持作用域、隔离、鉴权和清理方式。分组不触发额外登录、额外哈希或扩大数据库清理范围。
- Web 保留普通测试与 DOM 测试的区分，各自按功能分组；共享 setup/helper 保留在共同入口，不跟随某个业务测试移动。
- 同步更新测试发现、显式 node ID、路径推导、monkeypatch/mock 和验收脚本；保留文件名与用例名，便于映射迁移前后的用例。
- 已有默认测试与手动验收的选择范围不变；不能用全量递归扫描意外把真实模型、破坏性或需要隔离环境的测试加入默认 CI。
- 当前架构说明和运行文档中的有效路径随之更新；历史 Spec、原始验收报告和历史测试产物保留原始证据，不全量重写。

### 5. 后续维护

在现有架构说明中补充新增文件放置规则和本次目录示例，继续复用架构检查约束依赖方向、CSS 归属和循环导入。不得为了这次整理创建一套新的治理规则或文件数量评分系统。

## 边界条件

- 大小写不敏感的本地文件系统不能掩盖 Linux 导入错误；路径拼接兼容 Windows。
- 动态导入、字符串注册、子进程入口、资源相对路径和测试替身与静态导入同等检查。
- 涉及 LangGraph checkpoint、持久化类型或已保存任务时，先核实是否依赖 Python 模块全名；存在依赖的契约定义原位保留，不通过清空历史数据解决。
- 导出的 API Schema 和工具 Schema 不因模块归类改变；如果同名类型导致生成标识变化，应调整迁移边界。
- 同批存在用户未提交改动时保留并兼容，不能覆盖或重置。

## 技术约束

- 不改变依赖版本、打包方式、数据库 schema、部署拓扑或 CI 执行策略。
- 不通过新增多层 re-export、修改 `sys.path` 注入每个业务子目录、降低架构断言等方式让旧引用继续凑合运行。
- 使用项目现有格式化配置处理修改的源码；测试支持代码提取仅限迁移所需，不趁机改写测试逻辑。
- 实施按相互耦合的目录批次串行推进，由实施 Agent 开发、新的独立 Agent 验收。

## 兼容性要求

路由与响应、工具契约、Graph 节点标识、存储字段、任务状态、用户权限、流式事件、历史会话恢复、启动命令和部署入口均保持兼容。运行路径只随内部导入变化，不增加模型调用、数据库操作或前端请求。

不需要数据库或用户数据迁移。数据库迁移文件及版本链保持不变；不要求用户删除本地数据或重新创建账号。
