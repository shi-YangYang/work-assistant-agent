## 修改顺序

1. 冻结应用与运行配置，建立隔离资源，确认 API、worker 载入相同版本。
2. 生成 Agent 专项清单和适用性矩阵，编排样本、先验断言、故障位置与清理动作。
3. 补测试侧调用观测和循环分析，用固定轨迹验证重复识别及合法调用反例。
4. 运行相关固定测试，保留所有失败；顺序执行破坏性分组，恢复测试夹具后继续。
5. 运行真实多轮、保留样本和浏览器流程，按预注册计划观察高风险样本随机性。
6. 对失败作最小复现和归因，合并问题，核对覆盖缺口与清理记录。
7. 新的独立验收 Agent 检查证据、覆盖和问题归类。只返工测试／报告缺口，不修复产品。
8. 提交问题列表，等待用户决定修复范围。

## 数据流与观测

测试用例 → 已有 API／浏览器入口 → 真实 API 与 worker → 模型及工具 → 数据库／文件 → 用户结果。

观测同时关联四层：模型响应中的工具请求、调度后的逻辑节点、实际执行尝试、提交的副作用。以真实分发边界采集，不能仅依赖 UI todolist。可在隔离测试进程装配包装器，保持输入、输出、异常与授权检查不变。

重复指纹包含工具、规范化参数、用户／租户、用户轮次、目标与状态版本；保留游标、参数顺序语义及代码内容差异。语义相近只标候选，不能自动合并或抑制真实调用。公开报告使用脱敏摘要，原始证据按测试 run 归档。

测试观察器的状态 GET、故障注入的重发、工具内部尝试与模型新调用分别标记。不能把观察流量算成 Agent 工具循环。

## 检查与风险

规格编写按 S0，只检查文档 diff 和引用。执行阶段属于跨工具、权限、持久化与恢复的高风险测试，范围限定为 Agent 子系统；不默认运行 Electron 或全站构建检查。

- 先校验测试脚手架能够识别预制循环、真实重复写入和合法重试；新增／修改源码用项目格式化器处理。
- 基线记录已有失败，不修改其断言；若它阻塞后续执行，标明依赖范围，采用独立夹具继续可运行部分。
- Spec 058 曾记录的三项 `test_task_retry.py`、一项 `test_tool_catalog.py` 和一项架构循环失败列为待复验基线，不能直接沿用通过／失败结论，也不能全部当作业务缺陷。
- 破坏性分组顺序运行，恢复后核对资源归属与数据状态；并发仅用于专门的竞争场景，避免污染普通模型耗时。
- 真实模型结果记录首个可见文字、总耗时、工具／模型次数、重试和空转时间。用于解释问题，不用跨网络、跨强度的单次结果宣称性能退化。
- 测试超时需容纳应用预算与清理；受控长链可以加速时间，但报告必须区分模拟时间与真实耗时。
