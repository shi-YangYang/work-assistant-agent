# Spec 059：Agent 全量测试与工具循环排查

状态：测试与独立验收完成；产品问题未修复，等待用户审查[问题清单](issues.md)。

## 背景

以提交 `70ba0f76788b02c8d841bf22fb68d79f230c9b87` 中的 [Web 全量测试方案](../spec-054-web-comprehensive-testing/spec.md)为样本和覆盖方法参考，针对当前 Agent 重新测试。该提交包含测试和修复，不作为本次运行版本，也不直接继承历史通过结论。

曾出现同一偏好被保存两次、连续七次调用保存记忆但只写入一次等情况。只核对最终答复或数据库结果，会漏掉无效调用、工具循环和时间消耗。

## 目标

- 覆盖 Agent 的全部可用工具、业务动作、主要多轮流程及失败恢复边界。
- 引入隔离的破坏性测试，核对副作用、权限、恢复和终止行为。
- 分别统计模型发起调用、工具实际执行、最终数据写入，定位重复调用和循环。
- 全部测试结束后提交有证据的问题清单；测试期间不修复产品问题。

## 非目标

- 不测试 Electron，也不重新审查与 Agent 无关的 Web 页面和全部后台管理功能。
- 不调整提示词、模型参数、业务规则、工具额度、超时或产品架构。
- 不把精确字数、文风偏好、偶发知识错误直接判为系统缺陷，不恢复逐条模型核对答复。
- 不部署，不操作日常账号数据，不以“全部通过”为目标边测边修。

## 当前行为

- 工具按工作、汇报、资料、文件、记忆等目录按需加载；角色、权限模式、沙盒配置影响可用能力。
- 工具重试、业务回执、任务恢复与记忆去重各有机制，需要检查组合行为。
- 消息任务共享内部预算：默认 64 次逻辑工具调用、96 次实际模型请求、1800 秒；包含收尾预留。预算不向用户展示。
- 已有 API、多轮对话、浏览器、沙盒和故障测试脚本，可复用环境与证据采集。

## 目标行为

本次改变测试覆盖和问题可见性，不改变产品运行行为。测试应回答：用户任务是否完成、哪些调用必要、哪里发生重复或循环、是否多写数据、失败后能否安全停止或恢复。

## 功能需求

### 1. 冻结基线与覆盖清单

- 实施开始时记录实际应用提交、差异指纹、依赖、API／worker 运行版本、模型与强度、权限、预算、沙盒配置。实际冻结应用提交为 `12c4db10ed1a91a41fc6fab2b7374708b017b430`；测试期间不改应用。
- 从实际工具注册、动态目录、业务动作、Agent API 和任务状态生成清单，包含框架工具、兼容工具及沙盒开关差异。
- 每个可用工具和业务动作都映射到正常、适用的权限拒绝、输入边界、失败与恢复用例；逐项记录 PASS／FAIL／BLOCKED／NOT_RUN／N/A。N/A 必须说明原因。
- 不能以“接口被请求过”“前端有完成标记”替代业务断言；不能只用已有测试文件反推覆盖完整。

### 2. 分层测试

- 固定输入测试：覆盖工具、状态流转、去重、预算和故障边界，使用可控模型响应复现工具循环。
- 真实模型测试：至少 80 条不同任务，其中至少 50 条为 3～8 轮连续流程；员工、管理员各至少 30 条，至少 24 条重点观察重复调用或循环。数量不替代清单覆盖。
- 至少 20% 真实任务为新增保留样本；首次运行前冻结预期，不根据模型回答修改判定标准。
- 至少 12 条真实流程经浏览器完成，覆盖发送、中断、重试、确认／提问、工作引用、附件、流式交付和切换会话。
- 两个人设、三个权限模式、当前配置的思考强度均需覆盖；low／max 等已配置差异做同题对照，记录实际参数，不静默降级或混算结果。
- 对预先选定的 12 条高风险任务各运行 3 次，观察随机性。保留首轮成绩，不通过无限重跑消除失败。

### 3. 重复调用与循环证据

每条链路关联用户轮次、job／attempt、模型请求、tool_call、逻辑节点、实际尝试、业务回执与最终产物。记录脱敏参数、结果摘要、时间、状态版本与副作用。

- 同名同参调用至少两次且没有新依据：列为重复候选。
- 同一状态下相同调用至少三次，或 A→B→A→B 等反复往返：列为循环候选。
- 候选必须结合数据变化、分页游标、失败类型和用户新授权人工核对，不能机械认定同名工具重复。
- 分开统计工具自动重试、模型再次发起调用、接口兼容重发、恢复重放、测试观察请求；后端幂等成功仍可能存在模型无效调用问题。
- 检查参数轻微改写但意图相同、重复加载目录、永久错误反复重试、无变化的搜索／读取、反复生成文件、重复保存记忆和答复收尾循环。
- 合法分页、用户明确重复执行、写入后的核对、修正参数后的重试应有反例，避免误报。

### 4. 破坏性与边界测试

覆盖断网、丢响应、重复／乱序事件、并发发送与确认、版本冲突、取消、worker 中断、租约恢复、数据库暂时不可用、模型异常、沙盒超限及恶意输入。

重点在“接受任务前后、执行前、写入成功但回执未送达、恢复中、收尾中”注入故障，核对最终数据库、回执、文件与 UI 是否一致；已完成操作不得因重试重复产生副作用。

预算边界用受控时钟与固定模型响应验证，同时运行真实复杂工具链。不得为了获得通过结果提高预算、降低强度或关闭保护。

### 5. 发现问题后的处理

- 保留首次失败，记录最小复现和影响；继续不依赖该问题的场景。
- 不修改应用源码、提示词、数据库结构、业务测试预期或运行限制。不得把修复包装成测试前置准备。
- 仅允许修正本次测试脚手架、隔离环境或测试夹具的问题，记录修改原因、版本和受影响结果，保留原始证据。
- 既存失败重新验证后单独标记；模型错误、提供商错误、测试错误、环境阻塞与系统缺陷分别归类，证据不足时标为待定位。
- 全量执行结束后统一提交问题清单与修复建议。用户审查前不启动产品修复，也不进入“修到验收通过”的自动返工流程。

## 边界条件

- 破坏性测试仅使用独立测试数据库／schema、租户、账号、文件目录和运行资源；不连接生产，不删除日常数据，不发送真实外部消息。
- 提示注入、SSRF、路径穿越等使用受控材料与目标；沙盒资源耗尽测试不得在宿主直接运行攻击代码。
- 每例有取消和清理策略。测试看门狗与应用截止时间分开，不能用过短的测试超时冒充产品失败。
- 隔离失效时停止受影响分组，保留证据并报告；其余安全、独立分组继续。阻塞项不得计为通过或覆盖完成。
- 不设置与覆盖无关的总调用硬上限，但不无限增加样本、重复等待或重跑。达到冻结覆盖范围且结果明确后结束。

## 技术约束与兼容性要求

- 复用现有 `scripts/company/web-acceptance/`、后端测试与沙盒测试；新增内容只承担 Agent 专项样本、观测、故障和报告职责。
- 测试观测钩子仅在隔离测试进程启用，不改写工具参数、结果、授权和预算，不进入正式启动链路。
- 原 Spec 054 样本、首轮结果和历史报告不覆盖；本次产物独立存放。
- 记录可观察的工具请求和结果，不要求模型输出隐藏思考链；证据不保存密钥、会话凭据或真实用户隐私。
