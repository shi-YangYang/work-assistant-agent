## MUI-001：部分页面标题与返回区仍有过量留白

- **条件**：员工或管理员；宠物默认隐藏；Chromium 320×568、390×844，浅／深色；200% 文字放大也能观察到同一预留。
- **复现**：打开我的工作，再进入工作详情；对照原始上报及汇报规则页。
- **实际**：我的工作标题约 y=16–44，搜索到 y=112 才开始。工作详情菜单 y=8–52，返回入口 y=104–148，标题到 y=160 才开始。短屏的正文空间被固定留白挤占。
- **预期**：全局导航、标题／返回和内容有清楚但紧凑的层级；不为隐藏的元素保留大块空间。
- **证据**：[工作列表](../../artifacts/spec073/20261017-015130-b9afe2a/business/narrow-M08-admin-work-320x568-light-chromium.png)、[工作详情](../../artifacts/spec073/20261017-015130-b9afe2a/business/narrow-M09-employee-work-detail-320x568-light-chromium.png)。
- **根因线索**：公共 `PageHeader.module.css` 的手机 `min-height: 88px`、描述 `margin-top: 64px`，及 `DetailBackLink.module.css` 的 `margin-top: 88px`。以截图为依据，不仅由代码推断。
- **最小建议**：统一收紧共享页头、返回栏的布局。保持已确认的全站悬浮宠物行为，不恢复“显示宠物时给报告页额外占位”。
- **相邻回归**：来源、工作详情、普通设置页、长标题、低高度及导航按钮；报告详情当前独立布局不回退。
- **关联**：M07–M09、M15–M17、S05；原分组 BUS-001。

## MUI-002：320px 团队筛选区占用过多首屏空间

- **条件**：管理员，Chromium 320×568，团队看板的工作进展页，筛选默认收起。
- **复现**：打开团队看板，观察搜索、筛选、当前工作／期间更新的位置。
- **实际**：搜索约 y=251，筛选按钮独占 y=303 一行，当前工作／期间更新又在 y=361；首条工作标题到 y=477。统计条局部横滑是现有设计，不是整页横向溢出。
- **预期**：保持标题→子页→统计→筛选的已确认顺序，同时让首屏能呈现更多工作内容。
- **证据**：[320px 首屏](../../artifacts/spec073/20261017-015130-b9afe2a/business/narrow-M11-admin-team-work-320x568-light-chromium.png)。
- **根因线索**：搜索最小占用与筛选宽度、间距合计超过可用宽度；视图切换又形成独立一行。
- **最小建议**：手机搜索允许收缩，与筛选共用一行；减少视图切换的独立留白。不能只收紧页头而忽略筛选工具栏。
- **相邻回归**：360／390／430、日报周报、日历、自定义范围、长员工名、无结果和清除筛选。
- **关联**：M11、J09；原分组 BUS-002。

## MUI-003：“全部附件”弹窗中长文件名被裁切

- **条件**：员工，Chromium 390×844，工作包含多个超长文件名材料。
- **复现**：工作正文添加多个长文件名文本并保存→管理工作→全部附件。
- **实际**：第 4、5 个长文件名按钮超出弹窗内容宽度，文字被左右裁切，文件大小挤到下一行。整页 `overflow=0`，不能靠页面宽度断言发现。
- **预期**：文件名在自身区域换行或省略，可通过详情查看完整名称；大小和操作位置稳定。
- **证据**：[全部附件弹窗](../../artifacts/spec073/20261017-015130-b9afe2a/business/extras-recovery-M09-employee-all-materials-modal-390x844-light-chromium.png)。
- **根因线索**：`WorkMaterials.tsx` 使用 `.caption > button` 显示文件名；样式只对 `.caption a` 设置换行，按钮缺少相应宽度和文本处理。
- **最小建议**：文件名容器可收缩，明确最大宽度与换行／省略规则。保留材料详情及原文件下载。
- **相邻回归**：材料详情、移除确认、正文材料卡片、嵌入工作详情、中文／英文／无空格长名。
- **关联**：M09、S02、S04、J07；原分组 BUS-004。

## MUI-004：部分小按钮的实际触摸范围不足

- **条件**：员工聊天输入框；管理员模型设置；触屏、无 hover。浅／深色均有代表证据。
- **复现**：添加文件和录音后点击删除／播放；在模型设置中添加多个思考强度 Tag 后删除其中一个。
- **实际**：附件删除图标 DOM 为 22×22，但伪元素扩大了命中区；`elementFromPoint` 中心轴实测仍只有约 34px 横向、31px 纵向。草稿录音播放为 32×32。强度 Tag 删除按钮为 44×24。功能可用，但手指容易漏点或点到旁边预览。
- **预期**：主要触摸目标至少 44px；图标视觉尺寸可以保持紧凑。
- **证据**：[附件命中检查](../../artifacts/spec073/20261017-015130-b9afe2a/assistant/173-M05-chromium-390x844-light-touch-target-measure.png)、[命中采样](../../artifacts/spec073/20261017-015130-b9afe2a/assistant/touch-target-measurements.json)、[模型控件尺寸](../../artifacts/spec073/20261017-015130-b9afe2a/journeys/M18-control-geometry.json)。
- **根因线索**：`ComposerAttachments.module.css`、`ComposerAudioPreview.module.css` 和模型 `ReasoningSettings.module.css` 的点击区域约束。
- **最小建议**：扩大透明命中区并为边缘和相邻控件留出间距。不能只把伪元素放大到与卡片预览、其他删除按钮重叠。
- **相邻回归**：图片／文件／音频上传、错误重试、横滑附件、标签增删及桌面 hover。
- **关联**：M05、M18、S04、S05、J03、J04、J11；合并 A-001 与模型标签观察。

## MUI-005：200% 文字放大时“＋”面板标签拥挤

- **条件**：390×844 Chromium，计算字体和数值行高同时乘 2；`normal` 行高保持。这是文本放大仿真，不等同真机系统字体设置。
- **复现**：进入会话→输入草稿→打开“＋”→按上述方式放大文字。
- **实际**：四列标签不换行，“添加图片／添加文件／引用工作”挤在一起，末项上下文右侧截断；正文可以正常换行。
- **预期**：大字下入口仍可区分，允许合理换行或减少列数。
- **证据**：[字体与行高同倍放大](../../artifacts/spec073/20261017-015130-b9afe2a/assistant/161-S07-chromium-390x844-light-text200-with-lineheight.png)。
- **根因线索**：`MobileComposerPanel.module.css` 固定四列与标签 `nowrap` 组合。
- **最小建议**：标签允许换行，或按内容最小宽度改成两列，不通过强行缩小字体解决。
- **相邻回归**：普通字号、320／360、低高度、上下文百分比、强度及权限弹窗、文字草稿保留。
- **关联**：M04、S07、J02；原分组 A-002。早期仅放大字体而固定行高的压力图不作为本项证据。

## MUI-006：宠物隐藏时通知入口不明显（设计建议）

- **条件**：普通员工或管理员，沿用当前默认隐藏宠物设置。
- **复现**：打开主菜单和系统设置；再使用命令搜索“通知”，或先显示宠物再从宠物弹窗进入通知。
- **实际**：通知可正常访问，但主菜单、系统设置均没有明确入口；宠物隐藏时也看不到持续的未读角标。
- **预期／取舍**：用户不必知道隐藏入口或先打开宠物，才能发现通知。当前入口位置是之前确认的设计，本项不是权限或接口故障。
- **证据**：[动画结束后的主菜单](../../artifacts/spec073/20261017-015130-b9afe2a/business/acceptance-nav-M02-employee-main-navigation-settled-390x844-light-chromium.png)、[搜索通知](../../artifacts/spec073/20261017-015130-b9afe2a/business/journeys-recovery-J01-employee-search-notifications-390x844-light-chromium.png)。
- **建议**：宠物隐藏时保留一个可见通知入口或计数，具体位置由用户选择；本轮不擅自恢复已删除菜单。
- **相邻回归**：宠物显隐、未读数、标已读、通知权限及手机导航。
- **关联**：M02、M13、M23、S08、J01、J10；原分组 BUS-003。

## MUI-007：多文件回答末尾的材料范围说明过长（设计建议）

- **条件**：390×844，真实隔离 API／worker，两批 7 份文本加 1 张图片，模型由 localhost 受控服务返回固定回复。
- **复现**：上传并发送→任务完成→刷新后追问早期材料→查看回复末尾。
- **实际**：7 份文本分别重复“已准备文字 1/1 个分段；本任务已向主模型提供 1 个文字分段”等技术说明，占据大量纵向空间。该部分由系统追加，不是模型自然生成的冗长回答。
- **预期／取舍**：保留读取不全、未读、部分处理的透明提示，同时让完整读取的正常结果简洁可读。
- **证据**：[真实追问结果](../../artifacts/spec073/20261017-015130-b9afe2a/journeys/J03-real-followup.png)。
- **代码依据**：`apps/server/app/modules/attachments/documents.py` 的材料范围摘要与答案追加逻辑。
- **建议**：完整读取可汇总，逐文件细节放可展开区域；部分／失败等重要缺口仍明确展示。只调整本地结果整理和展示，不增加模型核对、提示词或往返，也不减少实际读取范围。
- **相邻回归**：完整／部分／失败混合、历史附件追问、重复附件及刷新；遵守附件读取透明度要求。
- **关联**：M06、M07、S02、J03。

## MUI-008：清空记忆与删除声纹的确认方式不统一（设计观察）

- **条件**：员工记忆设置、管理员声纹设置；与公告管理等已有公共 React 确认弹窗对照。
- **复现**：记忆编辑器点击清空；在有已登记声纹的列表点击删除。
- **实际**：这两处调用浏览器原生 `window.confirm`。清空记忆的取消／确认、刷新为空已通过真实隔离 API 验证；声纹删除使用受控 UI 返回，确认后条目消失。没有发现这两条操作的功能故障。
- **预期／取舍**：同类破坏性操作使用一致的应用内确认方式；浏览器和内嵌容器决定的原生外观不受应用主题控制。
- **证据**：[记忆确认事件](../../artifacts/spec073/20261017-015130-b9afe2a/business/memory-confirm-dialogs.json)、[声纹确认与请求](../../artifacts/spec073/20261017-015130-b9afe2a/business/voiceprint-controlled-evidence.json)。页面截图不包含原生窗口，本项不声称已审阅其真机外观。
- **代码依据**：`MemoryEditor.tsx:58`、`VoiceprintsPage.tsx:52`。
- **最小建议**：复用现有公共确认组件，保留取消、确认、处理中禁用和错误反馈；无需修改删除接口。
- **相邻回归**：取消不删除、确认只提交一次、失败可恢复、长姓名和关闭后的焦点。
- **关联**：M20、M21、S04、J12。
