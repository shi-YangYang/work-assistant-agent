# 工作助手三级执行权限与临时回答框

## 状态

已实施，独立验收通过。验证范围及限制见[验收结果](acceptance.md)。

## 背景与目标

工作助手已具备持久任务、持续指令、操作回执和澄清续接。用户还需要选择助手的自主程度，并在任务缺少必要信息时就地回答，避免在聊天正文里反复确认、重新描述任务。

- 提供三级执行模式，明确哪些操作需要点击确认。
- 用临时回答框承接结构化问题，回答后继续原任务。
- 模式、提问、批准和业务权限各有明确职责，复用现有任务与回执机制。

## 当前行为

- 会话只有人设选择，没有执行模式。`intent.py` 同时承载用户意图、授权来源、参数语义与部分确认判断。
- 创建／修改工作、生成／编辑报告在核对后执行；删除工作、提交／删除报告固定生成确认卡。
- `BusinessAction` 保存预览、回执和版本；确认接口只允许固定的三个动作，前端按钮也按提交／删除展示。
- 澄清通过普通聊天回复和下一条消息承接，没有结构化问题及回答入口。等待状态不占用正在执行的 worker。

## 目标行为

执行模式与回答面板按以下规则实施。

### 1. 三级模式

界面名称为“执行权限”，选项使用业务语言：

| 模式 | 常规业务写入 | 提交／删除 | 适用体验 |
| --- | --- | --- | --- |
| 逐项确认 `ask` | 展示变更后由用户确认 | 确认后执行 | 先看准备修改什么 |
| 自动审核 `auto`，默认 | 用户意图明确且核对通过后执行 | 保留人工确认 | 日常使用，减少打断 |
| 自主执行 `full` | 在用户任务范围内执行 | 用户明确要求且对象、内容清楚时直接执行 | 完整委托当前任务 |

- 三种模式都可以查询、分析、联网、读取已授权材料及保存私人创作成果；这些不逐次弹出批准。向“我的工作／报告”写入、提交、删除才受上述策略控制。
- 待确认建议仍是草稿，不能绕过模式直接应用。正式操作与建议落库的最终入口必须使用同一策略。
- 模式只控制执行确认方式，不改变管理员／员工角色、公司边界、对象所有权、来源访问、账号状态或版本校验。员工选择自主执行也不能访问同事的私人资料。
- 自主执行不允许把材料、网页或助手自己的推断当成用户指令；“帮我看看”不意味着自动保存，“这条不要保存”在所有模式下生效。缺少对象、日期或必要内容时仍应提问。
- 意图理解、参数与追加语义核对、公司权限、执行批准、交付核对分别表达。现有语义核对继续复用；不为三级模式叠加固定模型调用，也不把三种模式写成三套独立 harness。
- 策略统一输出允许、等待批准或禁止，并附明确原因。参数错误由助手修正，服务故障使用原重试，业务无权限直接说明；不能将这些错误伪装为用户批准问题。

### 2. 模式入口与作用范围

- 执行权限选择放在文字输入框下方，与发送按钮共用一行工具栏：左侧依次为“添加文件、执行权限”，右侧依次为“上下文、麦克风、发送／中断”。添加文件入口保留现有附件类型；人设选择继续放在会话顶部。
- 模式选择常驻显示当前模式名称，菜单中各用一句话解释。窄屏缩减间距和文案占宽，保持左右分组及顺序，不溢出；录音时停止控件仍位于右侧麦克风的位置，状态切换不改变按钮顺序。
- 按账号、会话保存。旧会话和新会话默认自动审核；空会话可先选择，首次发送时与会话一起创建。新会话不继承其他会话的自主执行。
- 任务在排队／执行时禁用切换；服务端也拒绝并发更改，避免只靠前端控制。等待用户回答时可切换，后续运行使用新模式。
- 每轮任务保存实际使用的模式及版本。修改模式不自动批准已有确认卡，也不让旧重试取得后来提高的权限；降低模式后，尚未执行的旧操作不得按旧高权限放行。
- 首次切换到自主执行时，明确说明该模式会免除用户已明确要求的提交／删除的再次确认；确认后对当前会话生效，不在每条消息上重复提示。
- 管理员和员工都可选择本人的会话模式；本期不增加公司级模式管理后台。

### 3. 操作批准

- 复用 `BusinessAction` 与现有确认卡，扩展到逐项确认模式的创建、修改及报告生成等动作，不另建一套操作回执。
- 卡片显示动作、对象、关键字段变化；删除沿用已有影响范围，报告生成明确只批准生成而非提交。按钮按实际动作命名，不能所有动作都显示“确认提交”。
- 一次批准仅针对所见的操作与版本；成功后返回原回执。拒绝结束该事项，不把同一操作换节点再次请求。
- 已批准的同一操作不再要求重复批准。内容、对象、来源或删除范围发生变化时，旧批准失效，重新展示真实差异。
- 人工批准后可继续原任务的后续事项，例如保存工作后解释实施建议；不能要求用户另发“继续”。拒绝后也应说明已保留的结果及受影响的依赖事项。
- 等待批准期间释放 worker。点击确认可尽快收起操作控件并展示处理中；网络提交失败保留输入和重试入口，不锁住整个页面。
- 一条变更只展示一个批准入口，避免确认卡和临时回答框重复询问。普通“嗯”“继续”或回答另一个问题不能被当作对危险操作的批准。

### 4. 临时回答框

- 助手通过结构化提问工具提出必要问题，类型包括对象选择、缺少的字段、用户偏好和任务范围。只有确实影响执行或结果时才问。
- 一次集中展示 1～3 个有关问题；支持单选、多选及自由文本。没有合适候选时直接输入，不凭空生成选项。选项不预先代替用户提交。
- 对象选项绑定已经读到且仍有权限的真实 ID；展示可区分的名称与必要说明，不暴露无权对象的名称或内容。
- 在输入区上方显示一个轻量回答面板，顶部为问题，下面为选项／输入和“提交回答”。桌面不遮住整个页面；手机适配键盘与安全区，长内容在面板内滚动。
- 支持收起、重新展开和取消本次任务。收起不是拒绝或回答，不触发执行；取消不回滚已经完成的操作。
- 提交成功后面板收起，问题与答案在聊天中留下简短、可展开的记录；原任务恢复执行，不重复发送原问题或已完成动作。失败时保留答案并就地显示错误。
- 保留普通聊天答复能力：用户可以直接输入“甲客户那项”“下周五”等，服务端关联当前问题后继续。同一输入不能既被当作回答又产生一次重复任务。明确改做新任务时使原问题失效，不把新内容填入旧问题。
- 三种模式都可提问。自主执行免除操作批准，不等于让助手猜缺失信息；选择人设只改变表达，不改变问题或权限规则。
- 沿用中性黑白灰、CSS Modules、现有工具栏与动效；不得使用浏览器原生 `prompt`／`confirm`，不增加常驻任务侧栏。

### 5. 持久化与恢复

- “临时”指界面仅在需要回答时出现。问题及状态必须持久化，刷新、切换页面、断网重连及 worker 重启后可恢复。
- 问题绑定公司、账号、会话、逻辑任务、来源消息及版本；答案作为真实用户输入保存，绑定问题版本，不能由模型代答。
- 生命周期明确区分等待回答、已回答、取消和失效。相同任务、相同缺失项没有新证据时复用同一问题；已回答问题不重新打开。
- 回答接口幂等；多标签页提交、重复点击和响应丢失只能生成一次续接。过期问题返回明确的失效状态，不能套用到新任务。
- 问题落库后结束本轮等待，不保持连接、数据库事务或 worker 租约等候用户。后续消息／批准创建关联的续接运行，复用既有任务与业务回执。
- 对仍未回答的问题，助手不得继续执行依赖其答案的操作；同一模型批次同时提出问题和相关写操作时也必须阻止先写后问。
- 删除会话／账号、来源修订、对象删除、权限变化、用户中断或任务替换必须处理相关等待项；旧运行的迟到结果不得重新弹出失效面板。
- HTTP、SSE、刷新查询使用相同的安全投影；节点列表显示“等待回答／等待确认”，不显示为失败或整个任务已完成。

## 非目标

仅覆盖 Web 工作助手。不增加新的公司角色、审批后台、任意 shell、跨会话永久批准、跨端 UI 改造或新的 Agent runtime。手动工作／报告页面的按钮权限与确认不随聊天模式改变。

## 技术与兼容要求

- 策略使用独立类型和可复用函数，业务模块执行真实权限校验，前端不提交可信的 `allowed` 标记。
- 继续使用既有持续指令、稳定事项 ID、操作回执、任务租约、检查点与节点重试。不能因增加模式绕过上一期的幂等、来源和追加保护。
- 扩展会话及相关 API 契约；旧客户端缺少模式字段时按自动审核处理。已有确认卡保持等待，不迁移成已批准。
- 旧消息没有结构化问题时继续展示原回复；不扫描历史生成待回答任务。
- 采用增量迁移；自主执行下明确要求的提交／删除免除再次确认，其他模式和手动页面保留相应确认。实施时同步相关业务文档，不保留“一律人工确认”的冲突约定。

## 验收标准

- [x] 三种模式对同一常规写入、提交和删除产生约定行为，既有角色、来源和对象权限不变。
- [x] 明确写入不重复询问授权；缺信息、权限拒绝、参数错误和批准等待各有正确入口。
- [x] 逐项批准展示真实差异；确认、拒绝和恢复均不重复写入，也不执行未经批准的新内容。
- [x] 单选、多选和自由输入均可续接原任务；不再要求重述整条请求，已完成事项不重做。
- [x] 回答／批准后自动处理后续事项；等待期间释放 worker，不占用超时预算。
- [x] 刷新、断网、多标签页、模式切换、取消、来源修订及删除后，问题与操作状态一致且不串账号。
- [x] 输入框下方工具栏左侧为添加文件、执行权限，右侧为上下文、麦克风、发送／中断；桌面与手机均保持顺序和对齐，录音及发送状态切换不造成跳动。
- [x] 前端回答面板可收起，错误保留输入；桌面／手机及浅深色可用，工具栏、发送／中断和展开状态稳定。
- [x] 定向回归和冻结的小规模真实场景通过；保留失败证据，未通过不能靠重跑筛选为通过。
