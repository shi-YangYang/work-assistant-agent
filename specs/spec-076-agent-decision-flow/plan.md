## 涉及模块

| 模块             | 输入 → 职责 → 输出                                                               |
| ---------------- | -------------------------------------------------------------------------------- |
| 当前任务与上下文 | 用户原话、引用、实际答复、来源版本 → 复用已确认事项及未完成项 → 最小有效任务快照 |
| 主模型与图控制   | 快照、工具事实 → 在原有响应中选择下一步，程序校验流转 → 提问／读取／执行／交付   |
| 工具与投影       | 参数及来源 → 执行必要读取，区分正文、覆盖与错误 → 简短且可核对的结果             |
| 等待与执行       | 有效缺项／明确操作 → 原提问、权限、版本、幂等路径 → 持久问题或真实回执           |
| 收尾与公开反馈   | 状态及真实结果 → 保留未完成边界与引用 → 用户正文、卡片和一致的恢复结果           |

## 修改顺序

1. **冻结基线和用例。** 记录当前 Git SHA、运行源码摘要、模型配置、有效提示与工具投影。基线和候选使用相同脱敏素材、历史、用户答复、业务状态和版本；旧报告只作为问题证据。
2. **定义控制契约。** 清点既有 task snapshot、interaction、tool outcomes、receipt 和 checkpoint 的职责，确定最小状态、唯一写入者、无效化条件与兼容路径。以一个普通问答、一个首轮提问和一个工具读取流程验证设计，不先铺开通用规划框架。
3. **接入图流转。** 复用主模型的现有调用表达决策，在 model/tool 边界落实等待、定向读取、结束探索和必要执行；普通答案可直接结束。检查决策协议是否制造新的往返，若会固定增加调用，调整设计后再扩展。
4. **统一必要工具事实。** 优先处理材料读取、工作查询、网页检索及回执投影；把真实覆盖与语义判断区分，复用已读来源。其余工具经共享边界覆盖，不顺带重写解析器、搜索传输或沙盒。
   以已注册工具集核对结果契约覆盖，并检查原进度控制与新决策控制是否对同一结果得出一致状态。发现单例后按共享规则排查同类任务，不以场景特判作为修复。
5. **移交职责并精简。** 为删除／合并的提示逐项说明由何处程序、工具契约或唯一保留的说明承担。同步精简给模型的封套；完整内部诊断保留，正文证据不损失。
6. **聚焦验证与独立验收。** 先通过相关确定性检查，再跑冻结的真实对照与少量 Web 完整流程；记录未解决项，独立 Agent 验收。本次性能问题不靠重复跑到成功或扩大额度处理。

## 数据流与状态约定

- 最小语义信息包括：当前必要事项、用户缺项、事实缺项、已验证来源／版本、未完成操作和下一步类型。内部命名由实现确定，不新建重复的用户业务任务或要求模型输出长计划。
- 用户来源、工具事实、模型判断分别标记归属。模型判断不能覆盖程序已经确认的失败、版本变化、未执行状态或待回答问题。
- 控制流优先级：取消／权限失效 → 有效等待 → 必要恢复 → 依赖满足的执行／读取／交付。混合任务按依赖项控制，不把单项等待误扩展为其他任务授权。
- 调用前按当前状态筛选可用动作；调用后把真实结果更新到同一任务作用域。并行结果合并不依赖返回顺序，未完成兄弟工具不会被误当作完成。
- “可交付”应携带已有来源依据和未完成项的简短状态；探索关闭后，仅允许有具体新缺口的局部重开。模型一句“再验证一下”不是新的事实。
- 已有首次决策与后续决策均在原有响应中完成；不固定增加独立 planner、充分性评审或问答审核。最终可见内容沿原流式链路发送，不为收束判断强制缓冲完整答案。

## 接口变化

- 优先增加版本化、可选的内部状态及工具投影字段，复用当前 `state/category/recovery`、来源、覆盖与回执语义；先核对消费者，避免同义字段并存。
- 首版不计划新增对用户公开的字段。确需调整公开接口时同步契约与消费者，并补对应兼容检查。
- 旧工具结果没有覆盖字段时保持“覆盖未知”，不能默认完整；旧 checkpoint 无新状态时走兼容路径，不据旧助手自然语言恢复授权。
- 状态更新与既有租约、来源修订及 checkpoint 绑定，取消、重试和接管遵守原任务身份；日志记录原因码、来源标识和实际事件，不记录隐藏思考过程。

## 测试计划

### 风险与范围

文档阶段 S0，不运行业务测试、构建、lint 或 typecheck。后续实施为共享 Agent 执行与持久状态改造，按 S3 验证相关子系统；受控模型用于确定性状态边界，真实模型用于产品行为、准确性与耗时，两类证据分开。

修复前先按 Spec 的归因边界区分系统、模型及未定问题。工具正确返回原文、模型自行过度概括，以及原文引文校验准确拒绝模型改写等已确认模型错误，仅保留结果，不追加修复或真实重跑。输入契约歧义、节点接入缺口、丢失纠错约束及程序固定往返仍继续处理；不能因输出来自模型就免除系统责任。未知原因使用既有记录定位，不自动增加测试批次。

### 确定性检查

- 核对首轮用户缺项、必要查询后的缺项、明确请求直接执行、普通答案直接结束；已足够与被预算截断分别记录。
- 核对来源不足、目录命中、正文截断、图片未读、相互冲突、未完成分页、用户要求全面核对时不能提前收束。
- 核对等待后的探索／写入拦截、答案续接、问题过期、用户换话题、重复请求、取消、重试、worker 恢复和并行工具结果。
- 核对 `ask/auto/full`、越权材料、失效版本、提示注入及真实副作用；新状态不成为另一套授权依据。
- 核对给模型的简化结果与原始结果语义一致，引用可读取，失败不伪装成用户缺项，技术问答不被过滤。

### 真实模型固定场景

所有首轮、工具决策和最终回答必须调用配置的真实模型；禁止由测试脚本预写“成功回复”。历史回放可使用已有脱敏历史，新增文件必须为可读取的真实文件。下列预期只用于验收，不塞进模型输入。

| 编号 | 用户输入与前置                                            | 重点                                                                             |
| ---- | --------------------------------------------------------- | -------------------------------------------------------------------------------- |
| R01  | E00-A 同构历史：“之前的都添加到我的工作里面”              | 先澄清文件／文字／工作事项含义，不先选生成文件并遍历工作；实际答复后准确续接     |
| R02  | E00-B 同构历史：已有拒绝与等待，再发送相同请求            | 不重复探索、重放旧提案或重复建问题；依据当前有效状态澄清或续接                   |
| R03  | 11 份成果、明确工作引用：“把刚才生成的文件都加到这条工作” | 不无谓提问，完整保存正确来源；原附件与其他字段保留                               |
| R04  | “帮我把这句话写得客气一点：资料今天发我。”                | 直接答复，不先加载工具或填写控制表                                               |
| R05  | 真实 PPT：“这份项目方案预算多少、什么时候交付？”          | 两项有据后交付，不读无关材料；另以缺关键页版本验证不臆造                         |
| R06  | 长合同：“这份合同提前解约，要付哪些费用？有哪些例外？”    | 读取相关条件及交叉条款，不能为提前结束漏掉例外或把局部命中说成全文结论           |
| R07  | “帮我找 Python 和 pandas 的官方文档入口，给链接就行。”    | 实际链接与归属足够后停止；真实网络失败单独记录，不假装取得正文                   |
| R08  | 图文混排文件：“这张项目进度图里，哪一项延期了？”          | 图上关键事实必须实际读取，不把文字提取完成当作答案充分                           |
| R09  | 当前周期无真实工作：“帮我生成本周周报。”                  | 沿已有规则说明无可用工作，不生成空报告、不反复探索，也不误判为权限问题           |
| R10  | 已有真实表格：“按部门汇总金额，给我一个 Excel 文件。”     | 输入足够后进入计算／生成，检查真实文件内容和可下载性；不把结束探索当成任务已完成 |

R01/R02 复用 [前一规格的同构场景约束](../spec-075-agent-execution-feedback/plan.md)，保留历史规模、11 份实际成果、原工作及其附件、版本、取消和拒绝的关键关系。匿名数据不等于员工真实意图，报告列出偏差；不为让模型更容易成功而额外提供原场景没有的目标引用。

### 前后对照方式与停止规则

- 修改前后分别冻结源码，隔离数据库／媒体／checkpoint；固定模型与服务、low/high、请求、附件、历史、执行权限和用户答复。冷／热读取、并发及网络环境一致或明确标注；基线不能读到候选刚保存的状态。
- R01～R10 在两档强度下各做一组前后配对；R01、R03、R05 预先固定为性能组，每档共三组配对样本，首次样本计入，采用交替先后顺序。R05 的缺页变体单独一次前后对照，不混入正常耗时组。
- 真实调用数量在启动前按上述矩阵列出，续接回合也计数。单次结果保留，不删失败、不挑最快；其余案例只报告观察，不用一个样本宣称总体提速。
- 已通过的确定性检查不重复跑。真实样本只按预先固定配对计划运行；出现新缺陷先定位修复，再仅补受影响场景，不扩大成无关全量测试。
- 配额不足、网络失败或环境不具备时记录未完成／环境失败，保留原始输出。不得换档、换模型、伪造工具成功或用受控答案填补真实验收。

### 指标与通过条件

| 项目         | 记录与判断                                                                                                                                                             |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 准确性       | 按固定事实与任务要求逐项核对：含义澄清、数量、目标、条件、例外、来源、真实副作用；不能只用模型自评或“回复成功”判断。候选不得新增事实错误、漏项、错误提问或错误提前结束 |

| 总耗时       | 消息接收到最后可见答复／成果；续接耗时单列，排除人的等待时间，同时呈现整个任务的系统处理总时长                                                                         |
| 调用成本     | 主模型和其他模型调用数、工具顺序、失败恢复、token 用量；不以把主模型工作转移给隐藏模型调用宣称减少往返                                                                 |
| 提问及时性   | 首轮即可确定缺项的样本在首轮提问；必要事实查询按预先定义的业务需要核对。禁止用事后“已经零写入”代替及时性通过                                                           |
| 探索收束     | 预先定义用例所需事实，记录实际何时满足；之后无无关探索，必要执行照常完成。不能用候选自报 ready 的时间作为唯一充分性证据                                                |
| 上下文体积   | 实际系统提示、工具 Schema、治理封套、原文分别统计；固定代表路径的治理与重复内容净减少，并保留相同必要事实                                                              |
| 性能回退     | 正常路径不得因设计固定多一个模型回合。性能组总耗时中位数或提问耗时中位数增加超过 `max(3 秒, 基线的 10%)` 时触发分析；这是调查阈值，不据此直接认定代码或网络责任        |

## 风险与迁移策略

- **过早收束：** 以真实缺项、来源覆盖和任务要求约束状态，加入全文／例外／冲突的反向用例；不使用单一 `enough=true` 绕过检查。
- **控制协议变重：** 首先验证普通问答与一步工具路径；复用响应，精简重复封套，禁止固定附加决策回合。
- **状态过期或职责重复：** 明确唯一持久状态与版本边界，复用已有任务／回执；新增字段缺失安全回退，不让旧状态直接触发新写入。
- **精简丢失语义：** 按职责迁移删除提示，按字段投影压缩重复信息；用同材料、同问题检查事实和引用。
- **环境波动误归因：** 冻结输入、交替配对并记录阶段耗时，区分代码路径改变与网络／模型波动。
- 首版不需要数据库 schema 迁移、不修改线上数据。旧任务兼容和回滚以实际内部字段版本为依据；若实施发现必须迁移，先补方案，不擅自改变存储架构。

## 实际控制契约

- 纯读取在原 `awrap_model_call` 返回后、整批工具派发前接收 `resolved={need:[receipt]}`。模型判断哪些具体需求已覆盖及尚缺什么，程序先登记同批全部缺口，再核对实际回执、来源版本与读取范围。未返回调用与未满足需求分开；已覆盖 A 不能压掉同批未覆盖 B。直接正文保持原流式出口，不新增决策工具、模型回合或完整正文缓冲。
- 已声明的全文范围不能被后续局部声明降级；来源变化仅使相关覆盖失效。有效失败恢复及写后读取仍沿原权限／版本边界，普通改写缺口不能成为重开已关闭探索的凭据。省略或无效字段保持旧安全路径，不强制格式纠错。稳定短句只是模型对需求的标识，程序不声称判断了新短句在语义上是否必要。
- 首次工具调用及加载后的首次读取用简短 `route=fact/execute` 与 `need`；有已登记需求的后续读取提供 `need/resolved`，`request_user_input` 本身代表用户选择缺口。预加载工具同样适用，普通直接回答无需填表。字段用于记录及路由，不成为授权或充分性证据；省略／无效的旧调用记为未分类并保留原安全路径，不制造格式修复回合。同批各调用分别记录，不把一项执行意图推广为整批授权。
- `_flow` 的范围、独立事项及恢复含义在共享说明定义一次；已有回执后才提供覆盖与恢复说明，各工具用紧凑对象 Schema 承载。调用前严格检查字段、类型和长度，再剥离后交原工具。原 `ready` 兼容保留，不能代替纯读取需求映射。没有跨角色抵扣输入体积，也不以删原文、条件或参数身份换取提示精简。
- `job.result.decisionFlow` 为版本化控制状态，使用既有租约串行合并。工具 admission、返回和最终正文写入同一状态；来源仍以既有附件／工作版本及回执为准，不复制业务真相。
- `ready` 随必要执行调用携带成功回执 ID，不能证明未读或失效来源；有效时收紧工具可见性。它只影响是否关闭探索，不能变成另一个执行授权门槛：无效、范围不符或来源不全时保持探索开放，当前操作仍交原业务授权、来源和版本检查，不能仅为修复可选标记要求模型再调用一次。挂载已知文件不要求先读完文件内容。
- 回执只绑定该次实际使用的来源与版本，其他材料变化不使它失效。准备好的页面引用不等于已向模型交付像素，工作材料读取与附件读取共用相同事实语义。一次真实失败回执支持必要的局部恢复，工作版本冲突沿既有刷新路径。
- 同批提问默认阻断其他调用，显式独立事项仅在该批次且没有步骤依赖时继续；原授权检查不变。旧等待不能由新标记解除。
- 错误适配保留状态码、机器分类与恢复责任，明确停止／权限拒绝／等待用户优先于通用失败；未知失败不自动开放探索。授权输出拒绝与缺项冲突时仍拒绝执行，仅通过来源与问题有效性检查的缺项进入原提问路径。完整诊断保留在内部，给模型的失败投影不直接带出内部核对理由。
- 实际成功操作产生的新版本／成果可支持对应数据域的后续查询；目录 → 详情 → 翻页共享一次局部读取过程，执行续接或最终答复后消费资格。已使用操作槽与已保存步骤是停止冲突，不与可刷新版本冲突混用。
- 普通问答直接正文结束，程序记录交付但不伪记所有需求有证。没有独立语义充分性裁判，真实模型是否使用读取覆盖契约须分别记录，不把程序边界通过当作所有实际请求都会及时收束。
