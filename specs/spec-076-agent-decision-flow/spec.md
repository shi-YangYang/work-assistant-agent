# Agent 决策流转与上下文：需求

[实施方案](plan.md) · [验收结果](acceptance.md) · [实现与验证](implementation.md) · [问题记录](rework.md)

## 状态

既有系统修复与搜索工具首轮可见的局部调整均已完成独立验收 PASS。纯读取的需求—回执映射已接入原模型响应与工具派发边界；既有授权和恢复保护保留。已确认的迟问、标识误填及回答生成错误按本规格归因边界记录后停止处理。真实样本仍有性能回退，且 v8 四条未触发全覆盖关闭分支，不宣称所有实际任务已保证及时收束或普遍提速。历史失败与当前证据限制见[验收结果](acceptance.md)。

## 搜索工具首轮可见

- 首轮直接提供 `web_search` 和既有公开研究规则；实际调用搜索后，沿任务作用域的能力记忆提供 `web_fetch`。其他能力继续按需加载，是否搜索由原主模型决定。
- 接受用少量固定输入换取联网前少一次工具加载往返。隔离实验首轮 system＋schema 为 5873→6621 字符，增加 748 字符；实际输入增加 214～228 token。这是明确的输入增长取舍，不宣称所有提示都缩短或所有请求都加速。
- 不增加模型节点、工具选择分类器、提示补丁或重试；可见工具仍受权限、等待、预算、探索收束与既有恢复边界限制。公开搜索不发送私人资料，来源规则随工具同轮提供且不重复。
- 16 次既有真实对照保留于 `artifacts/agent-decision-flow/search-preload-overhead/report.md`；正式代码采用同一行为时不重跑该实验，只补工具可见性、规则同步和停止边界的确定性检查及独立验收。

## 背景

Agent 已经可以提问、等待用户回答，并在写入前拦截有效缺项；这些能力不能再次作为新功能重复建设。但“能提问”不等于“及时提问”，“连续探索没有进展后停止”也不等于“材料已经足够时停止”。

[已有验收记录](../spec-075-agent-execution-feedback/acceptance.md)中，同构场景 E00-A 的 low/high 首轮分别在约 66/96 秒后出现提问框，经历 3/4 次主模型调用。此前进行过工具加载和只读查询；这些单次记录说明仍存在前置往返，不证明每次查询都无用，也不是本规格的冻结性能基线。

本次从任务状态、LangGraph 流转和工具契约入手，把“需要用户选择”“需要补充事实”“可以回答或执行”明确区分。同步移除程序已经承担的重复提示，避免用更多说明弥补流程缺口。

## 目标

1. 对只有用户能决定的关键歧义及时提问，减少无法解决该歧义的探索。
2. 对当前请求已有充分依据时及时回答或执行，减少无关搜索、补读和重复核对。
3. 让程序管理等待、续接、探索结束和已完成操作，模型集中处理语义理解与内容生成。
4. 精简系统提示词、工具描述和工具结果中的重复治理信息，保留回答所需事实和条件。
5. 用相同真实用户场景、真实模型 low/high 的前后对照验证准确性与耗时，不用模拟回复证明产品效果。

## 非目标

- 不更换模型、搜索服务、LangGraph／Deep Agents 或数据库，不通过提高额度、延长超时、降低思考强度掩盖问题。
- 不增加独立意图分类、规划、充分性审核或答复润色模型调用，不要求普通请求先填一套完整任务表。
- 不取消现有业务授权、来源、版本、幂等与租约检查；模型自报“可以执行”不是授权。
- 不重做提问框、来源卡或聊天布局，不在用户正文中展示内部缺项清单、覆盖率或读取范围说明。
- 不以固定搜索次数、文件数或 token 数直接判定材料充分，不承诺消除模型误判及网络波动。
- 已确认仅由模型造成的错误不作为本次代码修复目标：模型已收到正确、清晰且必要的材料与契约，仍自行改写引文、过度概括或添加无依据推断时，只记录实际结果，不增加审核调用、案例特判或提示补丁。不降低原有权限、原文及来源校验来容忍错误。
- 不合并关闭上一规格的全部未验收项；旧材料版本与其他运行问题只有直接影响本次范围时才另行记录处理。

## 问题归因与修复边界

- **系统问题继续修：** 节点未接通、必要信息未传到模型、工具描述／结果歧义、错误分类或恢复机制不正确、程序新增固定往返及重复输入，均属于本次范围。
- **模型问题记录后停止处理：** 有实际请求、返回和调用证据确认系统已正确提供信息、原保护正常生效，仅模型输出错误；这类样本保留，但不单独阻塞代码验收，也不重复调用直到答对。
- **原因未定不冒充模型问题：** 模型误填标识不等于工具呈现无责，单次变慢不等于代码回退或模型波动。先检查已有源码、请求与工具记录；没有证据时保持未定，不扩大试验或用长提示补救。由代码造成的准确性或速度退化仍须修复。

## 当前行为

- `agent/harness.py` 通过 `create_deep_agent` 构建图，`runtime/middleware.py` 管理工具可见性、持久等待、回执结束和预算收束。
- `request_user_input` 始终可见；`actions/clarification.py` 消费现有核对返回的有效用户缺项，在实际业务写入前持久化问题。
- `tool_progress` 已有重复调用、分页耗尽、读取复用及无进展控制。搜索当前以连续无新增证据为收束条件，新增链接或正文仍可被计为进展，即使它对当前问题没有帮助。
- `prompts/main.py`、`prompts/evidence.py` 等已要求“证据足够就回答”，部分业务回执支持直接结束；尚未形成覆盖一般任务的需求与证据对应状态。
- 当前任务快照、实际用户答复、来源版本和操作回执已经存在。本次必须复用，避免新建另一个具有授权含义的“计划”。

## 目标行为

普通问答保留直接回复的短路径；需要工具的任务按下面的逻辑选择下一步。这是职责与状态图，不要求每个方框独立调用模型。

```text
用户请求 + 有效历史／引用／实际答复
                 ↓
        现有主模型理解与决策
          ├─ 缺用户选择 → 持久提问 → 等待实际答复 → 补齐缺项后续接
          ├─ 缺必要事实 → 定向读取 → 更新事实与缺项 → 继续决策
          ├─ 依据已足够 → 回答／执行必要操作 → 依据真实结果交付
          └─ 技术受阻   → 既有恢复策略／准确结束
```

“结束探索”仅关闭寻找新信息的阶段，不跳过用户要求的生成文件、修改工作等执行步骤，也不把异步处理中当作已经完成。

## 功能需求

### 1. 最小任务状态与职责

- 按当前用户请求记录必要事项、尚缺的用户选择或事实、对应的真实来源／版本、待执行事项、已完成回执以及下一步类型。只保留控制流程需要的简短信息，不索取或保存思考链、长篇规划和自评。
- 语义识别复用原有主模型响应。工具适配层提供实际读取、截断、失败与副作用事实；程序核对状态一致性并控制流转，不能假装程序可以独立理解任何材料是否充分。
- “需要用户选择”与“需要补读”分开；“材料足够”与“操作已完成”分开；“无进展／额度结束”与“请求已满足”分开。
- 能直接从实际回执判断的完成项不再请模型确认。语义上的充分性由模型结合证据判断，不能把成功 HTTP 响应、目录命中、旧助手总结或模型自报状态当作充分事实。
- 优先扩展现有任务状态与 checkpoint，明确唯一写入者和恢复规则；不能在 job、会话与 graph 中保存互相矛盾的独立真相。

### 2. 及时提问

- 对操作含义、内容范围或目标存在影响结果且无法从有效上下文消解的歧义，使用现有提问框集中询问 1～3 项；不预先替用户选择一种解释。
- 首轮已能确定只能由用户回答的关键缺口，应在该轮提问。不得为了推测用户意图而加载无关能力、遍历工作详情或读取整批材料。
- 必要只读查询仍可执行，例如根据用户明确给出的名称查询真实候选；查询必须能够解决具体事实缺口或形成必要选项，不为把开放问题包装成选项而遍历所有数据。
- 发现有效用户缺项后，程序暂停依赖该缺项的探索和写入。沿用现有问题持久化与等待路径，不额外调用模型改写问题。
- 实际回答后保留已确认目标、材料选择和完成项，仅续接未完成部分；目标或来源发生变化时局部失效、重新校验。已经明确的请求、普通写作细节和用户委托自行决定的事项不机械追问。
- 技术故障、模型漏参数、版本冲突和权限拒绝不冒充用户缺信息；用户改变话题或取消后，不自动恢复旧任务。

### 3. 及时结束探索

- 每次继续探索应对应尚未解决、会影响当前答案或执行的具体事实缺口。新增链接或新材料仅表示数据变化，不能自动证明有必要继续探索。
- 材料已覆盖当前请求，且不存在影响结论的未解决冲突、必要执行前提时，形成明确的内部“可回答／可执行”信号。模型接收简短状态，程序将路径切到交付或必要执行，关闭不再需要的探索能力。
- 例如“预算多少、什么时候交付”：两项有明确原文依据即可回答，不再为了解整个项目遍历附件；“找官方入口链接”：实际链接及归属证据足够即可交付，不默认读取整站。
- 用户要求全文检查、多来源比较、指定数量、最新资料或核对事实时，这些属于任务要求，不能以已找到局部答案提前结束。
- 目录、未读取的链接、截断内容与局部命中不能冒充全文覆盖；证据冲突仍须处理或在结论中保留准确的不确定性。
- 进入交付／执行后，只有具体新证据、版本变化、执行结果暴露的必要缺口或用户新增要求才能重新打开相关探索；模型重复说“再确认一下”不能自行解除已确定的状态。
- 复用原有无进展与预算兜底。无法补齐关键事实时允许交付有边界的结果或说明未完成，不强制继续直到额度耗尽，也不把未完成包装为成功。

### 4. 提示词与工具结果精简

- 建立现有规则的职责归属：由程序保证的等待、重复执行、恢复和状态限制，删除多处重复的自然语言说明；仍需模型理解的语义边界保留一处清晰规则。
- 系统提示词保留目标、必要业务边界和“何时问、何时查、何时交付”；能力说明按需提供，不为此次改造叠加长篇决策协议。
- 工具描述说明用途、关键参数和结果含义，去掉重复教程；工具结果按实际需要提供事实正文、来源与版本、覆盖／分页、结构化状态及必要下一步。
- 完整诊断、调用栈、内部授权推导和重复回执放在既有诊断渠道。面向模型的投影和面向用户的结果分别处理；不能只在页面隐藏，而继续把同样冗余信息反复传给模型。
- 保留关键事实、原文条件、例外、表格关系、失败类型与有效来源。不能统一截断原文、强制摘要或隐藏未读部分来换取体积下降。
- 多轮复用稳定来源和已验证回执；只有模型仍可按有效标识读取或恢复时，才省略已经交付的重复大段内容。
- 精简前后记录实际系统提示、工具 Schema、状态封套与工具结果的字符数、字节数及可获得的 token 用量；区分治理说明和业务原文。与流程无关的人设重写、模型更换不混入对照。

### 5. 用户体验与可观测性

- 问题出现后用户能立即回答；刷新／重连保持同一有效问题，已回答的问题不会再次执行或重复写入。
- 正文直接回答用户问题，来源沿用引用卡；不展示内部“材料已足够”、需求覆盖清单、决策 JSON 或控制指令。
- 记录任务阶段、实际工具顺序、来源变化、问题可用时间、必要信息齐备后的额外调用及结束原因，沿用既有诊断能力，不增加员工诊断页面。
- 单独记录排队、主模型、其他模型、工具、恢复和前端可见耗时；不能把所有等待称为模型思考，也不能把服务端问题落盘时间当作浏览器显示时间。

## 边界条件

- 同一消息包含多项请求时，只对依赖缺项的部分等待，独立部分按现有授权处理；不能遗漏后续事项或反复重做已成功部分。
- 用户答复、引用及来源均按账号、公司、会话、输入修订和当前任务隔离；材料正文不能修改任务状态或获得写入权限。
- 处理取消、超时、重试、worker 重启、并行工具返回与版本冲突；过期返回不得覆盖较新的用户选择或重新打开已取消任务。
- 不能把一批工具中某个完成当成整批任务完成，也不能因另一个工具失败而丢失已经成功的证据或操作回执。
- 对工具目录加载造成的无效往返同步检查；可以复用有效上下文预备必要能力，但不全量展开全部 Schema，也不通过关键词硬编码用户意图。

## 技术约束

- 保留既有模块边界和业务权限检查，优先在 `agent/runtime`、现有任务状态和工具投影内实现；不重写框架，不建立第二个通用规划系统。
- 结构化控制信息应随原有模型响应或工具调用携带，支持直接答案；不能变成“调用决策工具 → 多一次主模型调用 → 才执行真正工具”的固定开销。
- 新控制字段不受支持或返回无效时，保留既有安全路径和有界恢复，不能让普通问答全部增加格式修复调用或静默跳过必要检查。
- 当前文档工作按 S0，只核对内容、diff 和引用；实施涉及共享执行与持久化状态，按 S3 执行相关 Agent 子系统验证，不默认运行桌面、发行包或整个仓库测试。
- 实施按一个实施 Agent 串行处理耦合改动，再由新的独立验收 Agent 验收。生产环境和现有员工任务不变，不自动 commit、push 或部署。

## 兼容性要求

- 保留 `ask/auto/full`、既有提问框、业务回执、来源卡、SSE 与历史读取语义。
- 旧任务和 checkpoint 缺少新状态时安全回退；不能推断为“材料足够”或重放旧写入。实际用户答复仍从原 HTTP 入口建立有效来源。
- 优先使用既有持久化字段的可选版本化扩展；不预设数据库 migration。如确需数据库或公开 API 破坏性变化，实施前更新方案并确认影响。

## 验收标准

以下语义和性能标准按上述归因边界验收：保留模型失败观察，不要求通过代码消除已确认的纯模型错误；系统缺陷、实现缺口和由改动造成的回退仍为阻塞项。

- [ ] 明确可在首轮发现的用户歧义在首轮提问；需要真实候选的场景只做必要查询。无写入后才补问、用不相关材料猜用户意图或强加解释。
- [ ] 已明确请求及普通问题不新增无谓问题或固定模型回合；真实回答能准确续接，刷新、取消及重启不会重复写入。
- [ ] 已满足当前需求时停止无关探索；保留用户要求的执行、完整检查和多来源比较。新增但无关的资料不能无条件延长探索。
- [ ] 必要事实缺失、截断、冲突、来源失效和操作未完成不会被错误判为充分／成功；引用可用，答案保留关键条件与例外。
- [ ] 新控制状态与真实读取、有效用户来源和操作回执一致；无权限降级、跨账号串用、漏保存或重复执行。
- [ ] 固定代表场景中，治理提示及重复工具封套总体净减少；没有依靠删除关键事实、一次性交付缩短或隐藏错误达标。
- [ ] 同一冻结用例和素材分别进行修改前后 low/high 真实模型对照，交付真实回复、问题、调用顺序、准确性和耗时；未测及失败如实记录。
- [ ] 及时提问与收束目标按 Plan 的过程指标核对，正常路径不出现设计引入的固定额外模型调用；性能回退按预设门槛分析，不以单个最快样本宣称提速。
- [ ] 相关确定性测试、真实 Web 完整流程及独立验收通过；Spec 075 尚未覆盖的无关问题继续单列。

## 待确认问题

无阻塞性产品问题。实现中的内部字段与路由形式可依现有框架细化，但必须遵守“复用模型调用、程序控制流转、精简重复说明、保留必要事实”的约束。
