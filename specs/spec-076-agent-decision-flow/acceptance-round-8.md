- **充分性与权限边界保留。** 语义对应关系仍由模型判断，程序校验真实成功回执、来源版本和覆盖范围。目录、未知／准备中内容、失败及部分内容不能满足全文要求；同批尚缺 B 不因已覆盖 A 被吞掉，全文要求不能降为局部事实。实际版本变化只清除对应需求的依据；真实失败恢复、工作冲突刷新及写后查询继续受原边界控制。新状态不授予写权限，不绕过来源、幂等或租约。

## 契约与真实样本归因

实际提供给模型的 `_flow` Schema 是 `object + required`，并未在各工具重复详细属性；它本身不保证提供方输出合法。验收同时核对真实系统消息与工具结果，不能只看这个 Schema：后续请求明确收到 `resolved={已覆盖need:[实际receipt]}（无则{}）`、复用 need 的规则、当前 missing 列表和真实工具 `_flow.receipt`。服务器只接受符合结构且可验证的回执，非法值不关闭探索。

- **R06 low：** 第二次请求确实使用真实 `be05c7de9ebd1dc7` 回执覆盖“合同结构与全文要点”；另一个自行改名的需求键未被采纳。证明真实模型可以进入需求映射入口，不能证明全部需求关闭。
- **R06 high：** 请求中已提供上述映射形式与实际回执；模型却填写条款文字、未登记键或空数组。**R07 high** 把映射值填成“搜索得主页……需确认 docs 入口”的说明字符串。它们违反已提供的形状与身份语义；本次未发现信息未传达、相反工具说明或服务器误拒绝合法回执的证据。通用 object Schema 的宽松程度不等于这几项实际错误的已证实系统原因，不要求为这些输出增加提示补丁、审核或重跑。
- **四条真实样本均未触发 `requirements` 全覆盖关闭或 `need_covered`。** 两条 high 的无效字段安全回退，R07 low 直接正文，R06 low 只覆盖一项。全覆盖、同批拦截及恢复的证据来自确定性检查；不宣称它们已经由真实 low/high 模型触发，亦不宣称已保证所有实际任务及时收束。
- **迟问归因可复核。** 原始 8 个 R01/R02 首轮请求均为 `toolChoice=auto`，均已提供提问工具及“不必先加载／查询”的明确说明；7 次先加载是模型选择。R03 low sample1 首次写入请求实际含完整 `materialSource` 和独立 `messageId`，提交的 11 项中 9 项错用消息 ID；原校验拒绝后修正。上述具体样本可按模型错误保留，不能泛化到未来所有迟问或 ID 问题。
