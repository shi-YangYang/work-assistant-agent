# Plan

## 对应 Spec

[工作勾选清单与轻量 Agent 操作](spec.md)。本文件定义实施范围，实际验证结果由验收文档记录。

## 涉及模块与数据流

- 工作正文：仍以 `WorkDocument` 为唯一内容源，补齐清单项稳定身份与确定性的简便编辑操作。
- 保存事务：沿用 `RecordPatch` → `mutate_record` → `save_work`，共享版本、幂等、权限和历史记录。
- Agent：已有读取工具返回当前正文状态，已有 `execute_business_action` 接收简便编辑；不新增模型阶段或工具发现要求。
- Web：详情只改变被点项的状态；编辑模式继续编辑完整文档，使用现有提交、冲突恢复和错误展示。

手动勾选：项编号＋目标状态＋工作版本 → 现有 PATCH → 权限／幂等／版本校验 → 单次事务保存 → 返回新正文与版本。

Agent：原始指令 → 必要时读取当前工作 → 当前执行权限与授权范围校验 → 简便正文操作 → 同一保存事务 → 真实回执。新建整批清单仍是一次 create_work；已有工作整批追加仍是一次 update_work。

## 接口方案

优先扩展已有 `bodyEdits`，保持工作字段仍归属 `body`，避免增加独立 checklist 实体和新的权限字段：

```json
{
  "bodyEdits": [
    {
      "action": "append_checklist",
      "items": [{ "text": "收集周报" }, { "text": "打印简历" }]
    }
  ]
}
```

- `append_checklist`：一次追加一组平铺事项；可选 `checked` 默认为 false。不带 `blockId` 时新建清单块，带编号时必须指向当前工作已有的顶层 `taskList`，向其末尾追加并保留原项身份与状态。程序生成节点及标识，仅在用户明确说明完成事实时允许传 true。
- `replace_checklist`：携带已读顶层 `blockId` 与事项，用于用户明确要求把指定普通块整理成清单；不能替代追加，也不能作为单项勾选的途径。已有带状态的清单重排／改文案仍走保留项编号的正文编辑，不整体再生编号。
- `set_checked`：`{action:'set_checked', itemId:'已读编号', checked:true}`，递归找到当前工作中的唯一清单项，只改布尔状态。可选 `blockId` 只作附加归属约束，必须是真实顶层清单且包含该项，不能忽略错误块编号。可以同批指定多项，全部校验后原子写入。
- 备注、标题和其他正文仍使用现有节点和块操作，与清单在同一次写入中保存；不再复制一个同内容的“下一步”字段。
- 各 action 按可识别的 Schema 校验必需字段、禁止多余字段、限制数组与文字长度；禁止同时替换整个 body 和应用 bodyEdits。同批重复／相互矛盾的目标拒绝，不能后者默默覆盖前者。
- 创建时允许 append_checklist；replace/set_checked 必须存在对应的已读对象。所有操作继续受文档总节点数和字节上限约束。
- 回执、预览及授权输入展示实际项文字和状态变化；映射到现有 body 变更范围，不能绕开已有核对，也不增加新一轮核对。

稳定编号由正文领域函数维护。旧记录读时产生确定性兼容标识，写时固化；必须验证同一版本重复读编号一致、读取不写库、复制和重复编号处理。不能依赖列表位置作为永久身份，不能因为返回兼容编号就声称旧历史已迁移。

清单勾选的目标范围由既有工作变更范围调用同时提取：只看原始用户指令、当前工作及其分组，返回明确的项编号与目标状态，或指出歧义；不提供主助手拟选项，也不新增模型调用。纯勾选请求完全匹配已验证的选择时，以该选择形成当前操作的正文变更范围，避免旧 `body=preserve` 重复表示产生矛盾。原始计划缓存保持不变，混合正文修改和全篇替换不能借用这一范围。普通操作保留原有 Schema。

## 修改顺序

1. 在任何业务修改前冻结基线 SHA 与独立代码快照，再冻结合成案例、模型配置和验收口径。基线 API／worker 仅导入快照，候选仅导入对应候选版本；独立运行环境允许实现与取证并行，仍按冻结顺序进行配对采样。
2. 实现清单项标识及局部编辑纯函数，补齐 Schema、原子校验、旧数据兼容和无变化保存行为。
3. 接入现有 REST／Agent 保存、授权预览、回执和历史描述；核对 bodyText、工作引用、报告来源中勾选状态的表达，不新增全量正文副本。
4. 接入详情勾选交互；编辑器生成／复制项时维护标识，保护未保存正文、材料和光标／滚动位置。
5. 精简工作工具说明，新增格式说明替换重复内容；不扩写全局提示或增加推理阶段。检查明确清单、普通正文、歧义和旧写法兼容。
6. 执行相关确定性回归、UI 检查与冻结的真实模型对照；遇到具体缺陷再修复、定向复验。
7. 新的独立验收 Agent 审查 Spec、diff、数据和测试证据；如实交付未验证项及性能限制。

## 测试计划

文档阶段 S0，只检查 diff、需求一致性和引用。实施涉及 API 与持久化，按 S3 验证工作／Agent 相关子系统，不默认运行桌面、沙盒或全项目套件。

### 确定性检查

| 类别 | 必须覆盖 |
| --- | --- |
| 文档 | 新建、追加、指定块转换、修改文字、重排、复制、旧项编号、保留材料和已勾状态 |
| 写入 | 勾选／取消、同值无变化、多项原子更新、版本冲突、同键重试、无效／重复／跨工作编号 |
| 权限 | 本人、他人、管理员查看员工工作、历史版本、三种执行权限、等待确认时内容变化 |
| Agent | 完整生成多项、备注与计划不冒充完成、整批单次写入、读取未完成、歧义、复合事项局部完成 |
| 兼容 | 旧 body/bodyEdits、普通正文、纯文本出口、已有确认卡、工作引用与相关报告来源 |
| UI | 点击／键盘／触摸、保存中防重复、失败恢复、编辑草稿与即时勾选隔离、长文本与修改记录 |

### 真实模型质量与耗时对照

仅测试 low、high 两档，不测试 max 或其他档位。每档的基线与候选使用同一服务商、模型、思考强度、执行权限、人格和网络出口；不通过降档获得提速，不混合两档统计，也不以 low 结果替代 high。环境由现有验收工具创建并声明资源归属，不连接生产；不改用户日常模型配置。基线与候选 API／worker 必须来自各自已确认代码版本，记录进程与版本，避免旧 worker 干扰。

每档对以下四组配对单轮案例各采集三对，按 A/B、B/A 交替顺序；每档 24 次用户请求，两档合计 48 次：

1. 普通知识问答：不调用工作工具。
2. 普通工作说明保存：不强制清单化，不丢正文和材料引用。
3. 明确保存 17 项待办，混合备注、时点与复合事项：同一份合成输入，逐项核对完整性和条件；候选必须真的生成可勾选项。
4. 对已有等价工作补充一批事项：检查既有状态、文字与材料保留，批量追加无逐项工具循环。

候选在 low、high 两档各执行以下两条多轮流程：

- 新建 → 用户手动勾选一项 → 聊天查询未完成 → 明确标记另一项完成 → 取消勾选 → 再次读取；逐步检查数据库真实内容、版本与回执。将同名项、过期项、同键重试的破坏性情形交给确定性测试，不依赖实模碰巧触发。
- 复合事项只完成前半段、两条同名事项和普通完成描述：验证不误写；明确完整对象和更新指令后才修改。

质量记录：项数与原文逐项对应、实体／数字／时点／条件、已完成与未完成、备注保留、非目标字段差异、重复调用／写入、最终回答是否与真实结果一致。判定由固定断言和人工审查完成，不在线增加一个评分模型。普通正文降级保留可用性，但清单成功率必须计为失败，不能混入成功样本。

计时至少记录：请求开始、API 接收、首段非空正文 SSE 到达、任务完成、模型／工具调用数、token 和错误。HTTP/SSE 计时不冒充浏览器实际绘制；新增流程和普通问答各选一例记录浏览器首字与最终完成可见时间，检查流式展示未被阻塞。

每档每组分别报告原始三对结果和中位数，不用少量样本宣称稳定 P95 或总体准确率。相同档位内，首字或总耗时中位数同时增加超过 20% 且 2 秒时进入排查；应用增加处理阶段、无必要模型调用、逐项循环、遗漏／改意／误标或重复写入均为返工项。怀疑网络或服务商波动时最多对该档异常组追加一次反序三对，保留首次结果；仍无法归因则记录“性能结论不确定”，不得宣布无退化或不断测到通过。

现有 `assistant-latency.py` 仅接受 spec055/spec056 归属声明，不能伪造旧套件绕过限制。需要扩展时只显式登记本次套件，保留精确环境所有权、失败留存和禁止覆写证据规则；环境创建／装配的对应校验同步扩展并在实际目录树记录。不为本次测试重建通用评测平台。

## 风险与处理

- 格式正确不等于语义正确：明确区分程序可保证的节点／权限／原子写入，与需要实模测量的识别、保留和指代质量。
- 保存字段虽沿用 body，但新操作必须贯穿授权、预览、回执、历史及报告来源检查，不能仅修改前端显示和最终写入。
- 兼容编号与并发可能导致误定位：先校验版本和真实项归属，不做模糊匹配或自动覆盖。
- 降级容易掩盖失败：只接受完整普通正文并如实反馈；不能算可勾选清单成功，不用无限修复调用维持成功率。
- 提示词和输出结构可能增加耗时：保留普通路径，对照测量并记录 token、调用数，不承诺完全零变化。

## 迁移策略

不新增数据库表、不批量转换历史正文、不修改历史快照。旧清单编号读时兼容、首次实际保存固化；旧普通正文仅由用户主动整理。部署服务与 CD 无预期变更。

回滚业务代码可继续显示既有 Tiptap taskList；新增编辑请求需要匹配版本的 API。发布前验证旧正文和旧客户端请求兼容，回滚时不删除已保存的清单数据。若发现不可兼容的迁移需求，先更新 Spec 决策再实施。
