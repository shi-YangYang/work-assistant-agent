# Web 前端模块化与可维护性重构

状态：已完成；[独立验收通过](acceptance.md)。

## 背景与目标

Web 前端已覆盖聊天、工作、报告、团队和多种设置，但功能主要平铺在 `apps/web/src`。当前 `ModelServices.tsx` 1376 行、`Assistant.tsx` 1214 行、`Records.tsx` 965 行、`App.tsx` 704 行，`styles.css` 4813 行。行数不是唯一问题：页面、请求、状态、副作用和不同业务的 UI 混在一起，增加理解与审查成本。

已有 `useResource`、分页状态、草稿隔离及通用控件，应保留有效能力并明确归属。例如 `api.ts` 混合传输、Hook 与日期工具；`Records.tsx` 同时容纳工作和报告，并从聊天模块引用工作表单；`ui.tsx` 同时依赖请求与工作空间状态。

目标是让开发者沿“页面 → 功能 Hook／组件 → 业务 API → 请求客户端”定位行为；修改一种业务时，主要在对应模块完成。成功条件是职责和依赖清晰、既有行为可验证，而非仅移动文件或把大组件变成大 Hook。

## 范围与非目标

- 本次聚焦整个 Web 前端，覆盖当前所有页面、公共 UI、请求层、Hook、纯函数、状态归属和样式组织；同步受影响的前端测试、构建引用与开发说明。
- 保留现有视觉、中文文案、响应式行为、HTTP 协议、权限与数据语义。原有问题如不由此次拆分引入，另行处理，不夹带产品改版。
- 不重构 Electron、Python API／worker／harness，不迁移数据库，不改 CI／CD 的触发政策或生产环境。
- 沿用 React、React Router、Vite、现有 CSS 与 npm；不为目录标准化引入 Next.js、Redux、TanStack Query、组件库或新的表单框架。
- 根目录的 apps／services／packages／tests 以及 Agent 文档结构保持原职责，当前跨端共享包继续复用。

## 目录与依赖方案

采用按业务组织的模块结构，结合薄页面和公共基础层。参考 [Bulletproof React 的目录实践](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)，不将其视为 React 强制标准，也不照搬全部目录和依赖。

```text
apps/web/src/
├── app/                    # 应用装配、路由表、Provider 装配、布局与导航
├── pages/                  # 路由入口，读取路由参数、组合功能模块
├── features/
│   ├── assistant/          # 会话、消息、编辑器、附件、录音、业务操作卡
│   ├── work/               # 工作列表、详情、表单及进展建议
│   ├── reports/            # 报告、来源、提交与汇报待办／通知
│   ├── team/               # 团队筛选、统计与结果列表
│   ├── members/            # 成员管理
│   ├── model-services/     # 服务编辑、模型目录、用途分配及用量
│   ├── auth/               # 登录、钉钉流程与配置、桌面授权
│   ├── settings/           # 账户、外观、汇报规则
│   ├── voiceprints/        # 声纹管理
│   └── feedback/           # 问题反馈
├── api/                    # 传输客户端、错误、请求身份代次与流式连接基础
├── components/             # 公共 UI；复杂业务不因被复用就变成基础控件
├── hooks/                  # 真正跨业务复用的 React 逻辑
├── lib/                    # 会话上下文等基础设施、非 React 资源控制器
├── utils/                  # 无业务状态、无请求副作用的通用纯函数
├── styles/                 # 全局基础样式与共享控件样式
├── assets/
├── main.tsx
└── index.html
```

- 功能模块按需要包含 `api/`、`components/`、`hooks/`、`utils/` 和样式文件，不机械生成空目录。组件 PascalCase，Hook 使用 `useXxx`，其余模块使用有含义的 kebab-case 名称。
- `app` 装配 `pages`，页面组合功能模块；公共基础层不能反向导入页面、功能模块或应用装配。纯工具不导入 React、网络客户端或工作空间。
- 跨业务组合优先放页面层。例如团队详情由页面组合团队筛选与工作／报告详情，工作模块不再依赖聊天页面。确有业务复用时，通过明确的具体组件／API 导出单向依赖，不导入其他模块内部实现；不建立循环依赖。
- 工作表单归 work；报告展示归 reports；读取来源、任务反馈等真正跨业务能力拆成职责明确的公共模块。基础控件不主动查询工作、修改身份或读取聊天草稿，改由上层传入数据／回调。
- 使用 Web 局部 `@web/` 路径别名并同步 Vite、TypeScript、Vitest；不改成整个仓库通用别名。直接导入明确文件，不用根级 `index.ts` 汇总所有模块掩盖依赖。
- `packages/api-contracts` 保留服务端 DTO 类型；组件 props 和模块内部状态就近定义，不复制一套 HTTP 类型。

## 拆分与复用要求

### 页面和组件

- App 拆出身份初始化、路由、应用布局、侧栏、顶部导航、命令入口及 Provider 装配。路由和导航元信息有明确来源，保留旧 URL、深链接、查询参数、返回位置及角色入口。
- 聊天拆出会话选择、消息列表／消息卡、输入编辑器、附件区域、录音控制、转写修正、任务状态及业务操作卡。每个异步流程有唯一状态所有者，不在两个组件间复制一份可变状态。
- 模型服务拆出服务列表、服务编辑、模型列表／手动添加、推理预设、连通性测试、用途分配和用量。编辑草稿、配置版本与未保存离开保护共同受一个明确的编辑状态管理。
- 工作和报告分开，列表、详情、表单、来源、删除／提交等边界独立；其余设置页、钉钉页、预览和声纹页按相同原则整理。
- 页面只做路由适配和组合，业务组件按用户可理解的功能单元拆分。复杂状态可使用领域 Hook 或 reducer，但不得把原页面整体塞进一个返回几十个字段的 Hook。
- 业务 TSX 超过约 350 个非空行时必须检查职责；这是本项目的审查提示，不是行业强制值。不能通过压缩换行、改扩展名或无意义拆碎来满足长度目标。原有千行页面的主要独立职责必须实际拆开。

### 请求、Hook 与工具

- `api/` 保留唯一 HTTP 请求实现，集中管理 CSRF、会话代次、取消、超时、错误分类和诊断。传输客户端不依赖 React。
- 每个业务的端点、参数和返回类型在其 `features/<业务>/api/` 中定义；页面和展示组件不散落端点字符串或直接 fetch。SSE 和二进制读取复用同一身份／错误规则，不另建绕过请求层的客户端。
- `useResource`、`usePagedResource`、分页筛选等保留各自有意义的职责，抽离 React 接口与非 React 控制器；不强行统一为一个带大量开关的万能 Hook。
- 发送消息、录音、会话恢复、模型编辑等业务 Hook 留在功能模块。日期格式化、时区展示等纯函数放 utils；上传大小和类型规则留在附件业务，避免全部丢进通用 utils。
- 抽取已有重复或清晰独立的逻辑，不为几行 JSX、单次简单事件或每个 useEffect 建抽象。遵循 [React 的 Custom Hook 指南](https://react.dev/learn/reusing-logic-with-custom-hooks)，Hook 复用逻辑不代表共享状态，避免 useMount 等生命周期包装。

### 状态、样式与长期约束

- 明确区分请求身份／用户、跨页面草稿、服务端资源、URL 筛选和局部 UI 状态。Provider 的装配位置与状态定义分开，功能模块不反向引用 app。
- 保留登录失效和跨账号草稿隔离；退出后的延迟上传／请求／录音回调不能重新写回旧状态。切换页面与功能拆分不额外启动订阅、录音或轮询。
- 按全局基础、公共控件和业务分拆 styles.css，由应用入口确定稳定加载次序。先保留现有选择器和层叠顺序；跨模块选择器明确归属，不能因路由加载先后改变样式。继续使用共享主题和选择控件 CSS，不借机换视觉体系。
- 把目录、依赖、命名和新增功能的放置规则补入现有架构文档，并在 AGENTS 中引用。用现有 ESLint／TypeScript 能力提供反向依赖和循环依赖的轻量检查，不只靠口头约定。
- 文档附一条新的“发送消息”文件路径，帮助开发者沿真实流程理解；不新增重复的长篇治理文档。

## 兼容与风险边界

拆分不能改变消息幂等键、请求是否自动重试、录音暂停／释放、附件 URL 生命周期、原始材料权限、模型配置快照、版本冲突、提交／删除确认、搜索防抖、分页顺序和错误提示。不能因为前端整理而要求现有用户重新登录、清缓存、重建账号或修改服务配置。

迁移期间允许短期兼容导出，最终移除旧路径适配层和无调用代码；只有证实无引用、无动态访问、无样式依赖时才能删除。原始资料、环境文件及模型资源不在清理范围。新路径仍使用原构建输出和部署入口，风险与分步回退见 [实施计划](plan.md)。

## 验收标准

- [x] 所有 Web 页面有清晰入口；App、聊天、模型服务、工作／报告等大文件完成职责拆分，开发者能按功能找到组件、请求和 Hook。
- [x] 请求层不依赖 React，公共 UI 不依赖业务页面；无内部实现跨域乱引、反向依赖或新增循环。工作表单不从聊天模块导入。
- [x] 既有 HTTP 类型、身份隔离、取消／超时／重试、SSE、草稿、权限失效、冲突处理和异步清理语义保持一致，有相关行为回归证据。
- [x] 电脑／手机宽度下，登录、聊天与附件、工作／报告、看板和设置页面无布局／导航回退；关键键盘与弹窗行为保持。
- [x] Web 前端全量测试、类型、Lint、格式和普通构建通过，并在本地检查关键页面与操作；不以只检查导入路径或源文件字符串替代关键行为验证。
- [x] 旧路径、临时兼容层和失效引用清理；架构说明和开发约束与实际目录一致，未夹带后端或 Electron 重构。

## 范围边界

只重构 Web 前端；保留既有功能、UI 和技术栈。完成后执行 Web 前端全量验证，Electron 和后端不纳入本次重构。
