# 实施计划

## 范围与风险

实施涉及 Agent 共享收尾、持久任务状态与操作结果，按 S3 验证相关后端和 Web 子系统；不默认运行 Electron、打包或整个仓库测试。

由一个实施 Agent 串行完成耦合模块，完成后由新的独立验收 Agent 审查。

## 模块边界与数据流

```text
当前请求＋可访问历史／材料
  → 现有 Agent 循环：分析、读取、执行、观察工具结果
  → 主模型 finish_task：正文＋任务摘要＋结果引用
  → 服务端：来源／结构检查，汇总回执与阻碍
  → 普通回答直接交付；业务结果或明确核验任务按需专项核对
  → 持久化正文与 taskOutcome，更新任务上下文及现有反馈
```

### 收尾契约

- 在 `delivery.py` 定义单一内部结构，包含版本、正文、现有 `TaskInterpretation` 兼容投影和业务结果引用；不建立新的任务状态机。
- 使用现有工具调用通道提供 `finish_task`，主模型在正常最后一轮提交正文和摘要，执行后直接结束图，不再调用模型复述工具结果。无需新增供应商专属 JSON 模式。
- 该工具只提交本轮答复与任务解释，没有业务写入、权限修改或确认能力。正文中的命令和模型给出的成功标记均不能执行操作。
- 终止工具不得与未完成业务工具在同批提前收尾；等待问题、待确认卡与纯回执快捷路径也归一到交付结构。
- 无效结构仅按现有节点机制有界修复。普通正文未按新协议返回时，保留候选并走有限的协议恢复；不能静默当成功，也不能回退为每条答复的逐段审核。

### 分流与专项核对

- 分流使用本轮任务摘要、工具尝试、实际回执、临时问题和明确核验要求，不调用独立分类模型，不根据新闻主题或固定说法硬编码例外。
- 查询、写作、分析走直接交付；真实业务执行回合核对结果陈述和请求覆盖。识别依据包含执行意图及失败尝试，不能以无成功回执为由绕过缺失操作检查。
- 收尾元数据是模型解释，不是授权或成功证据。访问控制始终在工具和持久层生效；业务陈述与回执冲突时不能让模型选择性忽略回执。
- `reply_review.py` 接收具体核对范围，返回问题、引用及待修正项；去掉全篇段落编号、支持关系和“额外内容”过滤。不得叠加一套默认全篇审核兜底。
- `response_repair.py` 只修明确问题，不执行写入；遗漏操作仍交回现有 harness，并使用原回执、步骤标识、阻碍和持久修复标记防止重做。
- 收尾修复与内容修复共用可记录的有限额度，禁止两个路径互相重置或各自循环放大。暂时节点故障仍遵循现有最多三次重试规则。

### 状态与历史

- `handlers.py` 负责装配，`delivery.py` 管交付，`outcomes.py` 管结果；不要把已拆出的规则重新堆回 handler。
- 普通回答的有效正文可完成；需要用户决定、工具受阻、确认未点击或报告未结束时，使用对应实际状态。语义层面的任务覆盖由主模型负责，业务真实性由服务端约束，不声称结构校验能够证明任意文本完全正确。
- 新协议版本进入候选正文与收尾缓存的指纹，不能复用旧逐段审核结论。旧 `pendingReply` 可作为恢复候选，已成功业务回执继续复用，不能重新执行整项任务来迁移缓存。
- 既有 `ConversationTaskState` 保存通过来源校验的解释；取消、换题、工作引用、澄清和旧消息重试继续受版本控制。

## 接口、迁移与兼容

- HTTP／SSE 保持原 `reply`、`taskOutcome`、`nodes`、结果卡和错误字段；不新增必填前端参数或设置选项。
- 新交付数据放入已有 Job JSONB 和受保护检查点，带内部版本；预计不新增表或 migration。
- 历史回复不改写，历史节点正常显示。新任务只发布实际发生的核对节点；前端仅在现有呈现不兼容时修改对应组件并同步目录树。
- 保留三种权限、两种人设、语音／附件、上下文压缩和手动重试能力。自主执行仍受真实用户授权与角色权限约束。

## 实施顺序

1. 固定新闻误删、多轮切换、业务假成功、部分完成和恢复去重的行为样本，核对已有未提交修复，保留有效用例。
2. 接入主模型收尾和内部交付契约，将任务状态更新从正文审核中解耦；先验证旧检查点、持续指令与报告交接。
3. 移除普通路径的固定审稿，将必要业务核对、正文修复和缺失操作恢复接入统一交付入口。
4. 精简提示，清理失效的通用裁剪逻辑、测试协议和文字，验证节点、SSE 与刷新表现。
5. 完成定向回归、真实模型样本和独立验收；如实记录未通过项，不以降低断言换取通过。

## 验证计划

- **确定性子系统检查**：运行新交付测试及已有正文、操作、任务上下文、权限、临时问题、联网、成果、引用、中断、重试和恢复相关测试。先定位耦合点，按行为选择文件，不默认跑全部后端。
- **关键故障**：无效收尾、只有承诺而没有结果、虚构操作成功、工作状态与操作状态混淆、专项核对失败、读取失败、内容拦截、重启后续接、旧缓存和来源撤销。
- **Web 检查**：运行现有任务进度与 JobNotice 定向测试；浏览器观察普通回答、业务执行、部分完成和重试，验证节点与正文一致。若修改 TS／TSX，格式化改动文件并执行相关 lint／类型检查。
- **真实模型评测**：复用 `scripts/benchmarks/agent-evaluation.py` 与隔离测试数据，准备 12 类场景、管理员与员工共 24 个样本，包含单轮与多轮；措辞不复刻提示示例，不用真实业务数据制造写入或删除。
- 场景覆盖：闲聊、自由拟写、材料分析、公共搜索、资料不足、引用后换题、自然追问、方案连续修改、明确入库、多动作加解释、确认／缺信息、失败后恢复。权限组合和故障穷举以确定性测试覆盖，避免重复耗费真实调用。
- 记录每例的用户请求、可见答复、来源、实际业务变化、终态、审核调用次数与耗时；比较普通路径是否移除固定审核。不把供应商故障当产品通过，也不承诺固定秒数或绝对成功率。
- 验收 Agent 检查行为和结果，不只采信 LLM 评分。已有检查通过且代码未再改变时不重跑，不重跑到绿。

## 风险与处置

- 减少审稿后，模型表达错误更依赖主模型质量。保留真实来源、业务回执与针对性评测，不宣称完全消除幻觉。
- 收尾协议可能增加格式失败；使用已有工具能力、简短字段和有界恢复，统计协议失败率，避免把原审核延迟换成新的固定调用。
- 老状态与新摘要混用可能恢复错误任务；版本化缓存、来源验证及重试去重必须先通过回归。
- 回滚可恢复旧代码与交付路径；不回滚真实业务写入，不删除用户聊天或批量清空任务状态。
