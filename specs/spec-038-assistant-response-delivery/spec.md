# 工作助手开放式任务交付与按需核对

## 状态

已完成，独立验收通过。

## 背景

工作助手需要协助用户查资料、分析、写作、制定方案和持续修改。工作管理与汇报是可调用的业务能力，是否写入由用户决定。

当前每次答复都经过独立模型逐段分类、裁剪和完成核对。北京新闻查询中，检索已有结果，但正文因证据工具分类缺失被程序删除，最终只剩泛化提示或道歉。后续供应商内容审核拦截是另一类故障，不能混为同一根因。

## 目标

- 普通任务默认交付完整、自然、有用的答复，减少固定审核调用和无必要澄清。
- 将正文交付、任务完成判断、业务执行权限拆开维护，避免通过新增句式特例修复每个案例。
- 保留真实操作、数据隔离、多轮承接、失败恢复和汇报能力。

## 非目标

不建设完整 Muse 平台，不新增浏览器自动化、任意命令执行、外部连接器、后台长期目标或跨会话记忆；不调整 Electron、模型供应商审核或三级权限产品规则，不新增常驻面板和核对开关。

## 当前行为

- `tasks/handlers.py` 固定调用 `reply_review.py`，后者同时决定保留哪些段落、是否补执行、是否修正文以及任务状态。
- 审核将正文分类为信息、查询事实、执行宣告等，裁剪额外内容和未通过证据校验的段落；工具类别维护不全会误删有效回答。
- 正文修正后再次审核；审核失败可让已有答复进入等待重试，业务回执另行保留。
- 多轮任务状态、持续指令和临时问题的收尾依赖审核输出。不能只跳过审核调用而丢掉这些能力。

## 目标行为

| 请求                             | 交付行为                                                                 |
| -------------------------------- | ------------------------------------------------------------------------ |
| 聊天、写作、建议、自由拟写       | 主模型直接交付，可合理展开；遵守用户明确的长度、格式和“不提供建议”等约束 |
| 联网查资料、阅读附件             | 根据实际读取范围回答，保留来源和日期；区分原文、推断及未核实内容         |
| 信息不足但可先开展分析           | 说明必要假设，完成不依赖缺失信息的部分；不要求补齐可选字段               |
| 对象不明、关键选择必须由用户决定 | 只询问阻碍执行的问题，沿用临时回答框或自然对话                           |
| 创建、更新、提交、删除           | 依照现有三级权限和用户授权执行，以服务端结果为准                         |
| 创建工作并解释方案               | 实际保存与必要正文都要交付，不能只给成功卡片或只给口头承诺               |
| 引用工作后切换为新闻话题         | 按当前请求查新闻，旧引用和旧待办不强制参与，也不自动写工作               |

## 功能需求

### 1. 普通回答直接交付

- 普通回答不再固定调用独立模型做逐段分类、删除“额外内容”或改写人设表达。
- 分析、建议、示例和假设可以有合理自由度；虚构样例须能被识别为样例，不能伪装成真实公司记录或已经完成的操作。
- 查询失败、资料不足时说明具体限制并保留可用结果；不能把系统核对失败表述为用户没有说明需求。
- 只有道歉、处理承诺或空正文而没有所求结果时，不因工具节点执行完毕就宣称任务完成。
- 回答沿用两种人设、Markdown、附件来源、私人分析成果和后续修改能力。普通正文不自动写入工作或正式报告。

### 2. 主模型收尾与服务端完成判断

- 主模型在正常收尾时同时提供正文和结构化任务摘要：当前目标、承接关系、未完成事项、具体阻碍、必要的业务结果引用及持续指令变更。
- 摘要通过现有模型／工具通道产生，不为所有请求再增加一次分类或完成判断模型调用；内部字段不显示给用户。
- 服务端验证摘要结构及来源，结合实际回执、待确认操作、报告任务、临时问题和执行错误决定最终状态。模型声明不能覆盖真实失败或制造成功回执。
- 保留“生成处理中”“待确认”“待补充”“部分完成”“完成”“无法继续”“中断”的既有语义。没有数据库写操作的正常文稿也可以完成。
- 持续指令仍须绑定真实用户来源和版本；收尾摘要不能自行授权，不能恢复已取消事项或将旧授权转移到新对象。
- 明确遗漏的已授权操作、必要正文或无效收尾结构允许有界修复；沿用持久标记、现有节点重试和去重，不能让收尾形成新循环。

### 3. 核对按明确问题触发

- 专项核对限于：真实业务执行的结果陈述、正式报告的数据一致性要求，以及用户明确要求的事实核验。正式报告复用已有生成与核验能力，不给所有助手答复增加报告审核。
- 真实业务执行范围依据本轮任务、工具尝试和结果声明识别；不能仅以“存在成功回执”触发，否则漏执行却声称成功的情况会被放过。不能靠“已完成”等词语名单判断整段话。
- 核对只处理具体事实冲突、遗漏或不成立的执行声明，输出问题及对应来源；移除通用段落分类、支持关系和“额外内容”裁剪规则。
- 业务回执提供对象、字段、版本和状态依据；操作保存成功不等于工作完成，报告入队不等于生成或提交成功。
- 核对无法完成时，保留已保存结果和无争议内容，说明具体未完成项。不得静默删成空答复或只有道歉后显示完成。
- 网络、参数、内容审核和核对结构错误分别处理；供应商拦截仍如实提示，不用恢复缓存或切换路径绕过拦截。

### 4. 工程边界保持严格

- 账号、公司、角色、对象所有权、来源访问、版本冲突和幂等检查仍在服务端执行，不依赖模型自报。
- 三种执行模式保持原意：只读不写入；自动审核按现有规则执行或确认；自主执行在用户授权和权限内直接执行，不重复索要同一确认。
- 文件、网页、工作描述和工具返回是材料，不能成为新授权；保留联网工具的网络地址限制和私人数据保护。
- 保留引用标记校验和读取覆盖范围，但不能因答案包含某种工具未登记的公共事实，就一律删除整个段落。有效检索也不代表来源内容必然真实。
- 用户只要求修改某个字段时保留其他字段；缺少日期等可选字段不能阻碍创建标题明确的工作。

### 5. 展示与恢复

- 普通回答不显示没有实际执行的“核对结果中”节点；需要专项核对或修复时才展示对应节点和重试状态。
- 复用现有正文、结果卡、节点列表、临时回答框和重试入口，保留折叠状态和中断行为。
- 查询接口、SSE 与刷新恢复展示一致；任务结束不留下持续等待的旧节点。
- 答复失败后重试只恢复剩余工作，已成功写入不重复；旧会话、旧检查点和旧待核对消息可以继续使用。

## 边界条件

- 当前明确请求优先于旧任务；相关的“继续”“第二项”仍正常承接，不通过清空会话实现任务切换。
- 无搜索结果、只有摘要、日期不匹配、附件部分可读时准确说明范围，不用模型记忆冒充本次检索。
- 用户需求本身无法完成时允许明确说明原因；开放式协助不等于承诺所有任务成功。
- 收尾缺字段、专项核对超时、worker 重启、版本更新和来源失效不得丢失已提交结果；缺省状态不能掩盖尚未完成的事项。

## 技术约束与兼容性

- 沿用 Deep Agents／LangGraph、PostgreSQL、任务 JSONB、租约、节点重试、操作回执和现有认证；不新增运行框架或服务。
- 收尾契约是内部协议，不改变现有 HTTP／SSE 的主要字段和状态含义；新增内部数据应带版本，旧缓存不能被误当作新协议结果。
- 默认不需要数据库迁移；历史消息原样展示，不批量重新处理。保留现有未提交新闻修复的有效行为，替换测试时保留其用户场景与断言价值。
- 方案借鉴公开产品的任务自主性和执行边界；不假定或复制 Muse 未公开的完整内部实现。

## 验收标准

- [x] 普通聊天、写作、附件分析、公共搜索路径没有固定的二次正文审核调用，也没有为分流增加固定前置模型调用。
- [x] 北京新闻及不同主题检索交付实际结果与来源；无结果说明范围，不能只剩道歉或“请补充事项”。
- [x] 工作引用后切换话题、再回到工作，以及自然追问均正确；无误写入、无上下文清空。
- [x] 私人方案连续修改与选定条目入库可用，正式报告只使用允许的真实来源。
- [x] 三种权限模式符合既有规则，跨账号／公司访问、材料注入和伪造来源仍被拒绝。
- [x] 业务执行声明与真实对象、变更字段、工作状态及报告状态一致；未执行不假称成功。
- [x] 多事项和“操作＋解释”没有遗漏；已完成结果与未完成部分分别展示，不仅依据节点数量判定。
- [x] 供应商失败、专项核对失败、缺信息和权限拒绝可区分；恢复不重复写入，不再次进入同一阻碍循环。
- [x] 收尾协议异常、旧缓存、重启、中断、来源失效的定向测试通过；HTTP／SSE／刷新状态一致。
- [x] 完成相关确定性回归与有限的真实模型评测，记录交付结果、审核调用次数和端到端耗时；不以工具成功或评测模型单一评分代替交付验收。

## 待确认问题

无。沿用已确认的“普通回答默认交付、操作按权限执行、必要场景专项核对”。
