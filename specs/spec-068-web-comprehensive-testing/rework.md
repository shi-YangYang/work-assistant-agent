# 审计问题修复与耗时约束

## 范围

用户已要求修复本轮问题，并要求 Agent 处理速度尽量不增加。本文件是原测试 Spec 的后续修复授权；原报告、问题清单与首次失败证据保留，不覆盖为通过。

修补已完成，最终范围与速度限制见 [修复报告](repair-report.md)，新的[独立验收 PASS](repair-acceptance.md)。

- 修复四项产品／架构问题：新会话草稿归属、报告最终状态收敛、图片内部路径展示、正文与清单循环依赖。
- 改进图片批量调用和报告参数契约，减少已观察到的无效工具尝试；不得以降低授权、幂等或真实成果校验换速度。
- 修复九项明确的测试维护问题，定位用量表键盘滚动检查；只有证据表明为产品缺陷时才修改相关产品行为。
- 图片预览切换属于新增体验建议，模型知识／旁支算术观察不在本次产品修补范围。真机、外部系统与未采样组合继续如实保留。

## 性能原则

- 不新增模型核对、意图分类或额外模型往返，不增加正常请求链上的串行网络调用。
- 优先修改本地状态匹配、工具 Schema／简短说明及确定性的渲染；不扩写全局提示词，不修改 low／high 的含义。
- 不删除权限、确认、来源、幂等、取消和版本冲突保护，不缩短回答或降低输出质量来优化时间。
- 对普通问答、报告、图片批量规划做修复前后同条件 low／high 对照。每档每版两次、交错顺序；记录全部原始耗时、模型／工具请求数、实际执行和副作用，不剔除慢样本。
- 图片规划对照允许使用两版完全相同的受控图片供应端，以隔离图像服务波动；必须明确这不是完整真实生图耗时。文本规划走真实模型及实际 API／worker，报告保存与最终状态实际读回。
- 记录受理、正文首片、持久终态，缺失值标未知；不把 API 观测冒充浏览器绘制。小样本不能保证所有请求都更快；若额外模型轮次或可归因的流程延迟增加，先返工再交付。

## 实施与验证

前端修复、后端修复、独立性能对照脚手架分别负责互不重叠的文件；后端相互耦合的状态、工具和架构由同一实施 Agent 串行处理。使用现有测试框架，针对实际改动运行相关模块检查；不重新运行全部审计或 308 张截图。

基线产品为 `0fd76fed8400d064d2585c4e753d542343eb864f`，当前未提交的审计资产保留。性能脚手架创建只读基线副本并冻结候选产品摘要；不切换当前分支，不丢弃工作区修改。数据库／进程／容器使用本次独占资源，避免重演共享连接耗尽。

实施后由新的独立验收 Agent 检查修复、保护性断言、性能对照及剩余限制。没有 commit／push 授权。

## 复验发现与定向返工

- 初次独立验收发现图片引用整理会误改 Markdown 代码示例；新的实施 Agent 补齐围栏、缩进和行内代码保护，最小 helper 检查 14 项通过，交新的独立验收。首次 FAIL 保留在 [初次验收](repair-acceptance-initial.md)。
- 第一版性能对照完成 24 条正式观察及 4 条原意图诊断。报告已保存后，模型曾写入的“仍处理中”说明仍可能残留；图片同时传 `prompts` 和相等的 `count` 被拒，产生无意义纠错，high 图片组中位数增加 1.32 秒。两项继续返工，不能用其它变快的样本抵消。
- 报告用本地回执状态收敛等待声明，保留其它未完成事项及真实失败；图片只接受与列表长度相等的冗余数量，数量冲突仍拒绝。不加模型判定、不猜测扩张生成数量。
- 最终候选只复验受影响的报告和四图：两版 × low/high × 两次，共 16 条固定新观察；继续 AB/BA、新鲜同事实夹具及相同供应配置。不重复无关普通问答，不覆盖初版不利结果，也不按结果追加样本。
- 这 16 条对照的候选 v2 又出现两条报告等待／告知步骤残留，见 [第二次独立验收](repair-acceptance-v2.md)。固定对照仍全部记录。新的实施 Agent 使用四条候选报告的真实输入和回执作本地回放，修复异步报告的同一状态问题；不再追加真实模型样本“刷通过”。最终差异仅为本地状态规则，性能数据明确标注实际测量版本。
