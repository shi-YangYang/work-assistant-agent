# Spec 082 — Agent 评测集与验收机制

## 状态

框架已完成独立验收（PASS），见 [验收结果](acceptance.md)。真实业务模型调用与离线模型评审均已实际执行；业务结果仍保留 FAIL/INCOMPLETE，未完成的人工复核不冒充通过。不设置费用预算前置条件，不新增费用、Token或总请求数限额。沿用产品已有超时和重试边界，按冻结的试验范围执行，禁止重跑到绿。未提交、推送或部署。

## 背景

项目已有真实模型测试、流程验收与耗时对照，但入口、样本格式、评分和报告分散。最近的问题包括：工具完成但正文错误、子任务未完成却被认为成功、旧测试未随工具契约更新、历史质量结果漏判，以及证据不足时无法区分程序、模型和网络原因。

需要建立长期维护的评测机制，使每次调整 prompt、工具、LangGraph 流转和结果契约时，能回答：哪些能力受影响、是否退步、失败在哪里、速度变化是否建立在质量相当的基础上。

## 目标

1. 建立本地手动运行的 eval：统一用例登记、分层执行、证据保存、评分及验收报告，复用现有测试与运行器。
2. 评测完整 Agent：用户请求、模型输入、工具执行、等待续接、业务结果、用户实际看到的交付。
3. 将质量、权限与副作用作为硬要求；耗时和成本单独呈现，不用快或便宜抵消错误。
4. 形成“故障证据 → 脱敏用例 → 失败复现 → 修复 → 定向回归”的闭环。
5. 明确失败、未执行和证据不足，禁止重跑到绿、只统计成功样本或替旧结果改判而不留记录。

## 非目标

- 不更换模型、搜索服务、Agent 框架，不添加线上意图识别、规划、审核、润色模型回合。
- 不恢复已删除的报告二次模型审查；离线评测不参与用户请求的执行或保存决策。
- 不在本 Spec 顺手修复全部被测业务缺陷，不为确定的纯模型错误持续打提示补丁。
- 不建设独立 Web 管理平台，不依赖托管评测平台，不自动上传用户对话或生产资料。
- 不将本次 eval 接入 CI，包括真实模型评测、目录校验、评分器自检和报告门禁；CI 继续承担既有代码检查职责。
- 首期聚焦公司 Web/API/worker Agent；不扩展为桌面录音、物理设备、ASR 全模型质量基准。

## 参考方法与取舍

- OpenAI 建议围绕实际任务定义目标、数据和指标，持续扩充用例，并用人工判断校准自动评分。本项目采用任务化样本和版本化评分，不直接照搬其示例阈值。[Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
- OpenAI 的 Agent 评测强调先看完整调用轨迹，再将明确标准沉淀成可重复的评测集。本项目保留模型调用、工具、保护措施与业务结果的关联。[Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals)
- Anthropic 区分任务、独立试验、轨迹与实际结果，建议结合程序/模型/人工评分、隔离环境、区分能力探索与回归；工具路径允许合理变化。本项目据此分层，不把部分得分或多次里成功一次算作完整验收通过。[Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

以下目录、结果协议和验收门槛是本项目方案，不是上述厂商的规定。首期使用仓库内 CLI 和静态报告，沿用已有 LangGraph 及服务，不引入另一套生产 Agent。

## 目标行为

```text
版本化用例目录 + 套件 + 模型/环境配置
                 ↓
校验、选择范围、展开运行计划（不调用模型）
                 ↓
冻结输入与源码 → 既有运行器 → 原始证据
                                     ↓
                             程序断言 → 语义评估/复核
                                     ↓
                          分项结果 + 验收门禁 + 同条件对照
```

## 功能需求

### 1. 用例登记与分层

每项用例记录稳定 ID、修订、来源、能力族、角色与权限模式、固定材料和初始状态、多轮输入/应答规则、允许操作、必须满足的事实、禁止副作用、执行层级、评分规则和证据要求。预期正文允许等价表达；明确要求原文、数字或条件不变时执行相应严格断言。

同一任务的模型/effort/重复采样是试验槽位，不增加“不同用例数”。既有用例通过 `source + sourceId` 接入，避免复制后漂移。只有保存在历史产物中的有效样本才脱敏迁入版本管理，并保留原始来源；迁移清单逐项标明接入、重复、过时或缺证据，不能静默丢弃失败样本。

套件分为：

| 套件     | 内容与用途                                                         | 通过含义                             |
| -------- | ------------------------------------------------------------------ | ------------------------------------ |
| 快速契约 | 确定性工具/结果契约、权限、任务状态、输入装配及评分器自检          | 只证明程序行为，不证明真实模型质量   |
| 核心回归 | 已明确支持的关键用户任务，正常与反向场景，真实模型、必要浏览器流程 | 所有必需断言及规定试验通过才通过     |
| 能力诊断 | 新能力、已确认模型失败、复杂边界和未决历史问题                     | 如实呈现能力缺口；不冒称全产品已通过 |

成员资格、必需项和模型矩阵在执行前冻结。不能在失败后将用例移出核心回归，也不能用“模型问题”自动豁免必需项。能力诊断中的已知失败不要求本 Spec 消除，但仍计入全部所选任务的质量结果。

各套件标注 `development` / `holdout`；已用于调 prompt 的历史样本属于开发样本，不能重新命名为未见样本。留出样本不进入提示和工具结果；一旦暴露并用于调优，标记消耗并在后续版本补充。期望答案和评分规则不交给被测 Agent。

### 2. 首批覆盖要求

先盘点既有样本，再按下表补缺口，禁止直接重启所有历史矩阵。首批每个能力族均须有当前有效样本、层级、断言及执行结果；多轮样本优先覆盖真实关联状态，不为凑数量生成近义问法。

| 能力族         | 必须覆盖的代表场景与反例                                                                                             |
| -------------- | -------------------------------------------------------------------------------------------------------------------- |
| 普通回答与交付 | 直接回答、改写、数量/条件/原文保持；不能用链接或操作回执代替所要正文                                                 |
| 澄清与工具选择 | 只有用户能决定时及时提问、1～5题/单选或自填、回答后续接；信息充分时不迟问/反复问；需要搜索与无需搜索均覆盖           |
| 材料理解与引用 | 多文件/混合格式、长文分页、正文与图片、同名不同ID、旧附件、新版本、恶意材料指令；读取成功不等于理解充分              |
| 工作与材料保存 | 创建、局部修改、保留未授权字段、选定材料、清单状态、无变化不增用户历史；重复请求/故障重试不重复写入                  |
| 周报           | 周期内工作正文/清单/进展完整传入，项目状态与已完成进展分清；无汇报规则的手动入口、删除后再生成、真正空周期、来源变化 |
| 文件成果       | 生成/修改/下载，真实文件可打开且内容正确；需要沙盒时核验实际执行，不能以 export_table 通过替代                       |
| 多轮与恢复     | 历史承接、上下文压缩、澄清、确认/取消、用户改口、等待续接、恢复后最终消息与卡片一致                                  |
| 权限与来源保护 | 角色/租户隔离、对象归属、明确授权与未授权、权限撤销、来源修订、幂等、租约和并发恢复                                  |
| 执行反馈与界面 | 运行/失败/完成卡片、首屏与最终结果、刷新持久性、移动端关键交互；隐藏数据库字段不能替代用户可见交付                   |
| 故障与效率     | provider错误、工具错误、断流/中断、重试恢复；无多余写后补查；次数/时长异常有证据，不能按次数推断语义充分             |

每个可能执行动作的能力同时包含“不应执行”的反例。首期涉及音频的 Agent 流程可使用既有固定输入或预先准备的转写结果，但必须标注 ASR 是否真实执行；不借此宣称 ASR 质量通过。

### 3. 执行等级、隔离和运行边界

- 明确区分 `contract/replay`、`real-model`、`real-browser`。真实模型直接调用现有 graph/process_job 的检查只能证明对应层级；API/worker/浏览器流程须由真实入口触发，不能通过直接插入成功记录代替。
- 环境沿用已有自有资源 manifest 校验，拒绝生产地址、生产写入和日常账号修改。固定业务时间/时区、材料、初始状态；独立试验隔离，多轮任务保留任务内状态。仅清理本次拥有的资源。
- 模型、provider、实际 effort、权限模式、persona、版本必须显式记录；初始真实回归覆盖当前配置的 low/high，不支持的配置标为不可执行，不静默降级或换模型。历史 max 只保留原标签，不能重命名成 high。
- 计划记录用例槽位、独立试验数、单试验超时和并发，默认串行；业务模型与离线评分调用分开记录。费用预算不阻止启动，按预先声明的有限试验槽位完成验证，不额外为转绿反复调用。
- 默认每槽位一次首试；权限/幂等/恢复关键任务的可靠性采样预先规定三次独立试验。已有生产内重试属于同一次试验，所有调用和失败保留。评测器不得为得到通过额外重跑。
- 已完成、失败、超时的试验不可覆盖。环境中断后的继续执行只补未开始槽位；需重做已启动槽位时建立单独运行并注明原因，旧试验保留。
- 缺少能力或超时时停止相应执行并标注未完成，不能删掉未执行项后宣布全套通过。取消不得遗留本次仍在运行的业务任务或模型请求。

### 4. 证据与可追溯性

冻结 run manifest：代码提交、未提交改动/源文件指纹、用例/材料/评分规则版本、依赖锁、模型参数、环境标识、运行计划及超时边界；API/worker加载同一份冻结源码，变更后必须新建运行。旧提交证据不能冒充新提交结果。

按 `runId / caseId / modelConfig / trial / turn` 保存：用户输入、实际发送给模型的业务上下文和工具 Schema、公开输出、工具参数/结果/顺序、确认/拒绝、父子任务关联、必要业务前后快照、下载文件与哈希、计时/usage、断言和失败证据。浏览器用例补可见文本、相关截图及刷新后结果。

首期用合成/脱敏数据；实际 wire 记录限隔离评测进程，过滤密钥、Cookie和认证头，不要求或保存私有推理过程。材料、回复中的指令视为被评测数据，不允许其更改评分或调用权限。业务正文、评分期望、原始证据和公开报告分别管理，导出不包含凭证。

原始证据只追加；评分修订作为新版本引用相同证据，允许离线重算而不重新调用业务模型。报告摘要必须能跳到具体断言和原始证据。没有完整实际输入时，不能证明“模型已收到正确信息”。

### 5. 评分与验收

**程序先判断可确定事实：** 参数/结果契约、对象身份和归属、数量计算、数据库真实写入、只改授权字段、无重复写入、来源修订、任务完成、文件有效性及用户可见状态。HTTP 200/202、工具返回 success、模型说“已完成”都不是充分证据。

**语义单独判断：** 是否满足请求、事实及条件保真、遗漏/无依据增加、引用正确、数量表达与实际一致。字符串包含、答案长度、合法来源ID都不能独自证明语义正确；不要求唯一措辞或固定工具顺序，除非用例确有权限/依赖顺序约束。

确定性可覆盖项由程序裁定；不能可靠自动判定的项进入人工复核。实现并真实验证离线模型初评，复用现有评分接口并采用结构化逐项结论/原文证据/`unknown`，用独立正负样本与人工结果校准。它只辅助离线验收，不改答案、不触发业务重试、不覆盖程序失败。初期所有必需语义项仍需人工确认，后续自动化门槛另行决定。

| 结果       | 定义                                              |
| ---------- | ------------------------------------------------- |
| PASS       | 必需断言、证据与语义复核全部满足                  |
| FAIL       | 至少一项必需要求有明确违反证据，包括模型错误      |
| INCOMPLETE | 缺环境/证据、评分器异常或待人工判断；不能当作通过 |

分项可以展示部分完成，但整体不因平均分高而通过。评测结论与故障归因分开保存：系统、模型、外部服务/网络、评测器/夹具、未知；可以存在多个原因。纯模型归因须有正确且完整的实际输入、明确输出违反，以及对相关程序路径的核对。网络需连接/首包等证据，等待时间长不等于网络问题。

核心回归门槛：冻结计划内必需试验全部 PASS，权限/越权/数据损坏零容忍，无未执行或待判项。能力诊断单独出结果；整体质量未全过时必须明说，不能只报核心通过。已知模型失败留档，不自动驱动无止境修复。系统缺陷给出定位及最小回归建议，另按授权修复。

机制本身的验收与 Agent 能力结果分别记录：框架能准确揭示失败，可以通过框架验收；不代表被测 Agent 全部通过。

### 6. 速度、成本和对照

保留端到端耗时、首个可见有效输出、最终可用成果、模型/provider等待、工具及持久化阶段、模型请求数、输入/输出Token和费用。SSE首文本不冒称浏览器首绘，阶段有重叠时不直接相加；未知阶段保留未知。外部网络耗时可分列，不随意扣除后宣称提速。

对照须使用相同任务/材料/初态、模型及参数、环境和评分版本，冻结 AB/BA 顺序及样本量；不能拿旧的失败续接与新的初始生成比较。同时展示全部样本状态、成功率、失败耗时和双方均通过的配对耗时，避免只留成功快样本。报告样本量和分布；样本少时只描述观测，不声称普遍提速。先满足质量与保护门槛，再判断性能改进。

费用由实际 usage 和价格版本估算，未知价格/usage记未知；Agent执行与离线评分成本分开。估计不是精确账单；不得靠无限提高产品已有超时或Token维持通过。

### 7. 使用与维护

- 提供本地统一 CLI 的目录查看、自检、校验/预览计划、运行、离线评分/人工复核录入、报告和同条件对照能力。旧入口和参数保持可用。
- 本次 eval 全部在本地手动触发，不接入 PR、push、定时或手动 CI 工作流；目录校验和评分器自检也通过本地入口执行，不能被默认 CI 测试发现机制隐式纳入。
- 真实流程在本地隔离环境运行，按变更涉及的能力选择；发布前也由开发者手动决定运行范围，不自动触发、部署、合并或创建付费资源。本地运行器仍可调用已配置的远程模型 API，“本地”不表示模型推理必须在本机。
- 契约/prompt/工具修改时通过目录中的模块关联选定相关回归，并加入跨能力核心样本；报告明确本次覆盖范围，不能以子集通过宣称全量通过。
- 每个线上故障先脱敏入库，标注预期结果和可复现条件；先审阅实际证据，不能自动把用户隐私数据加入 Git。评分误判修评分规则并回算证据，不靠再次采样消除误判。

## 边界条件与技术约束

- 测试材料中的身份不等于访问授权，用户模拟器只回答用例预先定义的信息，不替 Agent 补答案或盲目确认所有操作；首期采用固定输入和显式分支，不增加用户模拟模型。
- 外部网页会变化：固定网页夹具验证确定行为，真实联网验证实际集成，分开标注；材料内容变更后不能直接比较质量分数。
- 使用现有 Python/pytest/Playwright、SQL 与隔离环境能力；新增评测代码不进入线上请求路径，不增加运行时提示字符或模型回合。
- 涉及适配、评分共享逻辑按 S2，若调整环境隔离安全边界则相应部分按 S3；本次仅文档按 S0。

## 兼容性要求

保留原始用例ID和历史证据，采用带命名空间的统一ID解决重名；保留既有命令与历史结果可读性。旧数据不满足新证据要求时标注限制，不伪造字段。接入旧评分器时以当前实际 UI 为准，特别核对已移除的版本提示、状态文案和卡片可见内容，不以过时投影代替真实页面。
