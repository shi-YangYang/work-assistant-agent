# Agent 全流程性能优化

## 状态

流程减负已实施；相关系统检查通过，整体性能目标未证实。速度回退基线为测试修复提交 `70ba0f7` 的父提交 `48452f69c8cd6b79c3005f8a698ae63a42b8b9ad`。`70ba0f7` 是修复后版本，不是快版本；此前以它和 `3d0a0d1` 为基线的测量只作中间版本记录。max 工作修改仍有约 420 秒长等待，不能将该问题标记为已解决。

## 背景

用户需要更快拿到完整、正确的答案或实际成果。只有首字变快，或者把工作移到回复之后而没有真正完成任务，都不算任务提速。

上一轮已拆开临时正文传输与数据库最终保存，精简主提示、交付协议并按需加载工具。但业务操作仍有主模型、变更范围判断、授权判断等调用，附件、搜索、沙盒和队列的全流程成本尚未统一评测。[已有计时](../spec-055-assistant-response-latency/implementation.md#最终源码真实计时)包含外部网络失败和篇幅不足，不能作为稳定性能结论。

## 目标

- 减少系统给模型增加的提示、决策轮次和等待，在保留必要输入、能力与操作正确性的前提下，缩短发送到完整结果可用的时间。
- 覆盖普通问答、SaaS 业务、编码计算、搜索、材料、文件、记忆、长会话、混合任务和异常恢复。
- 用分段数据定位瓶颈；区分程序、模型服务、网络与资源排队，不再笼统归因模型慢。
- 优化通用执行流程，不为固定测试问题增加特判。

## 非目标

- 不更换默认模型，不降低用户选择的思考强度，不限制答案篇幅换速度。
- 不重建 Agent 框架，不新增分类模型、全局审稿模型、RAG 或托管基础设施。
- 不改造 Electron 本地会议流程，也不顺带重做 Web 管理页面。
- 不承诺控制供应商推理时间或网络，不保证任意开放问题绝对正确。
- 不以作文足额字数、文采、一般知识或逻辑错误作为本次性能返工条件，不针对评测答案反复调提示词。

## 当前行为

- 普通回答可一次主调用直接输出；工具任务先通过 `load_tools` 加载相关能力。
- 业务写入按操作检查范围、授权、来源、角色、版本与幂等，必要时等待用户确认；部分检查复用模型，已有任务内缓存。
- 附件解析、上下文、记忆、压缩、网页、沙盒和报告作业参与不同任务路径。
- 临时正文走 Redis／SSE，最终答案及操作回执落 PostgreSQL；前端有打字效果。
- 已有模型、工具及发布计时，但缺少完整网络阶段、跨作业关联和浏览器最终可用时间。已有基准入口固定七轮，不能表达全能力旅程。

## 目标行为

保留现有操作体验、任务能力与授权规则。足够的上下文只准备一次，已取得的有效资料不重复读取；独立步骤有界并行，依赖步骤顺序执行。每次模型调用都有具体职责，交付足够后不继续无意义核对。真实结果及时显示，错误和未完成事项如实保留。

## 功能需求

### 1. 完整任务计时

| 指标         | 定义                                                                                               |
| ------------ | -------------------------------------------------------------------------------------------------- |
| 完整可用耗时 | 浏览器提交开始，到所需正文全部呈现、文件可下载、业务结果真实保存；同一任务有多种成果时取最后完成者 |
| 首次有效内容 | 用户首次看到能回答问题的正文或真实操作结果；不把“处理中”、心跳和推理分片算答案                     |
| 活跃处理耗时 | 完整可用耗时扣除用户回答澄清／确认的人工等待；另保留不扣除的总时间                                 |
| 流式间隔     | 合法正文首次到达服务端、到达浏览器与呈现的延迟，以及后续最长无正文间隔                             |
| 分段成本     | 接收、上传就绪、排队、准备上下文、模型、工具、授权、执行、保存和交付的耗时与次数                   |

- 上传在发送前已完成时单独记录添加附件到就绪的时间；发送后仍需解析／转写的时间计入完整任务。
- 报告入队、沙盒受理、等待确认都不是用户要求的成果已完成。关联后续作业和交互轮次，分别记录受理、就绪、可用时间。
- 用 request／job／attempt／fence／model call／tool／子作业关联事件；进程内用单调时钟，跨进程不直接相减不同起点的时间。
- 显示关键依赖路径；模型嵌套在工具内、工具彼此并行时不能重复加总。
- 区分连接建立、首个上游事件、首个正文、最后有效进度、完成与超时。保留安全的错误类型和发送阶段；无法观测 DNS／TCP／TLS 时明确缺口，不猜原因。
- 日志有界且低开销，不记录密钥、用户正文、网页内容或隐藏推理。基准原文仅来自隔离测试资料。

### 2. 按证据优化流程

| 环节             | 分析与优化要求                                                                                                             |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 接收与调度       | 检查队列等待、锁持有时间、worker 占用和连接等待；避免长模型或沙盒调用无谓占住数据库事务                                    |
| 上下文           | 去除同任务内重复构造／读取，按所需片段提供材料；保留当前指令、持续任务、工作版本和来源                                     |
| 主模型与工具发现 | 测量按需加载的额外轮次与输入大小；比较小型常用工具集、批量加载、已有结构化引用等方案，不增加前置分类模型或关键词分流       |
| 业务检查         | 列出变更范围、操作意图和执行授权各自保护什么；复用同一合法范围内的证据，去除实测重复工作；不能未经验证直接删除独立保护职责 |
| 工具读取         | 减少重复查询、无效分页、同页重复抓取；只并行没有数据依赖且被授权的读取，限制并发与结果大小                                 |
| 代码与文件       | 常规操作沿用内置工具，自定义任务保留代码执行；优化沙盒就绪、资料传递、结果回传和文件发布，不以文字描述替代实际执行         |
| 附件与媒体       | 各独立附件在资源预算内解析；多语音、多图片和混合材料都保留各自来源、顺序、失败状态，避免重复解析                           |
| 流式与收尾       | 不阻塞上游消费，不等额外总结才展示合法正文；最终提交后及时显示全文，不能继续排动画拖延可用时间                             |
| 失败与恢复       | 只重试失败且允许重试的节点；复用已有有效成果，避免重新搜索、重跑成功代码或重放已完成写入                                   |

候选优化只有在基线证明成本或受控测试证明因果时才实施。每项记录瓶颈、改法、预期影响、真实收益与质量检查；没有收益的复杂化不保留。

### 3. 安全并行与复用

- 根据真实依赖执行，不让“读后写”“创建后修改”“审批后提交”“执行后导出”越序。
- 业务写入保持现有事务、版本、租约、幂等与回执边界；不并行写同一对象，也不因为模型输出多个工具就盲目并发。
- 缓存键包含实际依赖的公司、用户、权限、来源／对象版本、任务及配置。先复用任务内已有机制，不建立共享私人结果缓存。
- 用户新消息、修改指令、来源撤回、权限变化、对象变更和显式刷新使相关复用失效；缓存命中不替代必要的实时权限检查。
- 多用户、API／worker 重启、取消及断线下不会串任务、泄漏资料或留下失控后台任务。
- 以 4 核 8 GiB、沙盒并发 2 为现有资源基线。先优化流程，不通过加服务器、无限并发或扩大连接池掩盖等待。

### 4. 系统正确性与评测边界

- 在计时前为样本写清必需成果、允许假设、禁止操作和核验依据，避免看到答案后修改标准。
- 业务检查实际记录、字段差异、版本、权限与副作用次数；文件检查实际生成、可下载、可打开，传输没有损坏或遗漏；搜索检查真实工具调用、返回数据与来源没有被系统丢弃或篡改。
- 模型自由生成的字数、文采、一般事实及逻辑问题仅作观察，不构成本次验收阻塞，也不为此增加补写、审稿或重复实测。
- 保证完整传递用户输入、模型输出与工具结果；系统导致的截断、错误过滤、重复调用、权限回归或执行失败仍须修复。输入、模型和思考强度不能为了提速而偷换。
- 原始答案及原评审结论保留，另列当前范围内的系统结果；不能把未生成成果、只回提问、等待确认或超时计为已完成成果的提速。
- 人格、思考强度、模型参数与原任务相同；主调用和辅助调用分别记录有效配置，不把辅助调用配置冒充用户主模型强度。

## 边界条件

- 三档执行权限与用户明确“先别保存”“先给我看”仍生效；自主执行不等于绕过角色与数据权限。
- 长会话压缩、记忆读写、用户引用工作、切换话题、澄清及持续指令都属于完整流程，不只测试新会话。
- 保留现有有界重试、无进度超时和总时限的职责；持续有效生成不得被误算闲置。性能改造不以单纯延长等待作为修复。
- 失败时间、重试成本和成功率必须列入报告；不能删除失败后只展示较快成功样本。
- 浏览器断开不等于取消后台任务；只同步既有状态，不新增自动重发、无限重连或高频轮询。

## 技术约束

复用现有 FastAPI、Deep Agents／LangGraph、PostgreSQL、Redis、沙盒和基准脚本。先不新增数据库 migration、公共配置入口或依赖。文档阶段按 S0；实施如触及权限、调度、持久化和共享执行流程，按 S3 对相关子系统验证，不顺带运行 Electron 全套测试。

## 兼容性要求

保留旧会话／checkpoint、业务操作回执、引用与附件、成果版本、来源撤回、账号隔离、记忆开关、两种人设、三档执行权限、用户选择的强度、取消与恢复。既有模型使用供应商默认输出配置，不借本次改造重新加答案长度限制。

## 验收标准

- [ ] [覆盖矩阵](test-matrix.md)映射到实际注册工具、业务动作和关键分支，没有未解释的遗漏。
- [ ] 所有代表旅程有发送到完整结果可用的计时；队列、模型、工具、网络、人工等待及并行关系可解释。
- [ ] 同模型、同强度、同输入和隔离数据比较实际调用负担；low 与 max 分开。已有问答、写作、业务、搜索、编码／文件与混合样本用于定位，只补受改动影响的必要对照。
- [ ] 每项保留的优化都有成本下降证据；选中的瓶颈旅程完整可用耗时中位数目标下降至少 20%。未达到时报告实际收益，不能宣称目标通过，也不能靠降质量达标。
- [ ] 未优化类别出现完整可用耗时超过 10% 的回退时必须解释和定位；若是本次代码造成则修复，外部噪声只能标记结论不足。
- [ ] 系统正确性不退步，权限泄漏、越权／重复写入、丢失或篡改输入输出、虚构执行等严重回归为零；模型一般内容质量不作为本轮验收门槛。
- [ ] 多轮流程、用户确认、附件、压缩、恢复、取消及多用户竞争通过对应检查；报告和文件到实际可用才算完成。
- [ ] 不新增线上全局审稿／长度补写，不降低主模型强度，不删必要来源、权限和一致性保护。
- [ ] 隔离环境清理完成；交付改动、每类耗时、质量结果、失败原因与尚未控制的外部因素。

## 待确认问题

无新增产品交互决策。20% 为本次优化目标，不是供应商响应时间承诺；实际优化项按基线选择，新增基础设施或改变授权规则另行讨论。
