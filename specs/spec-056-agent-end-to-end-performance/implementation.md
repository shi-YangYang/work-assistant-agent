# 实施结果

流程减负已实施并验证。基线为 `3d0a0d1`；真实测量未证明总体提速或 20% 目标，max 工作修改长等待仍未解决。

## 改动

| 环节     | 改动                                                               | 已有因果证据                                                                                                      |
| -------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| 模型网络 | 同一任务内复用安全传输连接；成功流式响应有界消费 HTTP 尾部         | 真实 HTTP 四次流式请求由四条 TCP 连接降为一条；异常、停滞、取消仍有界退出                                         |
| 工具发现 | 有合法工作引用／文档附件或紧邻回合真实业务回执时预载对应工具组     | 工作引用读取、工作创建后修改、报告生成后提交均有受控主模型 3 → 2 证据；读取、授权和副作用不减少，不累积更早的工具 |
| 多文档   | 独立文档有界并行，保留来源、顺序及失败结果                         | 单任务最多 2 个，单 worker 事件循环全局也最多 2 个解析任务，取消回收子进程                                        |
| 多成果   | 沙盒多个文件按最多 2 路下载，全部校验后发布                        | 保留顺序、大小、哈希和归属校验；现有批次总量上限不变                                                              |
| 业务恢复 | 当前真实读取、成果版本或回执变化后，使旧拒绝失效并重新独立授权     | 复现并修复补齐方案后仍反复拒绝的循环；未直接放行，不重放成功操作                                                  |
| 任务反馈 | 合法来源补齐后的相同完整动作精确替代旧错误；最新授权分类替换旧分类 | 不同内容、已绑定条目、独立副本与其他提案状态保持                                                                  |
| 观测     | 增加排队、网络阶段、有效进度、调用关联和浏览器完整可用时间         | 日志不含正文、密钥或隐藏推理；父子调用和并行时间不重复加总                                                        |

未更换模型、降低主模型强度、压缩输出长度或新增线上审稿。未修改 Web 业务界面、数据库 schema、沙盒服务或部署配置。

## 真实测量

固定专业人设、同一模型与输入，low／max 分开。主模型和辅助模型参数分别记录；每项保留原回答、实际数据库结果、文件和浏览器呈现时间。

- 首版 22 个任务及其中质量失败完整保留，不混入返工后统计。
- 已执行 86 个任务：原有 84 个，加回执预载后的 max 创建／修改两轮。原计划剩余矩阵停止，不补满 212 个历史预算，代码版本与未执行范围分别记录。
- 一般字数、文采、知识与逻辑问题作为模型观察，不再触发调参、重测或性能返工。任务是否实际交付、系统是否完整传递输入输出仍单独核对。
- 报告的父任务结束、子报告就绪与报告页面正文呈现分别记录；文件实际可下载、业务结果已保存才算完整可用。
- [逐项结果](../../artifacts/spec056/performance-results.json)持续更新；完成后由独立验收核对，不用一次快样本或首字时间替代任务耗时。
- [阶段与输入体积总表](../../artifacts/spec056/performance-summary.md)区分模型调用、工具、准备和保存。相同工作 schema 在 low 与 max 有显著不同时长，不能只凭提示字符数归因。静态工具说明去重候选另存[体积分析](../../artifacts/spec056/receipt-preload/schema-size.json)，没有据此删除参数契约或宣称已提速。

最后一次 max 创建完整可用 139.42 秒，其中发现约 2.14 秒、已加载工作工具的主调用约 130.71 秒、授权约 4.20 秒；创建只发生一次。下一轮首调用已直接提供 9 个工具，没有再调用 `load_tools`，但仍在约 420.49 秒后结束为待重试，工作未修改。预载减少一轮的机制有效，却没有解决这一主调用的长等待；不能把该失败包装成提速成功。

## 限制

真实性能在本地隔离环境测量，并非 4 核 8 GiB 云服务器整机压测。日常本地沙盒实际并发为 1；并发 2 验证使用独立临时控制服务，没有修改日常配置。模型和网络波动、实际调用失败及答案篇幅差异均保留，不能全部归为程序提速或退化。

已有受控与真实证据能确认减少固定开销，不能证实 max 长等待的完整根因。相同体积的提示在 low／max 耗时差异明显，仍须区分输入语义、思考强度及上游因素。[离线还原](../../artifacts/spec056/request-reconstruction.json)的 messages、system、tools 哈希均与慢请求记录一致，可用于相同输入的提示／工具负担对照；完整 HTTP 请求体字节未保存，不能称为原始报文。还原未调用模型，也未证明长等待原因，不恢复开放答案的大矩阵评测。

[最终独立验收](acceptance-final-scope.md)确认代码与已验系统边界通过，整体 20% 目标未通过。测试专用 API、worker、Vite、PostgreSQL、Redis、临时账号及凭据均已清理，日常服务未动；[测量环境清理](../../artifacts/spec056/cleanup-final.json)与[实施数据库清理](../../artifacts/spec056/implementation/cleanup.json)分别记录。
