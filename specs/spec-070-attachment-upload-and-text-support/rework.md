# 必须修复的验收问题

## 24 小时回收与工作材料绑定竞争

隔离测试中，在 maintenance 的附件筛选快照之后、附件行锁之前完成工作材料绑定，回收仍将已引用的来源标记删除并清理原文件。实际工作材料副本尚存，但来源保护不满足 Spec。

- 回收与正式绑定必须使用一致的公司／附件锁顺序，并在获得锁后以最新事务视图复核正式引用。
- 同一事务先执行其他附件写入会因自动 flush 提前持有行锁；安排回收顺序时必须避免随后再取公司锁。候选筛选继续预先排除已知正式引用，避免每轮对全部历史材料逐项加锁；最终安全判断仍在取得锁后重新查询。
- 保留 tombstone 先提交、物理清理后执行及失败重试机制。
- 以确定性时序复现“绑定先提交，随后回收复核”，断言来源与副本都保留；同时验证真实未引用孤儿仍能回收。
- 原始证据：`artifacts/spec070/acceptance-maintenance-race.json`。

## 长按直发时登录过期，恢复后草稿卡住

身份暂停保留了 `directSend` 临时录音，但旧草稿 writer 已失效。原账号恢复后上传协调器跳过该文件，录音 ref 又已释放，文件永久等待上传，阻止原草稿发送。

- 暂停身份时丢弃本次直发临时录音并释放本地 URL，保留正文及其他附件。
- 不改为普通草稿上传，不自动重新发送；对是否已被服务端受理不确定的文件，继续避免误删。
- 用登录暂停／恢复的具体用例验证原草稿可继续使用，不出现残留等待录音或重复发送。
- 原始证据：`artifacts/spec070/acceptance-recovery.test.ts`、`acceptance-recovery.log`。

## 已过期附件的发送错误缺少操作指引

过期附件发送只显示泛化的 404，未满足“明确提示移除后重新添加”的验收要求。

- 在能够正确归因的范围内，告诉用户重新添加已不可用附件；不暴露他人或其他公司的附件状态。
- 不自动上传或重复发送，不破坏消息幂等和未知受理结果保护。
- 覆盖过期附件实际错误呈现，以及权限信息不泄露。

## 验证边界

只运行这些修复直接影响的定向检查，保留已经通过且未受修改影响的证据。返工由新的实施 Agent 完成，随后由另一个新的独立验收 Agent 检查；不顺带修复无关类型错误，不提交或推送。
