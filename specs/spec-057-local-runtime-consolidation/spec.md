# Spec 057：本地启动与容器管理统一

## 状态

已实施，本机迁移与独立验收通过。统一为一个本地 Docker 项目分组，保留四个服务；生产部署与 CD 不变。测试结果与限制见[验收报告](acceptance-rework.md)。

## 背景

启动 Web 后，Docker 界面出现多个独立入口，难以判断哪些属于 Noria、哪些需要一起启动或停止。此次更新精简运行环境管理，并验证现有功能不受影响。

## 当前行为

本地实际运行 4 个容器，分为 3 个顶层入口：

| 入口 | 容器 | 职责 |
| --- | --- | --- |
| 独立数据库 | `paa-company-postgres` | 业务数据、会话、记忆、任务与 checkpoint |
| 独立缓存 | `paa-company-reply-redis` | worker → API 的临时正文流与恢复快照 |
| 沙盒 Compose 项目 | `control`、`runtime` | 私有控制接口、带 gVisor 的独立 Docker 引擎 |

- 数据库脚本兼容旧 `docker run` 容器；Redis 脚本自行 `docker run`，同时 Compose 又定义了 Redis。
- 沙盒使用独立项目名、独立启动与资源归属逻辑。runner 是构建镜像，不是常驻服务；执行任务时会在沙盒引擎内创建短期容器。
- `npm run dev:web` 已自动启动依赖，并非需要用户手动启动三个入口。API、worker、Vite 在宿主机运行。
- PostgreSQL 数据位于 `paa_company_pgdata`；沙盒引擎缓存和控制状态使用旧项目名下的数据卷。不能仅修改项目名后创建空卷。
- 生产 Compose 已统一管理服务；本地为兼容 Docker Desktop，额外使用独立沙盒引擎，二者拓扑不同。

## 目标

统一本地编排与生命周期：Docker Desktop 中一个项目分组，命令、服务配置、健康检查和停止规则一致。

- 普通聊天使用 PostgreSQL、Redis 两个常驻容器；启用本地沙盒后共四个，全部在同一项目下。
- 保留 `npm run dev:web`、独立 API／worker 命令及现有沙盒命令。
- 迁移后保留账号、工作、聊天、记忆、附件、成果、密钥和沙盒持久状态。
- 回归验证启动、流式聊天、业务操作、沙盒和异常恢复。

**此建议精简的是管理入口与重复编排，不减少四个服务的实际数量，也不承诺因此明显减少内存或模型响应耗时。** 若目标是减少实际容器数量，需要重新确认替代架构，不以分组变化冒充达成。

## 非目标

- 不删除 Redis，不恢复逐批正文写数据库，不合并 API 与 worker。
- 不把数据库与缓存打包进同一容器，不将沙盒控制服务并入特权引擎。
- 不移除 gVisor，不在宿主机或业务进程执行模型代码。
- 不新增容器平台，不修改业务协议、模型、人设、权限、并发数或资源预算。
- 本次限定本地开发；不重构生产部署、不操作线上服务器、不升级数据库版本。

## 目标行为

```text
npm run dev:web
  ├─ 同一 Compose 项目
  │   ├─ postgres
  │   ├─ redis
  │   ├─ runtime       本地沙盒启用时
  │   └─ control       本地沙盒启用时
  └─ 本地进程：API、worker、Vite
```

Docker Desktop 中统一显示为一个项目分组；执行中的临时沙盒容器仍在私有引擎内独立运行、完成后清理。

## 功能需求

### 编排与启动

- 复用现有开发 Compose 和沙盒覆盖文件，以同一项目名组合运行；Redis 服务参数只由 Compose 定义，删除对应的重复 `docker run` 创建逻辑。
- 统一管理 Docker 命令、依赖健康检查、资源归属、失败清理；沙盒镜像构建和载入保持专门职责。
- 开启沙盒时，先启动引擎并载入 runner，再启动控制服务。只有所需依赖就绪后，才启动应用进程。
- 未启用沙盒时，不创建、构建或启动沙盒服务；不因沙盒变量未填写而阻止普通聊天启动。
- 外部数据库、外部 Redis、远程沙盒沿用配置；不创建替代容器，不停止外部服务。
- 冷启动缺少 Docker、端口冲突、依赖不健康、镜像载入失败时，明确指出失败阶段并有界退出。

### 停止与重启

- `Ctrl+C` 停止本次启动的 API、worker、Vite，以及本次拥有的 Redis／沙盒服务；数据库继续运行，保留已有使用习惯。
- 已运行或手动启动的共享服务不因另一条开发命令退出而停止；并发启动不能互相接管或清理资源。
- 启动中断和部分失败只清理本次启动的资源，不使用全局 `docker prune`、`down -v` 或无差别停止。
- 重复启动、退出、再启动不新增重复分组、残留 worker 或重复端口监听。

### 旧环境迁移

- 首次发现旧容器时，给出迁移入口和具体说明；不在日常启动中静默替换正在使用的数据库。
- 提供一次性本地迁移命令：检查无活动开发进程和任务 → 记录旧资源及镜像 → 备份并校验可恢复性 → 停止旧服务 → 使用原持久卷创建统一项目 → 健康及数据核对。
- Compose 标签不能靠修改名称补齐，允许重建容器外壳，但保留持久卷；同一 PostgreSQL 数据卷不得同时被两个数据库进程挂载运行。
- 沿用实际数据库镜像与主版本，不顺带升级；识别命名卷、绑定目录及实际挂载，不假定所有安装都与当前机器相同。
- 沙盒控制状态与引擎数据一起保留。socket 卷属于运行时通信，不当作业务备份；停止旧引擎后重新建立有效连接。
- 迁移失败可以恢复旧拓扑与镜像；未核对成功前不删除旧容器与持久数据，不在失败后自动初始化空数据库。
- 不将旧 Compose 标签变成长期兼容分支；迁移完成后只走统一的管理路径。

## 边界条件

- 迁移必须在无在途任务时进行；任务仍运行则拒绝迁移，不强行终止或自动重发。
- 只确认属于本项目的资源；同名外部容器、未知挂载或端口占用须明确报错。
- 沙盒未启用、仅使用远程依赖、部分服务已启动、第二个终端重复启动均需覆盖。
- Redis 是临时缓存，停止时在途预览可能失效；迁移不承诺保留未完成的模型连接。已保存的消息、业务回执和成果必须可读取。
- 本地测试、用户日常环境与生产环境的容器、端口、卷和凭据必须隔离。

## 技术约束

- 单一 Compose 项目不等于共用所有网络。数据库／Redis与沙盒保持网络隔离；沙盒控制容器不新增业务凭据或业务卷。
- 仅沙盒引擎保留当前所需特权；控制服务仍为独立受限容器，执行代码仍采用 gVisor、无网络、非 root、资源上限。
- 不向公网或业务容器暴露 Docker socket；不将宿主 Docker socket 替换进本地沙盒。
- 不新增业务数据库 migration 或修改前端；如实施发现必须修改这些边界，先更新方案。
- 工程依据：[Compose 项目与资源分组](https://docs.docker.com/compose/intro/compose-application-model/)、[容器服务职责划分](https://docs.docker.com/engine/containers/multi-service_container/)、[显式复用持久卷](https://docs.docker.com/reference/compose-file/volumes/)。

## 兼容性要求

- `.env.web` 既有配置、端口和启动命令兼容；迁移生成的本机资源映射不进入 Git，不输出密钥。
- `sandbox:setup/start/stop/status` 继续可用，统一引用同一项目；单独停止沙盒不影响数据库和聊天流。
- 生产 Compose、CD、API 与消息流协议保持原有行为。

## 验收标准

- [x] 新环境与完成迁移的旧环境均只有一个本地项目分组；服务数量和功能开关符合声明，无重复容器。
- [x] 普通启动、沙盒启动、外部服务、重复启动、启动失败和 `Ctrl+C` 按归属正确处理。
- [x] 旧数据库与沙盒状态保留；迁移失败回滚成功，无空库替换、同时写卷或误删。
- [x] API 与 worker 分进程下，正文实时增量、完成保存、中断、手动重试和刷新读回正常。
- [x] 员工与管理员的工作、报告、附件、记忆和权限流程回归通过。
- [x] 真实沙盒代码执行、内置工具、文件生成／下载及连续修改通过，隔离限制和清理有效。
- [x] 定向故障注入及资源残留检查通过，受影响的既有测试通过；无法验证的项目明确标注，不用 mock 代替真实容器结果。
- [x] 更新启动／迁移／回滚说明，交付实际测试结果与限制。

回归保留 1 项既存测试失败：旧 `review` 分支断言仍等待已移除的模型二次核对。Windows 退出仅验证参数分支，未实机验收；远端 CI 未触发。

## 待确认问题

无。采用统一分组与本地范围，保留四个服务；CI 增加对应测试，CD 不变。
