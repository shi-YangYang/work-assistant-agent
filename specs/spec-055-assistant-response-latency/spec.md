# Spec 055：聊天搭子响应速度与等待优化

## 状态

传输与持久化改造已通过原独立验收；新会话普通写作的长等待已复现，整体性能目标尚未完成。已进入共用主模型流程返工，实施与验收要求见 [长等待返工方案](rework.md)；该方案替代下文旧的强制收尾方式。原工程验证与性能限制见 [验收报告](acceptance.md)。

## 背景

聊天搭子的知识问答、写作和工具任务均存在较长等待。取消在线额外模型审稿后，已有六轮真实请求仍累计耗时 395.93 秒。回答质量已接受的知识、日期和措辞问题保留样本，不在本 Spec 继续专项修补。

## 目标

- 分开测量等待首字、持续输出和完整任务完成时间，定位排队、模型请求、工具、数据库及浏览器呈现的实际耗时。
- 减少收尾补调、重复生成正文、重复下载网页；将正文流传输与聊天数据库持久化分离。
- 保持现有任务能力、授权、来源、取消、恢复和打字效果；明确哪些时间来自外部服务、哪些可由本系统优化。

## 非目标

- 不增加快慢模式或新的用户设置，不改管理员模型配置、用户思考强度、输出长度意愿和重试次数。
- 不通过缩短答案、跳过必要工具、删除授权检查、扩大总时限或提前宣称成功提速。
- 不引入另一个模型、额外意图路由模型、跨用户回答缓存或新的浏览器后台轮询。
- Redis 仅用于临时流与恢复缓存，不接管任务队列、业务数据库、Agent checkpoint 或长期记忆；不建设通用消息平台。
- 不重做全站 UI，不全量重跑 Spec 054，不以纠正模型知识题为验收目标。

## 当前行为

本次实施对照基线为 `4e4da8a`，已解除正文固定字符限制并保留 2 MiB 单行 SSE／非流式响应保护，不回退这些行为。以下为此前 `70ba0f7` 隔离环境中使用 `deepseek-v4.1-flash / low` 的真实记录，计时从发送到终态及 API 读回，不代表首字时间或稳定延迟分布。

| 任务               | 完整耗时 | 模型请求累计耗时 | 模型调用数 | 已观察到的额外工作                         |
| ------------------ | -------: | ---------------: | ---------: | ------------------------------------------ |
| 列表／元组问答     |   26.72s |          25.402s |          2 | 一次收尾协议补调                           |
| 约 150 字祝福      |   14.37s |          12.289s |          1 | 长度字段再次包含全文                       |
| 读取 csv 官方文档  |   66.31s |          50.854s |          4 | 三次读同一网页，一次收尾协议补调           |
| asyncio 实测与来源 |  231.31s |         171.652s |          6 | 三次执行代码、六次读取网页，含同页重复读取 |
| 创建工作           |   18.47s |          16.691s |          2 | 包含独立操作授权                           |
| 继续修改工作       |   38.75s |          36.825s |          4 | 包含变更范围提取、授权和主 Agent 调用      |

来源：[真实任务记录](../../artifacts/spec054/20261008-direct-answer/report.md)、[逐轮耗时](../../artifacts/spec054/20261008-direct-answer/readback.json)。模型请求累计约 313.71 秒，占上述总耗时约 79%；这个区间也包含网络、回调写库及请求收尾，不能全部归因于供应商推理。并行场景不得直接相加成关键路径耗时。

已确认的实现路径：

- `harness.py` 在模型输出普通正文而未调用 `finish_task` 时，再调用模型包装正文和任务元数据。`ReplyCandidate` 只展示符合条件的 `finish_task.answer`，普通正文不会提前展示，因此补调也可能推迟首字。
- `AnswerLength.body` 要求模型复制完整计数正文。长文可能在答案生成后继续重复输出，用于本地计数。
- `web_fetch` 每次都下载、提取整页，再按 `offset/find` 返回片段。同页换词、翻页仍重新请求外站。
- `chat()` 读取流时直接等待 `on_delta → ReplyPublisher.write`；发布执行来源校验与数据库事务，最短写入间隔为 200ms。慢数据库可能反向拖住分片消费；尚无分段数据量化实际占比。
- worker 空闲时最多等待约 1 秒再领取任务；SSE 服务端每 500ms 获取一次状态；前端平滑输出每批最多追赶 480ms，终态直接显示。不能将这些小等待解释为几十秒或数分钟耗时的全部原因。
- 模型请求目前每次创建 HTTP 客户端；所有业务工具与较长规则进入主 Agent。连接复用、上下文体积及连接池竞争是待测候选，不预先认定为瓶颈。
- API 与 worker 独立运行，现有依赖没有 Redis；进程内字典不能直接用于二者通信，不能仅删除写库而保留原 SSE 读取路径。

## 调研依据

- Open WebUI `v0.11.1` 将生成中的正文保存在内存／Redis，结束时写入最终结果，取消时保存部分内容：[流式处理源码](https://github.com/open-webui/open-webui/blob/v0.11.1/backend/open_webui/utils/middleware.py#L5672)、[临时缓存源码](https://github.com/open-webui/open-webui/blob/v0.11.1/backend/open_webui/tasks.py#L153)。
- LibreChat 将生成任务、事件传输和恢复存储分开，提供内存及 Redis 实现：[已合并的流式恢复设计](https://github.com/LibreChat-AI/LibreChat/pull/10926)。
- [Open WebUI 刷新丢失前半段显示的问题](https://github.com/open-webui/open-webui/issues/29596)说明恢复快照必须与后续增量正确衔接；[LibreChat 切换会话后未保存的用户报告](https://github.com/LibreChat-AI/LibreChat/discussions/13338)列为故障用例参考，其根因未获维护者确认。
- 以上是公开项目的具体实现，不代表 ChatGPT、DeepSeek 网页端公开了数据库写入频率，也不证明本项目已有固定幅度的性能收益。

## 目标行为

普通问答／写作在正常格式下用一次主模型请求完成交付；有必要的搜索、执行和业务授权仍按真实流程发生。同一任务读取同一网页的不同片段复用已获取的页面。已获准展示的正文通过临时流通道送往浏览器，在完成或中断时持久化；切换页面或断开浏览器连接不影响后台生成和最终保存。

## 功能需求

### 1. 可归因的分段计时

- 区分消息被 API 接收、任务领取、附件／上下文准备、每次模型发送／首个有效事件／首个可展示答案／结束、工具起止、临时流发布／来源校验／SSE 发送、最终写库及完整终态。
- 模型调用区分主任务、协议修正、变更范围、授权和上下文压缩；记录输入／输出用量和额外调用原因。
- 浏览器验证记录发送、首个答案实际绘制、终态绘制；思考状态、心跳和隐藏推理不算首字。业务回执直接完成或团队权限禁止预览时，注明没有正文流，不能伪造首字指标。
- 使用关联的 job／attempt／fence／call ID 与单调时钟计算同进程耗时；跨进程只报告可关联事件，不直接相减不同进程的单调时钟。工具并行区间及嵌套请求不重复加总。
- 复用现有日志与用量记录，不新增数据库 migration、公开诊断页面或逐 token 写库。日志不保存密钥、完整正文、私人材料和隐藏推理；测试原文仅进入隔离评测产物。

### 2. 普通正文与业务状态分别交付

- 普通正文正常结束，不再要求 finish_task 包装完整答案或补调模型；聊天与业务共用精简后的主模型请求，保留全部必要工具。
- 业务写入、确认、持续指令与任务承接使用真实回执和显式结构化操作；不从自由正文猜测授权、业务成功或任务状态。
- 流式正文可使用极小、严格定界的内部交付标记，标记本身不展示；不含标记的合法普通正文仍可终态交付。不能要求主模型填写与本次任务无关的整套收尾字段。
- 普通 assistant content 可能是工具前说明；团队来源、撤回、混合调用与取消边界保留，不无条件透传全部分片。
- 旧 finish_task、Delivery 与 checkpoint 保留读取及恢复兼容；恢复不重新要求普通回答填写整套任务表单，坏结构不能被当作成功。授权、变更范围独立提取和真实回执收尾继续保留。

### 3. 移除额外字数交付协议

- 用户篇幅要求原样交给模型，不要求声明长度引用、单位、正文范围，也不要求计数证明或重复正文。
- 移除在线字数自动提取、计数验收与长度不符后的自动改写；不另加分类器或替代性核对流程。
- 旧长度字段与标记只作读取兼容，不再触发字数核对或额外模型调用；流式预览可保留固定空标记。
- 离线评测仍如实记录实际篇幅与质量，不因取消在线门槛就把原有不足样本改判通过。不缩短用户原始要求，不承诺精确字数保证。

### 4. 任务内网页快照复用

- 将安全下载／提取与片段读取分开。同一任务执行中的同一规范 URL，可从同一份已读取快照执行 `offset/find/match_index`，并合并同页同时发生的下载。
- 快照只在本次 RunContext 生命周期使用，最多保留 8 页、累计 8 MiB，最长复用 120 秒；超限淘汰，任务结束释放。计量须覆盖文本与链接等实际缓存负载，不仅计算 URL 长度。
- 新消息、重新执行的上下文与过期快照不共享缓存；用户要求重新读取最新页面时支持绕过快照。失败与未授权访问不缓存为成功。
- 保留原始 URL、最终 URL、抓取时间、片段边界和真实来源。缓存命中只表示重读已取快照，不声明又进行了一次联网获取；发现链接仍不等于读取目标正文。
- 新下载仍执行 URL、DNS、IP 固定、重定向、类型和大小检查。缓存不得扩展到业务记录、登录网页、搜索结果或其他用户材料。

### 5. 正文流与持久化分离

| 数据                             | 保存时机与位置                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------ |
| 用户消息、任务身份               | 请求接收时写 PostgreSQL，保留现有幂等规则                                                  |
| 正在生成的正文                   | worker 有界缓冲 → Redis 临时流／快照 → API SSE，不反复写 `Job.feedback` 或 `Message.reply` |
| 完整回复                         | 交付与来源校验通过后写 PostgreSQL，再发布成功终态                                          |
| 普通报错或用户中断的部分正文     | 经授权后保存一份中断快照，不冒充完整回复，不自动作为成功答案加入后续上下文                 |
| 工具回执、业务修改、任务关键状态 | 继续在相应步骤及时持久化，不能等到整条回答结束                                             |

- 每次生成只创建一个受管理的发布任务，合并短时间内的增量，使用有界缓冲；流消费不等待数据库事务或每个 Redis 往返，不为每个 token 创建后台任务。
- 正常传输只携带新增正文；新订阅、序号缺口或前缀被替换时发送一次带游标的完整恢复快照。不在每个事件中携带全部历史正文或重复节点列表。
- API 直接订阅正文事件，不等待原有 500ms 数据库状态快照。任务节点、操作卡片的既有状态同步保留，禁止把它重新用作正文传输通道；这次不重构全部任务通知。
- Redis 为私有跨进程通道，按公司、用户、job、attempt、fence、generation 隔离；事件另带 call ID 和单调序号。旧尝试、重复及乱序事件不能覆盖当前内容。
- 开始、来源变化和公开预览前继续执行既有归属、角色、租约、输入版本及材料检查。权限查询可影响预览发布时间，但与上游消费分离；不能通过缓存权限放宽现有边界。团队来源继续禁止未经完整校验的预览。
- 撤回、租约变化、资料失效、内容审核或协议错误使旧生成失效，清除不允许展示的临时正文，不持久化为可读中断答案；终态之后禁止晚到增量恢复旧内容。
- 保留现有打字效果；首次有合法正文即可显示。完整结果保存后，终态直接显示全文，不继续等待动画队列。

### 6. 恢复、异常与资源边界

- 后台生成和最终保存不依赖 SSE 订阅人数。切换会话、刷新或浏览器断网只关闭订阅，用户点击中断才执行取消流程。
- 保留现有一次性恢复入口，不增加自动重发 POST、无限重连或轮询。重新订阅时先校验权限，再原子衔接快照游标和之后的增量，既不缺字也不重复。
- 正常完成须先提交最终正文／任务状态，再通知终态并释放临时流。保存失败不得显示成功；保留可用缓冲，按现有有界失败处理，不重新调用模型或重放工具来补保存。
- 用户取消由持有新 fence 的取消流程封存已授权前缀；旧 worker 不能再写正文。普通模型错误可保留已授权部分内容，删除会话和来源撤回清除缓存。
- Redis 中断／容量不足时，停止本次流预览并提示，后台仍可完成与保存；通过既有终态同步取得结果。不得悄悄恢复高频 PostgreSQL 正文写入，不自动重新生成。
- Redis 是可丢失的临时缓存。API 重启可从仍存活的缓存恢复；worker 崩溃或 Redis 重启可能丢失未持久化尾部，不承诺崩溃后无损续写。已保存消息和工具回执保留，任务按现有租约／checkpoint 恢复；不能因缓存丢失宣称业务操作未发生。
- 临时流需设置每条字节／条目上限、总内存上限和 TTL；慢订阅者通过新快照追赶，不无限积压增量。达到缓存上限不截短最终答案、不调小模型输出上限；完成、失败、取消和退出均关闭后台发布任务与连接。

### 7. 次要瓶颈按证据处理

- 分段结果若确认连接建立、无变化的上下文构造、重复查询或 worker 等待占明显开销，可在原模块内减少重复操作；先记录改善对象和对应证据，不扩大为整个基础设施重构。
- HTTP 复用若实施，须按 origin、安全配置和进程生命周期隔离，正确关闭连接；不能复用可变 scheme 校验状态、默认鉴权头或跨用户请求数据。
- 保留工作变更计划现有缓存与失效规则；不跨消息复用授权结论，不裁掉约束、否定、版本或用户资料换速度。
- 首轮不调整 worker／沙盒并发、数据库连接池、总时限和服务器资源。4 核 8 GiB 环境下的竞争先测量，不以增加并发承诺缩短单条消息时间。

## 边界条件

- 外部模型首字慢、联网不可用、冷启动、限流和必要工具运行均单独归因；耗时不足以证明模型能力差或工程存在死锁。
- 未触发持久化权限校验不能显示成功；最终结果仍以数据库和实际工具回执为准。
- 长文、中文／Emoji、分片 JSON、模型返回普通正文、旧任务恢复、附件和工作引用保持兼容。
- 已接受的回答质量样本如再次答错，如实记录，不因此启动额外核对或反复重跑到绿。

## 技术约束

- 文档按 S0，仅检查 diff 与引用；实施涉及交付协议、异步资源生命周期和来源隔离，按 S3 选择相关子系统验证，不默认全项目重测。
- 新增 Redis 服务及异步客户端，限用于正文流。复用现有 FastAPI、任务上下文、SSE 入口和评测设施，不把 API 与 worker 合并为单进程。
- PostgreSQL schema 不变；扩展 SSE 增量事件和版本协商，保留现有快照与历史消息读取。新工具参数兼容旧输入，内部可选计时不改变公共 HTTP 响应。
- 本地启动、Compose、发布和相关 CI 同步配置临时流依赖；正式 Redis 不暴露公网，测试使用独立命名空间，不能清理其他实例数据。具体资源预算见计划。

## 兼容性要求

保留两种人设、三档执行权限、账号隔离、管理员团队资料边界、持续任务、业务幂等、引用／附件、记忆、压缩、断线恢复、取消和用户选择的思考强度。模型配置不被静默修改。

## 验收标准

- [x] 报告分别列出首字、模型请求、工具、授权、协议补调、发布和完成时间；未测区间明确标记，不再把完整请求耗时当供应商纯生成时间。
- [x] 受控正常问答与写作路径一次主模型请求完成；未支持工具选择、格式损坏和旧任务走明确兼容路径，无无限重试、工具重放或权限放宽。真实模型的额外调用单列，不保证任意输出永远无需修正。
- [x] 新回复不要求长度元数据或整套任务表单，不因字数差异自动改写；旧字段、任务恢复和真实业务状态保持兼容。见[移除负担验收](acceptance-burdens.md)，不代表整体性能目标完成。
- [x] 同任务、有效期内同页三次不同片段读取只下载一次；新任务、过期、显式刷新及缓存淘汰正常，恶意 URL 和失效来源仍被拒绝。
- [x] 受控长回复的中间正文不写 PostgreSQL；增加分片数量不会增加正文保存次数，任务／工具／checkpoint 写入单独统计。
