# 助手长等待：兼顾回答质量与业务正确性的修复方案

状态：实施中。原型仅提供可行性证据；最终业务、恢复与浏览器结果须通过返工验收。

## 诊断结论

新会话只有一条用户消息、12 字跨会话记忆，仍发生 324.43 秒单次模型调用。消息创建到模型调用约 0.45 秒。绕过数据库、Redis、worker 和浏览器，直接重放其请求，仍出现长时间无正文。

同一服务、`deepseek-v4.1-flash`、`max`、用户原文“写一篇1000字作文”的对照：

| 请求                                                 | 结果                                          |
| ---------------------------------------------------- | --------------------------------------------- |
| 仅发送用户原文                                       | 18.98 秒；1033 个汉字                         |
| 当前完整 Agent 请求                                  | 一次 171.47 秒；再次到 120 秒诊断截止仍无正文 |
| 仅缩短系统规则，保留全部工具和完整收尾               | 120 秒仍无正文                                |
| 仅保留 `finish_task`，系统规则不变                   | 120 秒仍无正文                                |
| 简化通用规则、普通正文交付，保留全部 32 个业务工具   | 24.98／24.97 秒；818／767 个汉字              |
| 在上一原型中重新加入完整 `finish_task`，但不强制调用 | 120 秒仍无正文                                |
| 保留原结构，只提示将机械字数统计交给程序             | 120 秒仍无正文                                |

171.47 秒样本用了 13,399 个推理 tokens、884 个正文及工具参数 tokens。没有第二次审稿或实际工具执行。输入规则、工具收尾约束与当前模型共同触发过量生成前推理；不是只有数据库、提示长度、强度或某一字段能单独解释。

通用写作也必须提交 `finish_task.answer`、任务关系、持续指令、业务声明、核验声明和长度元数据；普通正文反而被当成缺少协议，可能再次请求模型包装。这是需要解除的结构性耦合。将 `required` 改回 `auto`，或追加“不要反复思考”，均不足以解决。

其他对照：原流程回答“你是谁”仍只需 9.15 秒；精简原型写《我的妈妈》用 18.31 秒、911 个汉字；工作修改请求在 3.09 秒选择 `find_work_items`。后者只验证工具选择，未执行真实工作修改。

原型不是上线结果：767 字样本未达到现有 800 字下界；不得把它算作完整通过。上述均为少量样本，120 秒是诊断截断，不是完成时间；不能据此承诺 p95、稳定降幅，或认定某个提交是唯一原因。变更前提示／工具重放也出现过长等待，不等于完整旧运行环境回归。

## 业务操作的实际瓶颈

此前同进程的“修改刚才创建的工作”流程总耗时约 362 秒，阶段记录如下：

| 阶段                                     |      耗时 |
| ---------------------------------------- | --------: |
| 主模型决定读取工作                       | 325.64 秒 |
| 读取工作                                 |   0.07 秒 |
| 主模型根据工作内容提出修改               |  17.15 秒 |
| 独立提取修改范围，两次调用含一次失败重试 |   6.61 秒 |
| 核对操作授权，两次调用含一次失败重试     |   8.33 秒 |
| 最终任务保存                             |   0.04 秒 |

模型核对时间已包含在业务工具耗时中，不能重复相加。主要等待发生在第一次读取工作之前；取消全部范围与授权检查也不能解决这次长等待。当前业务链仍需完整对照验证，普通回答的原型提速不能直接当作业务流程的提速结论。

已存在的优化继续复用：相同用户来源、目标版本等条件下缓存独立变更计划；确认整个请求已由一条真实回执完成时直接收尾。不能把它们重新计为本次收益。

## 官方实践对照

以下是公开开发建议，不代表 ChatGPT／Claude 网页版的完整内部实现；供应商专有 API 能力也不能直接视为当前 DeepSeek 服务可用。

- [OpenAI 延迟优化](https://developers.openai.com/api/docs/guides/latency-optimization)：减少重复请求与多余结构化输出，独立步骤可并行，固定操作回执可由程序生成。单纯压缩输入长度通常收益有限。本项目重点削减协议要求的额外推导和包装，不缩短用户要求的正文。
- [OpenAI 工具检查与审批](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)：检查应放在对应输入、输出或工具边界。写入前完成必要检查；不能用推测执行提前修改数据。已有依赖关系的范围提取、提案核对和写入不强行并行。
- [Anthropic Agent 模式](https://www.anthropic.com/engineering/building-effective-agents)：增加步骤应有可测收益；反复评审适合有明确评价标准、改写确有帮助的任务。本项目保留针对性业务校验，不把每个离线失败都转换成线上通用审稿步骤。
- [Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：规则清晰、工具职责明确，避免不断堆叠例外；精简仍须覆盖必要行为。本项目保留原文、目标版本与业务约束，移除重复说明，按操作提供专项信息。
- [Anthropic 工具使用](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)：普通文本回答和结构化工具调用各有用途。本项目保留动作与任务状态的结构化合同，正文无需为完成交付再包装成工具调用；不从自由文本抽取业务授权。
- [Anthropic Agent 评测](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：评测同时看环境真实结果与交互质量，在固定任务上追踪延迟、用量及错误。本项目把质量基线和线上业务检查分开；提速对照必须核对最终数据，不能仅凭助手说“完成”。

## 推荐方案

1. **普通正文成为正常终态。** 主 Agent 可以直接回答，也可以调用工具；不把 `finish_task` 放进每次普通生成的工具表，不要求将完整答案装入工具参数。普通回答正常结束不补调模型包装正文。
2. **正文与任务状态分别处理。** 写入成功、待确认、执行中、取消、等待问题回答，分别由真实业务回执和交互记录决定。持续指令变更、明确承接未完成任务使用单独的结构化上下文工具及现有原文引用校验，不再与整篇答案绑定。不从普通正文猜测授权或成功；纯聊天结束不覆盖待确认的业务状态。
3. **通用规则精简，业务规则就近使用。** 主模型保留身份、当前请求、用户记忆优先级、工具能力和安全边界。具体工作字段、报告、督办、持续授权等规则归对应工具／授权路径，必要时随相关工具结果提供。沿用服务端角色过滤、访问控制、版本、授权和幂等，不增加分类模型或关键词意图路由器。
4. **移除额外字数协议与普通回答表单。** 用户篇幅要求原样交给模型；不要求长度引用、单位、重复正文或计数证明，不再自动提取字数要求、验收计数或因字数差异调用模型改写。旧长度字段只作读取兼容。普通回答及旧任务恢复不强迫填写任务目标、业务／核验声明和完成度表单；真实回执、提问、持续指令及已知未执行项继续维护任务状态。离线评测仍记录实际篇幅，原有 767 字不足样本不改判通过。
5. **复用现有流与保存链路。** 合法普通正文接入现有候选、来源校验、撤回和 Redis 通道；不是将所有 `delta.content` 无条件透传。团队资料、工具前说明、同批混合调用、取消、旧 generation 与断线恢复仍按原边界处理。最终正文和真实回执仍写 PostgreSQL。

6. **业务操作与普通回答共用精简后的主模型请求。** 不是只为聊天增加快速旁路。先解决读取工作之前的主模型长等待，再优化各业务操作的专项核对；不以减少必要检查次数作为首要指标。
7. **独立校验保留，减少重复推导和无关输出。** 工作变更范围仍从用户原文独立提取，不能让修改提案反向影响范围；该计划不等于授权。专项授权检查复用已验证的范围，只判断当前动作的目标、授权与内容是否吻合，避免再次生成整套相同字段清单。只有能由现有计划和程序校验完整承接的重复字段才可移除；报告事实核对、真实原文引用、用户确认、版本冲突、权限及幂等检查保留。按动作收窄输出结构，修复具体格式失败，不能把重试上限提高来掩盖失败。

实施分两步：先改所有任务共用的主模型请求与交付协议，保持业务校验语义；对照验证后，再按实测证据精简专项校验的重复输入输出。任务未完成或存在剩余步骤时不能提前用成功回执结束。

保留用户选择的模型及思考强度、2 MiB 单行传输保护、必要工具、节点重试和总时限。单独记录推理／正文 token 数与首个正文时间，不记录推理内容。暂不继续优化连接池、数据库或扩展超时。

## 实施范围

### 完整对照后的补充返工

共享正文协议首轮真实对照没有整体提速：1000 字作文 182.02 → 188.91 秒，续聊修改 258.26 → 334.35 秒；创建工作 96.66 → 14.13 秒。质量与实际写入通过，不能把创建收益推广到全部任务。完整记录见 [共享流程对照](../../artifacts/spec055/shared-flow/benchmark/comparison.md)。

新请求仍携带 4,465 字符系统提示、23 个工具和 30,467 字符工具定义。按实际作文输入进行请求层探测：精简通用说明并去掉任务状态工具定义用 45.98 秒、903 汉字；精简通用说明与按需能力入口用 44.90 秒、925 汉字。两者均未执行业务工具，不是完整流程验收，也不能据此把收益归于某一个字段。另一组仅减少工具而保留长规则得到 56.62 秒、篇幅不足，保留为失败样本。

继续采用以下实现，不增加模型分类器或新的用户设置：

- 主提示只保留通用行为、角色、当前权限、人设与交付边界的精简表达；移除重复样例和同义规则，不改变两种人设、用户要求与事实优先级。
- 工具分能力提供，通过本地 `load_tools` 加载具体定义及专项说明；由同一个主模型按需选择，不按用户关键词路由。普通问答无需加载工具，也不增加前置分类请求。
- 加载状态限定到当前任务及 scope，恢复后可读取；不串用户、不跨新任务自动沿用。能力目录按角色和执行服务可用性过滤。
- 工具可见性不是权限边界。现有工具仍受原访问、授权、来源、确认、版本和幂等检查；旧 checkpoint 中已登记的工具调用保持兼容，不能因按需加载重放已成功操作。
- 业务、材料、公开检索、文件计算、记忆和任务上下文均可被发现。加载工具仅提供能力说明，不读取私人资料、不授予写入权限，不额外消耗业务工具步骤配额；实际调用预算不提高。
- 已发现的真实工具额度拒绝必须保存具体未执行项，收尾沿用 blocked；仅达到软封口阈值、实际查询都已执行时仍正常完成。复现与返工见 [独立验收](acceptance-shared-flow.md)。

## 验证与交付门槛

- 实施前固定样本与判据；同配置测首个正文、首次工具调用、实际业务完成、总耗时、推理／正文用量、实际篇幅和额外请求。先判质量与业务正确性，再比较时长；失败、超时和修复耗时全部保留，不挑快样本。
- 普通问答、写作、旧长度标记和旧任务恢复覆盖定向测试；确认没有字数或普通表单补调，业务失败与未完成项仍被保留。移除协议本身不要求重跑真实模型基准，也不据此宣称整体提速；后续性能评测仍记录内容不足和完整耗时。
- 在隔离数据上验证创建→继续修改、只分析不保存、持续指令生效／撤销、澄清→继续、提交／删除确认与自主执行。核对真实数据和回执，不以工具选择代替流程通过。
- 业务断言覆盖选对工作、只改指定字段、不遗漏同组修改、局部完成不误改整体状态、追加保留旧内容、报告不虚构事实；不能只检查接口返回成功。工作修改和多步骤任务必须完成端到端实测。
- 回归来源撤回、跨用户隔离、混合正文与工具、旧 checkpoint、取消、刷新和断线恢复；不得重放已成功写入。
- 先跑受影响后端子系统，再用真实模型与浏览器验证最终实现。原型的 18～25 秒只能作为可行性证据，不能代替端到端验收。
