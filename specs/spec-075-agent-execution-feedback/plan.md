# 执行反馈与写入前提问：实施方案

## 对应 Spec

[Spec 075](spec.md)。先完成本地实现与验证，生产发布另行处理。

## 涉及模块与数据流

```text
用户原文 + 已授权会话来源 + 工作引用 + 成果集合
  → 主模型判断影响结果的歧义；必要时直接提问并等待用户回答
  → 解析操作意图、来源范围与目标
  → 意图／字段核对 + 业务权限、版本校验
      → 有效用户缺项：程序持久化现有提问框并暂停，收到答案后续接
      → 参数／服务／权限问题：保留原修复或失败分支，不向用户索要授权
  → 执行模式决定直接执行或批准
  → 真实写入与持久回执

任一步失败
  → 结构化原因 + 恢复责任 + 缺项／证据版本
  → 复用结果 / 一轮必要修复 / 最小澄清 / 结束对应事项
  → 任务状态与公开业务说明
  → 流式消息、操作卡、刷新与任务续接

内部诊断留在受控记录，不直接成为公开业务说明
```

- 范围解析复用 `agent/context/references` 与 `actions`，不得创建新的权限事实来源。
- 错误契约和任务恢复结合 `actions/task_outcomes`、`runtime/tool_progress`、`tasks/feedback`，区分按原子操作判断与整个任务的完成度。
- 公开 DTO 在服务端转换，Web 只消费适合用户的字段；不能只在一个 React 组件隐藏错误。
- 普通正文仍由原有主模型正常生成。已有核对确定的有效用户缺项（包括目标和范围同时缺失）直接进入现有交互，不局限于已选材料仅缺位置；复用已通过恢复契约校验的问题，不公开内部原因，不增加问题改写模型。不把候选目录或模型提案当作用户选择。
- 优先让主模型主动提问；工具链在真正执行前承担兜底。保持现有工具名、checkpoint 和问题答复 API，不另建一套 LangGraph interrupt 恢复协议；已有持久交互和等待机制足以表达暂停。明确请求不新增模型核对、不强制确认；结构化结果不完整或不一致仍按内部错误处理。

## 当前工具链返工

- 最新 high 样本的授权核对已经同时返回有效 `target/materials` 缺项，但程序仅接管材料集合的单独位置缺口，导致主模型再次改写提问。修复这一分支缺口，不继续增加提示词。
- 在业务写入前将已验证的缺项直接转换为持久问题；目标选项仅使用当前有权读取且版本有效的真实对象。无法构造安全选项时保留开放回答，不从候选中默认选择。材料含义未明确时不得限定成全部生成文件。
- 等待时依赖写入停止，回答后按原真实用户答复重新核对与续接，保留幂等、版本及所有权限边界。不自动恢复旧失败或已取消任务。
- S3 范围仅限此写入边界：复用上一真实 high 普通结构化返回作确定性回归，核对暂停、无写入、问题持久化、回答续接；同时检查明确请求不多问以及内部错误不变成提问。之后固定 E00-A low/high 与明确引用 E01 low/high，真实模型各一槽并保留全部结果，失败时不无依据扩大。


## 当前收敛验证：主动澄清

- 本轮先交付窄修改与现场同构开发环境验证，不继续自动扩展为此前 68 槽全矩阵；全 Spec 未覆盖项继续标记未验收，旧失败记录保留。
- 使用原脱敏历史、11 份成果及同样原话。本次工具链返工固定执行首次请求 E00-A 和明确引用 E01，`low/high` 各一次；携带旧拒绝的 E00-B 保留已有结果，本次未重测。冻结原 manifest 和结果不改，原件内容仍是已披露的合成短文件，不能声称还原员工原始文件。
- 本轮统一使用 `full` 验证自主执行下的主动澄清；线上第一次实际为 `auto`，此差异明确记录，不再说所有配置完全等同线上。不预设模型必须理解成保存文件，也不将程序生成问题当作模型主动提问。
- 记录模型真实问题、首个可操作问题耗时、总耗时、调用顺序和零写入。通过真实开发 API／worker 与浏览器提问框，使用测试者明确回答“生成的文件、全部保存到已有目标”，再验证保存、刷新与不重复；这是测试选择，不代表孙建芳真实意图。
- 补一个明确工作引用的正常请求，检查不产生多余澄清。相关工具目录／交互回归通过后不重复；不新增固定模型调用，字符和工具 Schema 变化如实记录。

## 修改顺序

1. **冻结基线与问题清单。** 记录实施起始 SHA、模型／服务配置、`low/high` 设置、任务输入、附件及数据库种子。用脱敏数据重建多轮材料与工作场景，保留未修复版本真实输出。确认传给主模型和核对器的来源、目标及历史拒绝的差异。
2. **检查并统一失败契约。** 列出受影响工具及状态生产者、消费者，梳理 `category/state/message/reason/nextAction`。将恢复责任、缺项、公开说明和诊断明确分开；不靠诊断自然语言关键词决定授权。
3. **修复来源与目标解析。** 优先修正数据遗漏、作用域错误和错误复用；已有结果足够时不额外调用模型。保留独立权限边界，检查“全部”、明确承接、版本和多目标场景。
4. **修复恢复与澄清。** 在已有拒绝缓存和无进展机制中计入修复范围、事实版本与操作身份，处理跨动作改道。复用已成功回执；内部错误不生成用户问题。用户答复能继续，旧拒绝不长期封锁新事实。
5. **治理公开反馈。** 依次覆盖工具输出、任务汇总、节点 DTO、操作卡、正文交付与流式发布。替换原有重复提示，补安全兜底与旧结构化数据兼容；检查普通技术答案不受影响。
6. **验证并收敛。** 先执行相关确定性检查，再进行同一用例 `low/high` 前后对照和 Web 流程验证。独立验收 Agent 核查结果与副作用；发现同根因缺口返工，范围外问题单列。

## 接口变化

- 在既有工具结果和任务结果中表达稳定原因、恢复责任、明确缺项与候选、证据版本、用户业务说明；完整诊断单独保留。复用现有枚举和结构，不先增加一套全局异常框架。
- `missing_info` 必须有可由用户解决的真实问题；未知或矛盾结果不能直接变成 `needs_input`。
- API、SSE 和历史读取保持一致的安全展示规则。若必须扩展公开字段，同步 `packages/api-contracts` 及对应消费者；不得直接公开内部恢复详情。
- 不用“是否成功解析为 JSON”代替业务一致性判断，不以模型的一句“用户已授权”替代真实来源。

## 完整流程用例

测试用普通员工会说的话；下表中的数据、作品和同事均使用隔离测试素材。

### E00：线上员工场景优先复现

这是本次必测主案例，先于简化用例执行。以已查到的线上消息、任务和关联记录为依据，只读核对后在隔离环境脱敏重建；不操作员工线上账号，不把员工文件和整段聊天原文提交到仓库。

保留影响判断的条件：

- 使用自主执行 `full`；现场模型为 `deepseek-v4.1-flash`，配置为 `low`。先按现场档位复现，再用相同场景测 `high`；模型或服务已不可用时明确记录差异，不称完全复现。
- 保留多轮文件生成与修改历史，共 11 份成果，包含 Word、Excel、PPT 和两组同主题不同版本的成果。稳定 ID、实际版本、生成顺序、条目与工作关联以记录为准，不能按名称合并，也不能仅伪造一个“已有 11 份文件”的提示。
- 保留已有的资料整理工作及其内容、修订、一个已绑定附件；不能为了让测试成功额外添加现场没有的明确目标引用。
- 保留保存前的普通问答、一次“添加到 我的工作 里面”的取消记录，以及两次“之前的 都添加到 我的工作 里面”的先后关系。取消前是否已有副作用以真实记录为准，不自行假定。
- 第二次请求前已有的未完成任务、拒绝理由、助手澄清回复与来源映射均属于关键条件，不能清空历史后当作全新会话测试。

分开验证两个固定切入点：

| 子例  | 固定初始状态                                       | 目的                                             |
| ----- | -------------------------------------------------- | ------------------------------------------------ |
| E00-A | 首次完整保存请求前的会话与业务状态                 | 重现范围核对、错误澄清及更新／新建之间的无效尝试 |
| E00-B | 第二次相同请求前的状态，包含先前真实拒绝与等待信息 | 检查历史拒绝、恢复状态和重复请求是否加重阻塞     |

两版从各自相同的冻结快照起跑，不把修改版第一次执行产生的新状态混入 E00-B 的基线对照。另沿完整流程连续发送相同请求，验证修复后第一次若已成功，第二次不会重复创建或绑定；如果确实只缺目标，补充选择后能够完成。

脱敏保持材料含义、指代关系、重复版本和上下文规模，记录与生产上下文的差异。不得为凑出故障编造助手回复或强制真实模型输出某种拒绝；现场既有历史回复可作为冻结输入，但本轮回复必须来自真实模型。

复现报告逐项回答：是否出现同一范围误判、是否错误等待用户、是否跨动作探索、是否泄露内部说明、是否实际写入及耗时分布。没有复现某项就标记未复现；故障注入回归作为单独证据，不能声称它证明了真实模型复现。

### 其余流程与边界

| 编号 | 输入／前置                                                  | 核对结果                                                 |
| ---- | ----------------------------------------------------------- | -------------------------------------------------------- |
| E01  | 多轮生成 11 份成果 → “这些都加到这条工作”；已有明确工作引用 | 数量与版本完整，直接执行，不重复询问                     |
| E02  | “之前的都添加到我的工作里面”；上下文未指定已有或新工作      | 保留成果集合，只问保存位置；答复后完整保存               |
| E03  | 上述请求但已有明确工作关联，另有同名候选                    | 使用准确关联，不因同名误拦截或错写                       |
| E04  | “新建一条，把刚才的两个文件都放进去”                        | 合理默认标题及字段，真实创建，不重复授权                 |
| E05  | “把第二份和第四份加进去”，含同名文件、多成果版本            | 选中准确 ID／版本，未选材料不被保存                      |
| E06  | “只分析，别保存”“先给我看看再提交”                          | 不擅自写入／提交，自主执行仍遵从明确限制                 |
| E07  | 参数漏项或范围计划与已确认请求矛盾                          | 针对性修复后执行或准确报失败，不让用户重述               |
| E08  | 修复后仍失败，再换字段、步骤号、工具或改成新建              | 无新事实不绕过；必要的合法后续步骤不误杀                 |
| E09  | 同一请求重复发送、写入成功后断线或 worker 恢复              | 回执一致，无重复工作、绑定或提交                         |
| E10  | 用户补充目标／材料选择；此前任务为等待或曾取消              | 仅明确承接时续接，已回答问题不再问                       |
| E11  | 三项操作一项完成、一项真缺目标、一项暂时失败                | 结果逐项准确，成功部分保留，状态不混淆                   |
| E12  | 更新前版本变化；改为读取别人的或已删除对象                  | 合法冲突可恢复，越权或无效来源被拒绝                     |
| E13  | 正常生成周报／工作为空／生成并提交／子任务失败              | 来源与状态准确，空工作不造空报告，入队后不阻塞主对话     |
| E14  | 正常问答、读取文件、完成一条简单工作                        | 答复质量与原路径一致，不新增审核调用                     |
| E15  | 附件读取失败、搜索失败、代码执行失败、图片生成失败          | 保留有用限制与修复建议，不复述系统字段，不错误等待用户   |
| E16  | 分类写“缺信息”，但结构或理由表示助手能修复                  | 作为内部契约异常处理，不能直接补话，也不能默认授权       |
| E17  | 生成正文中夹带内部字段，且字段名被拆到多个流式片段          | 发布、最终、刷新结果一致，不先泄露后消失；正常流式不中断 |
| E18  | 用户问代码中的 `missing_info`／Schema 或引用一段报错        | 正常解释用户问题，不被关键词删除误伤                     |

E01～E13 的关键写入场景覆盖 `ask/auto/full`，以风险组合为主，不机械执行全部笛卡尔积。至少包含“生成多份成果 → 保存 → 刷新 → 追问”和“受阻 → 回答必要选择 → 继续 → 再次刷新”两条完整 Web 流程。

## 确定性检查

受控模型用于固定故障分支，必须经过真实参数解析、来源核对、权限、业务写入、任务推导和公开 DTO；不能绕过待验证的校验，也不能把这些结果称为真实模型对照。

```bash
npm run test:server -- tests/server/tasks/test_receipt_completion_state.py tests/server/agent/completion/test_response_delivery.py tests/server/scenarios/test_execution_feedback_workflow.py
```

Web 检查包含桌面和手机视口、实际 SSE、进度、操作卡、澄清提交、刷新、断线恢复。截图只用于必要展示证据，业务结果必须核对数据库和回执。

## 真实模型准确性与耗时对照

- 只测 `low`、`high`；基线和修改版使用同模型、参数、服务、输入历史、种子数据、附件和权限。真实模型故障复现与受控分支测试分开列出。
- 使用本地／隔离环境的真实消息提交与 worker 链路，不在生产账号上试写。凭证由既有配置加载，不打印、复制或入库到评测材料中。
- 每个用户场景两版两档至少一组。E00-A、E00-B、E07、E14 为固定重复核心，各做三组配对，交替运行版本；测试开始前固定清单和重复次数，不重跑到绿。E01／E02 作为较简单的对照，不能替代 E00。
- 记录完整真实回复、澄清问题、任务状态、写入数量／内容／版本、重复调用与副作用；工具成功不等于用户目标完成。测试问题和期望事实可以预设，模型回复不能预设或自行编造。
- 记录提交到首段有效正文／可操作问题、提交到最终完成、队列时间、各主模型／范围核对／授权调用耗时与次数、工具耗时、重试和阻断原因、输入输出 tokens。后台报告另记报告最终可用时间。
- 每个固定问题展示修改前后回复及耗时，汇总成功率、错误澄清、漏项、重复写入和内部说明泄露。只有小样本时报告中位数、范围及最慢样本，不声称可靠 P95。
- 正常路径模型调用数不得增加；E14 各档配对总耗时中位数及首段有效内容中位数，增幅不得超过基线的 10% 或 2 秒（二者取较大值）。超出即标记回退调查，不能直接归因网络。
- 故障路径必须满足有限恢复的结构性门槛，复现旧循环时应减少无效往返；不能以更快结束但漏保存、错误澄清或放宽权限算提速。总耗时下降须由真实样本支持，不预设降幅。
- 如外部超时、限流或模型波动影响对照，记录 HTTP／首事件／模型阶段等证据，保留失败样本并标记结论限制；追加配对须针对明确异常，不能无限复测。
- 输出到 `artifacts/agent-execution-feedback/` 的基线、修改版原始结果及对照文件；只有脱敏摘要和结论进入验收文档。

## 风险与处理

- **过度放行：** “全部”不等于任意对象；独立权限、来源与具体目标仍验证，负向用例必须通过。
- **继续误拦截：** 原请求、真实关联、缺项与核对输入一并记录到受控证据，不能只改报错文案。
- **恢复规则过强：** 允许新的相关事实和不同独立事项，拒绝只在同一证据版本、同一缺口生效。
- **隐瞒错误或破坏回答：** 业务限制保留；分清系统诊断与用户讨论的技术内容，流式与刷新同测。
- **新增延迟：** 不新增正常路径模型调用，不堆政策段落；对照分离队列、模型和工具耗时。
- **旧任务兼容：** 缺少新字段时使用安全业务提示，不依据未知旧字段恢复写入或生成虚假澄清。

## 迁移与交付

不计划 schema 迁移、目录迁移或历史正文回填；旧结构化结果使用兼容读取。新恢复状态必须可持久化、可幂等恢复，旧成功回执不可失效。实现与验收由不同 Agent 完成；验收记录实际覆盖、原始证据位置、回退及未执行项，不预填 PASS。生产发布不属于本次 Spec 编写。
