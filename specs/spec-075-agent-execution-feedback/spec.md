# Spec 075 — Agent 执行范围、受阻恢复与用户反馈治理

## 状态

实施中。已冻结修改前代码用于同输入对照；实现、真实模型验证和独立验收分别记录结果。生产环境保持不变。

## 背景

线上员工要求“之前的都添加到我的工作里面”，在自主执行模式下两次等待数分钟，最后仍被要求说明保存范围。另有“服务端没放行”“变更计划不匹配”等内部解释出现在用户回复中。本次沿同一处理链排查和修复同类问题，不以单条话术或单个员工为特例。

已确认的现场证据：

- 重新只读核对线上原始记录：账号当前为自主执行 `full`，第一次任务为自动审核 `auto`、第二次为自主执行 `full`。两次均在意图／范围检查中受阻，没有权限开关未生效的证据；此前将两次均记为 `full` 不准确。
- 两次请求约耗时 233 秒、387 秒，分别调用模型 11、12 次。后一次排队约 0.88 秒，模型调用累计约 378 秒；主模型配置为 `low`。
- 添加材料的提案被变更计划判为 `materials=preserve`，一次范围重提取后仍被拒绝。随后主模型继续查询、思考、尝试创建工作。
- 后续拒绝理由含“助手可自行修正的内部前置与范围问题”，但分类为 `missing_info`，最终转为等待用户补充。
- 此案例原始消息是保存成果到工作，未查到对应的周报生成任务；不能将它写成已复现的周报故障。

仍需通过复现确定：目标与材料关联是否充分传给核对环节、已有目标歧义是否被误编码为未授权、历史拒绝是否影响本轮判断，以及无进展控制为何没有更早结束尝试。其余同类场景是检查范围，不预先宣称都有缺陷。

## 目标

1. 明确区分保存意图、材料范围、目标定位、参数正确性和权限，避免把助手内部问题交给用户。
2. 自主执行时，对已明确且可定位的任务直接完成；真正影响结果的歧义只问必要问题。
3. 受阻后依据结构化原因修复或结束，减少重复探索和无效模型往返。
4. 用户只看到任务结果、真实限制及必要下一步；内部诊断继续可追踪。
5. 尽量不增加正常请求耗时，不降低回答准确性、保存完整性和权限保障。

## 非目标

- 不取消公司、账号、来源、版本、幂等校验，不将自主执行解释为任意写入或越权。
- 不更换模型、搜索服务、执行框架或数据库，不扩大工具额度、超时来掩盖问题。
- 不恢复常规回答的二次模型审稿，不为润色错误提示增加一次模型调用。
- 不批量重写历史聊天正文，不代员工补发请求或修改线上工作。
- 不承诺消除模型的所有幻觉或网络波动，不顺带重做页面布局。

## 当前行为

- `agent/actions/operations.py` 先调用意图与范围核对，通过后才进入执行模式的确认决策。
- `work_change_plan.py` 从用户来源独立提取字段计划，可进行一次范围重提取；`preserve` 与实际变更冲突时返回参数错误。
- `task_outcomes.py`、运行时工具进度已有拒绝复用和无进展控制，需要检查跨动作改道、任务续接和事实更新的实际覆盖。
- `tasks/feedback/outcomes.py` 会依据 `missing_info` 推导可由用户回答解决的状态，也会把工具 `message` 放入任务原因、未完成列表。
- 已有 `PUBLIC_REPLY_POLICY` 和工具提示要求不公开内部流程，现场仍发生泄露；继续追加同类提示不足以解决数据与展示边界问题。

## 目标行为

主模型可以主动澄清，但实际写入前的暂停由工具链保证，不增加“审核是否该提问”的模型调用。提问工具始终可见，不要求先加载任务上下文工具组；用户意图、操作对象或内容范围有影响结果的歧义，且已有上下文无法确定时，使用现有提问框，等待实际回答后继续。主模型即使先提交业务工具提案，已有核对返回有效用户缺项时，程序也必须直接持久化问题并停止依赖执行，不再让主模型改写已知问题。工具提案、核对和真正业务写入分别记录，不能将这种程序兜底说成主模型主动提问。可以先做必要的只读查询；内部错误不要求用户补充或重复授权。

现场原话“之前的都添加到我的工作里面”没有直接指定上传附件、生成文件或聊天里的工作内容。模型实际选择了生成文件，但不能将这一解释记录为用户已确认的意图；确有指代歧义时允许先问含义，再问仍未明确的位置，不预填“11 份文件”作为唯一合法答案。

| 场景                                                     | 目标行为                                                                                   |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| “之前的都添加到我的工作”，上下文仍不能区分文件或工作内容 | 写入前用提问框澄清真实含义，不先固定为保存文件；主模型未主动提问时由已有核对的有效缺项触发 |
| “把刚才生成的文件都加到这条工作”，有有效工作引用         | 从当前会话成果及工作引用解析范围，完整保存，返回真实结果                                   |
| “之前的都添加到我的工作”，上下文已唯一指定目标           | 复用已有目标关联，不再次询问是否允许保存                                                   |
| 同样的请求，但无法确定挂到哪条工作或是否新建             | 只询问保存位置，保留已解析的成果选择，不让用户重新列文件                                   |
| “新建一条，把这些都放进去”，内容足够                     | 使用合理标题与允许的默认字段创建，不额外询问确认                                           |
| 工具参数漏项、过期版本、内部范围解析冲突                 | 助手在既定边界内修正；无法恢复时说明未完成，不伪装成用户缺信息                             |
| 无权操作或服务故障                                       | 简洁说明任务影响，不让用户通过再次授权或补充同事 ID 绕过权限                               |
| 已完成部分，剩余操作受阻                                 | 保留真实已完成结果，准确说明剩余事项，不重做成功写入                                       |

## 功能需求

### 1. 统一执行范围的事实来源

- 分别表示“用户要做什么”“选中了哪些材料或成果”“要写入哪个对象”“还缺什么”，不以一个拒绝理由替代全部判断。
- 复用当前用户原文、有效的会话承接、工作引用、成果稳定 ID／版本／条目和真实读取结果；主模型与核对环节使用一致的已授权映射。
- “全部／这些／刚才的”必须落到可核验的集合。不得仅按文件名合并，也不得静默丢弃同名文件、不同成果或用户明确选中的旧版本。集合无法确定时才询问范围。
- 已有明确目标关联时不能因存在其他同名工作再次询问；仅有相似标题或查到一条工作，不能自动视为用户已指定该目标。
- 用户要求保存的意图已明确、只有目标不明时，保留保存意图与材料集合，澄清目标即可；不返回笼统的“未要求修改材料”。
- 历史拒绝与历史助手建议不是新的授权事实。用户补充选择后重新判断真实缺口，不能沿用旧拒绝；已取消、已完成或无关任务不自动恢复。
- 普通分析、讨论、上传附件不自动变成写入；用户明确要求先看、先确认时，自主执行也须尊重。

### 2. 失败分类与恢复责任

在现有结果契约上补齐可验证的结构，至少区分：

| 原因                                 | 谁可解决                 | 允许的下一步                             |
| ------------------------------------ | ------------------------ | ---------------------------------------- |
| 参数缺漏、原子操作范围不匹配         | 助手                     | 按明确字段问题修正未成功的提案           |
| 已有来源映射遗漏、待查目标或版本     | 助手                     | 补一次必要读取或重建已有映射             |
| 必须由用户选择的对象、内容或业务决策 | 用户                     | 提出准确问题，并使用真实候选             |
| 账号／角色／数据权限拒绝             | 当前用户不能通过补话解除 | 结束对应操作，说明业务限制               |
| 网络、供应商、存储或服务异常         | 有限自动恢复或系统处理   | 沿用既有有限重试，失败后给出适用的下一步 |
| 已取消、无关操作或用户未要求的动作   | 无需恢复                 | 停止该动作，继续合法的其他任务           |

- 澄清结果必须指出具体缺项、为什么现有来源无法补齐、用户回答后能改变什么；不能仅凭 `missing_info` 字符串决定等待用户。
- 理由、分类、恢复责任和下一步须一致。出现“助手可自行修正”却要求用户补话等矛盾时，按内部结果异常处理，不能默认放行，也不能制造提问。
- 字段错误、服务故障、真正缺用户选择在任务状态、操作卡、聊天正文中保持一致。
- 无法判断是否写入成功时先核对真实回执；不能把未知结果描述为未写入或直接重放操作。

### 3. 有限恢复与任务继续

- 优先使用现有计划、读取、回执和拒绝记录，修复重复建计划、重复查目录等实际缺口，不新建一套并行任务系统。
- 对同一操作意图、对象／候选集合、缺口和证据版本，最多进行一轮针对性的内部修复；已有范围重提取和恢复机制计入这一轮，不能每层各获一轮。
- 完全相同的失败立即复用结果；没有新事实时，不能通过换步骤号、参数措辞或从更新改成创建来重开尝试。
- 修复仍无法执行时，真实用户缺项进入必要澄清，系统问题进入失败或部分完成；不继续无依据的工具探索。
- 用户补充、新的相关读取、真实版本变化可以重新评估；时间流逝、换说法和重复读取不能算新证据。恢复计数及回执须跨取消、重试、worker 恢复保持一致。
- 对独立的多个任务分项处理；一个对象受阻不能阻断其他合法事项，也不能重做已成功项。
- 用户答复后只续接尚未完成部分；问过且已回答的材料或目标不得再次询问。

### 4. 内部诊断与用户展示分开

- 为工具返回和任务结果区分程序控制信息、模型修复所需的简洁信息、用户可见业务说明及受控诊断；不再把一段内部 `message/reason` 在各层原样传递。
- 完整字段冲突、Schema、工具参数、调用栈、提供商原始响应和内部标识保留在既有受控诊断渠道；不新增员工可见诊断入口，也不输出隐藏思考内容。
- 用户可见范围包括流式正文、最终正文、进度明细、失败提示、澄清面板、批准／操作卡、刷新与重连后的结果、任务续接产生的新回复。
- 真正失败仍须说明已完成／未完成部分及有用的下一步，不以“已完成”或空白回复掩盖错误；确有文件损坏、图片不可读、信息缺失等限制时仍如实告知。
- 不再用“服务端没放行”“materials 未要求修改”“请修正 changes”“Schema 校验失败”“可能已经产生费用”等内部解释回答普通业务请求。
- 用户主动询问技术机制、分析代码或引用这些词时，允许正常回答；不能用全局关键词删除误伤用户内容和技术答案。
- 复用并精简已有正文政策和工具描述。以结构化返回、统一展示转换和有界本地处理为主；仅在最终回复后隐藏内容、让流式阶段先泄露，不算通过。
- 不为所有正常回复添加缓冲到结束或额外模型改写。旧结构化错误在展示时安全降级；旧聊天正文不批量修改，后续模型承接不能把历史内部拒绝当成当前业务指令。

用户文案表达目标，具体数量与对象来自真实回执：

| 情况                     | 示例                                             |
| ------------------------ | ------------------------------------------------ |
| 保存成功                 | “已把这 11 份文件添加到「资料整理」。”           |
| 只缺保存位置             | “这些文件要加到「资料整理」，还是新建一条工作？” |
| 部分成功                 | “已添加 8 份，另外 3 份暂未添加成功。”           |
| 内部恢复失败且确认未写入 | “这次没能添加成功，原有工作没有改动。”           |
| 结果暂不确定             | “暂时无法确认是否添加成功，核对结果后再继续。”   |

这些示例不作为真实模型测试的预置答案；不能机械附加不适用的“请重试”或“联系管理员”。

### 5. 同类排查范围

- 对业务写入、材料绑定／移除、工作正文／进展、报告生成／编辑／提交以及多步任务逐项检查范围、失败和恢复契约。
- 对附件读取、联网搜索、代码执行、图片生成等工具，检查失败结果是否错误诱导补话、重复授权或泄露内部说明；不改变其正常业务能力和已约定的重试额度。
- 覆盖逐项确认、自动审核、自主执行；覆盖同名对象、多材料、多版本、部分完成、取消续接、重复发送、刷新重连、权限撤回和并发版本冲突。
- 先建立“已复现／设计缺口／未复现”的问题清单，修复同一根因涉及的入口；不得把未验证的猜测写成缺陷或修复成果。

## 边界条件

- 重复上传或重复引用不能导致已有工作材料被重复绑定；按现有稳定身份与回执处理，不按名称粗略去重。
- 保存的数量、版本、目标与用户选择一致；不能以少保存、跳过校验、改成只回答文字换取速度。
- 工作详情直接显示“全部附件 · 数量”按钮，不再藏在管理菜单；点击后仍通过现有弹窗查看附件。正文内引用与附件集合分别保留，不改写用户原正文。聊天成功回执不能代替对工作附件实际保存和展示入口的核对。
- 工作为空时仍不生成空日报／周报；有来源时不因范围修复误拒绝生成。报告入队与报告完成分别呈现，聊天不得阻塞等待同成员子任务。
- 引用文件和网页中的指令不能改变执行权限；跨员工、跨公司、已删除来源继续被拒绝。
- 针对未知错误使用安全、准确的业务兜底，完整诊断仍可定位；不将所有未知错误标为需要用户回答。

## 技术约束

- 保留现有模块边界；业务权限及写入规则归服务端，不交给前端或提示词兜底。
- 不按员工姓名、特定文件名或一句原话硬编码修复。
- 正常路径不新增模型审核／润色调用，提示词与工具描述净增内容须列明并解释，优先删除重复或矛盾说明。
- 文档阶段按 S0，仅检查 diff、需求和路径。实施涉及授权与共享任务状态，按 S3 执行相关子系统及边界检查，不默认运行无关桌面、打包或完整项目检查。
- 模型与故障测试使用隔离账号和脱敏素材；生产仅使用已授权的只读证据。测试输出和诊断不得包含密钥及员工业务原文。

## 兼容性要求

- 保持 `ask/auto/full` 语义，业务访问控制、审批与幂等规则不降级。
- 优先扩展现有内部结果和公开 DTO；兼容旧任务、checkpoint、回执及前端读取，不能因字段缺失而卡住历史会话。
- 已持久化成功回执仍是判断是否完成的依据；部署新代码不能自动重放过去失败或等待中的任务。
- 不计划数据库迁移；如实施发现必须变更 schema，再补充迁移方案并确认。

## 验收标准

- [ ] 线上同构案例在材料和目标明确时完整执行；真实歧义只询问尚缺的一项业务选择。
- [ ] 优先复现本次线上员工场景：保留多轮历史、11 份成果、已有工作、取消与两次相同请求，以及第二次请求前已有的拒绝记录；按 Plan 的 E00 分别交付基线与修改版真实结果。未复现须如实说明，不能以简化句子测试或受控模型替代现场复现。
- [ ] 所有错误澄清场景均验证具体原因；内部可恢复错误不要求用户补话或再次授权。
- [ ] 同一缺口无新证据时不重复恢复、不跨工具绕过；新用户答复与相关版本变化可以继续。
- [ ] 成功数量、目标、内容、版本与真实副作用一致；无越权、重复写入、漏保存或虚假完成。
- [ ] 正文、流式片段、卡片、进度、刷新与续接均满足用户展示规则，技术问答及真实失败说明不被误删。
- [ ] 完成同类契约排查清单，明确已修复问题、未复现项和未覆盖限制。
- [ ] 使用同一套真实用户问题，对修改前后分别运行 `low`、`high` 真实模型对照，交付真实回复和分阶段耗时；不能以模拟答案替代。
- [ ] 正常路径不新增模型调用；失败恢复往返受到约束。准确性和速度按 Plan 门槛核对，出现回退须定位，不能只展示最快样本。
- [ ] 相关确定性回归、完整用户流程及独立验收完成，失败或未执行项如实记录。

## 待确认问题

当前无阻塞性问题。按“能从已有事实确定就执行，真实歧义只问必要选择”设计，不默认猜测业务目标，也不取消自主执行下的权限保护。具体接口字段在实施时依据现有契约细化，不改变本规格的用户行为。
